我建议这次**不再把它设计成“廉价审美评分器”，而是设计成“高质量图片召回器”**。

这两种设计的区别很大：前者会不断尝试让第100名比第101名更合理；后者真正关心的是，**一张本来值得精筛的图片，是否因为低热度、采集时间、画师知名度或标签偏差，被挡在前33.3%之外。**

因此，我会保留旧方案中“按Rating分别处理”和“校正时间因素”的方向，但放弃过于复杂的全局审美加权，改成：

> **较简单的主公式＋独立的低曝光补救通道＋少量随机审计。**

下面将这一版称为 **MetaRecall v1**。你这次提供的是字段说明，没有附带新版全库分布与审美验证标签，因此下面的数值是**可直接实现的首版默认参数，不是已经通过实验确认的最优权重**；所有特征均围绕你实际拥有的字段设计。

---

## 一、先确定整体结构：不是只截取一个分数榜的前三分之一

我建议仍然在 `g / s / q / e` 内分别筛选，每个Rating保留约33.3%，但把名额拆成三部分：

| 入选通道        | 占该Rating候选池的比例 | 主要作用                      |
| ----------- | -------------: | ------------------------- |
| **主公式通道**   |      **28.0%** | 保住有较明确正面证据、没有严重负面信号的大多数图片 |
| **低曝光补救通道** |       **4.3%** | 补进绝对热度不高，但相对表现或画师先验较好的图片  |
| **随机审计通道**  |       **1.0%** | 给公式盲区留下被发现的机会，并估计误杀情况     |
| **合计**      |      **33.3%** | 全部进入后续LLM精筛               |

**这些比例全部以原候选池为分母，不是依次对剩余图片取百分比。** 三条通道依次从尚未入选的图片中取图，所以不会重复占名额。

这里的候选池，应当是“经过文件可用性检查、训练用途限制和字节级去重之后的图片集合”。原始记录数、可用图片数、用途过滤数、元数据初筛淘汰数要分别统计，不能把它们混成一个“低质量淘汰率”。

### 为什么不直接用一个超级公式取33.3%？

因为不同证据的可靠性不一样。

绝对热度很适合找到“有充分关注度支持的图片”；同年代、同帖龄的相对热度，更适合寻找“可能被低估的图片”；画师先验只能提供有限的间接支持。

将它们全部混成一个分数，就很容易出现：

> 为了救出一部分冷门好图，必须提高时间校正或画师权重，结果又把大量普通图片一起抬上来。

拆分名额后，**补救机制可以积极一些，但它最多影响4.3%的候选池，不会接管整个榜单。**

不过，28%／4.3%／1%不是不可修改的比例。最终应根据补救通道实际找回多少好图，以及它替换掉的主榜边缘图片质量如何来调整。

## 二、先把“资格判断”与“审美代理信号”彻底分开

新版字段里有几处很容易造成系统性误筛，值得在公式之前固定下来。

### 1. 分辨率是训练用途门槛，不是审美加分项

沿用你此前的**最短边至少768**要求，但检查对象应该是实际保存的成品尺寸，而不是源站原图尺寸。

按照字段表，读取顺序是：

```text
storage_details_json.stored_width / stored_height
    ↓ 缺失时
assets.observation_id 对应原记录中的
raw_stored_width / raw_stored_height
```

两处都没有，就保留“尺寸未知”，不能用 `image_width / image_height` 冒充成品尺寸。你的字段说明明确区分了二者。

我的建议是：

**达到训练门槛后，不再因为尺寸更大而增加初筛分数。** 1024、1536、2048乃至更大的图，交给LLM看实际质量，不让像素数量继续竞争审美名额。

尺寸不达标的图片进入“用途不匹配”队列；尺寸未知的进入“待核验”队列，都不要直接标成“低质量”。

### 2. 站点状态不直接等同于画质

| 字段或信号                     | 首版处理                 |
| ------------------------- | -------------------- |
| `has_image`、已知解码失败、明确损坏   | 文件可用性检查              |
| `is_deleted`              | 不直接作为低质量判据           |
| `is_pending`、`is_flagged` | 保留状态标记，不自动扣审美分       |
| `is_banned`               | 交给独立的使用资格／分发策略检查     |
| `issues_json`             | 判断哪些字段不可用，不按问题数量统一扣分 |

尤其不能认为“被封禁就画得差”。Danbooru当前源码中，`paid_reward` 或被限制的画师标签等情形就可以触发 `is_banned`，这不是一个纯粹的画质标签。([GitHub][1])

### 3. 一些看起来能打分的字段，首版明确不用

`stored_bytes`、`file_size`、WebP编码quality、标签总数量、是否填写来源，都不直接增加或减少审美分。

同样，**漫画、线稿、黑白、简单背景、扫描媒介，不自动等于低质量。** 其中确实不适合本轮训练的类型，可以在“训练用途”层单独分流；但不要把“不是这次想训练的类型”写成“审美差”。

这样能避免公式越复杂，暗含的风格偏见越多。

## 三、主公式：绝对热度为主，时间因素只做有限补救

主通道使用下面这个分数：

$$
\boxed{
S_i
=
100\,\operatorname{clip}_{[0,1]}
\left[
G_i
+
0.30(C_i-G_i)_+
-
0.08V_i
-
T_i
\right]
}
$$

其中：

| 符号        | 含义                   |
| --------- | -------------------- |
| \(G_i\)   | 同Rating下的绝对热度百分位     |
| \(C_i\)   | 考虑上传年代、采集时帖龄后的相对表现   |
| \(V_i\)   | 有一定支持度的负票异常，范围0～1    |
| \(T_i\)   | 少量明确技术缺陷的惩罚，默认上限0.08 |
| \((x)_+\) | \(\max(x,0)\)        |

**\(S_i\)是入选优先级，不是审美分，也不是“有多少概率是好图”。**

这个结构有一个重要特点：

> 时间校正可以有限地帮助一张图片，但不会因为“它在自己的年代没那么突出”，就直接扣掉它已经取得的绝对热度。

当然，固定名额下，其他图片被补救上来仍然会造成竞争；这里避免的是公式对某张图施加直接的时间负分。

### 3.1 合并收藏和赞票，不重复计算三次热度

定义：

$$
F_i=\texttt{fav\_count},
\qquad
U_i=\texttt{up\_score}
$$

先计算共同热度：

$$
\boxed{
L_i
=
\frac{\ln(1+F_i)+\ln(1+U_i)}{2}
}
$$

再在同Rating内，将 \(L_i\) 转换成中位秩百分位：

$$
\boxed{
G_i
=
\frac{
\#\{j:L_j<L_i\}
+
0.5\,\#\{j:L_j=L_i\}
}{
N_r^{\mathrm{valid}}
}
}
$$

这里的分母是该Rating下热度字段有效的图片数。

采用中位秩，意味着同样的收藏／票数得到相同的热度位置，而不是靠帖子ID或数据库行顺序偷偷分出高低。

选择合并，而不是分别给予“收藏分”“点赞分”“净分”，还有一个实际依据：**Danbooru的收藏操作会在满足投票权限等条件时触发赞票，取消收藏也会相应撤销赞票。** 它们不是两批彼此独立的评价者。

因此，首版不使用：

$$
a\cdot fav+b\cdot up+c\cdot score
$$

这种三次重复计入热度的形式。`score`主要用于一致性检查，不再次正向加分。

缺失值则按下面处理：只有收藏或赞票一项有效时，用有效项计算对数热度，同时记录缺失标记；两项都缺失时，使用中性占位 \(G_i=0.5\)，并标记“热度未知”。**不能将未知补成0收藏、0赞票。** 这类记录的入选与漏选情况必须单独审计。

### 3.2 时间校正必须使用“采集时的帖龄”

这是新版方案最需要落实的一处。

定义：

$$
a_i
=
\texttt{observed\_at}_i
-
\texttt{created\_at}_i
$$

它表示：

> 当前这份收藏和票数快照，是帖子上传之后多久采集到的。

不是：

$$
\text{今天}-\texttt{created\_at}
$$

例如，一张2024年1月1日上传、1月3日采集时有2个收藏的图，现在仍然只是“上传两天时有2个收藏”的记录，不能被解读成“放了两年仍然只有2个收藏”。

你的字段表还明确说明，`updated_at`是源站记录更新时间，`ingested_at`是进入本地新库的时间，二者也不能替代真实观察时间。

首版按以下条件建立比较群体：

$$
\text{同Rating}
+
\text{相近上传时间}
+
\text{相近采集时帖龄}
$$

建议默认设置为：

| 项目      | 默认设置                                                 |
| ------- | ---------------------------------------------------- |
| 上传时间邻域  | 前后各6个月                                               |
| 采集时帖龄桶  | 0～3天、3～7天、7～14天、14～30天、30～90天、90～365天、1～3年、3～7年、7年以上 |
| 邻域最低样本量 | 5,000张                                               |
| 样本不足    | 先扩大上传时间邻域，再合并相邻帖龄桶；仍不足则停用该项补救                        |

在这个比较群体里，对 \(L_i\) 再算一次中位秩百分位，得到 \(P_i^{\mathrm{local}}\)。

**这不是给每个年代各保留33.3%。** 它只是补充一个特征，最终名额仍然在整个Rating内竞争。

### 3.3 对“小支持度下的高百分位”做适度收缩

假如一个很年轻的比较群体大多只有0收藏，某张图仅凭1个收藏就处在很高百分位，不宜直接把它当成强证据。

先对比较群体本身做收缩：

$$
Q_i
=
0.5+
\frac{n_i}{n_i+1000}
\left(P_i^{\mathrm{local}}-0.5\right)
$$

再定义正面互动支持量：

$$
M_i=\max(F_i,U_i)
$$

这里不用 \(F_i+U_i\)，避免把高度重叠的互动当成双倍支持。

支持度收缩参数从相同比较群体估计：

$$
K_i
=
\operatorname{clip}_{[1,10]}
\left[
0.25\,
\operatorname{median}(M_j\mid M_j>0)
\right]
$$

$$
c_i=\frac{M_i}{M_i+K_i}
$$

最后得到时间条件化表现：

$$
\boxed{
C_i=
\begin{cases}
Q_i,&Q_i\le 0.5\\[4pt]
0.5+c_i(Q_i-0.5),&Q_i>0.5
\end{cases}
}
$$

这里刻意采取了**单侧收缩**：

**对“高百分位但互动支持很少”的上浮证据打折；不因为一张低百分位图片票数少，就自动把它抬回中等位置。**

这比对所有低票图片统一收缩到50分，更符合“让低质量候选沉底”的目标。

这些系数是用于约束特征的工程规则，**不是经验证的审美置信概率**。观察时间未知时，直接设 \(C_i=G_i\)，停用时间补救；只有日期精度、且恰好处于短帖龄桶边界的记录，应采用更宽的比较桶，而不是假装知道精确小时。

### 3.4 负票只做有限扣分，不做一票否决

定义负票数量：

$$
D_i=|\texttt{down\_score}_i|
$$

在同Rating内，从有效记录估计总体负票比例：

$$
q_{0,r}
=
\frac{\sum_jD_j}{\sum_j(U_j+D_j)}
$$

对单图进行平滑：

$$
\widehat q_i
=
\frac{D_i+20q_{0,r}}{U_i+D_i+20}
$$

再定义：

$$
\boxed{
V_i
=
\mathbf 1[D_i\ge3]
\cdot
\operatorname{clip}_{[0,1]}
\left[
\frac{\widehat q_i-q_{0,r}-0.05}{0.25}
\right]
}
$$

这个设计意味着：

**一两个负票不扣分；负票比例明显异常且有一定数量支持时才扣；最多扣8分。**

同时，如果赞票或负票字段缺失，停用该项并记录未知状态，不凭空推断。源站源码也明确将正票和负票分别累加到 `up_score`、`down_score`，所以这里使用两者，而不是拿净分估算负票比例。([GitHub][2])

保留这个较小上限，是因为我们没有“投票者为什么反对”的字段，不能把所有负面反应都解释成画质问题。

### 3.5 标签惩罚只保留窄白名单

首版 \(T_i\) 建议非常克制：

| 候选信号                                                        | 默认处理           |
| ----------------------------------------------------------- | -------------- |
| 已确认的压缩损伤标签，例如 `jpeg_artifacts`                              | 0.04           |
| 已确认的扫描损伤标签，例如 `scan_artifacts`                              | 0.04           |
| 同一类损伤的多个近义标签                                                | 取最大值，不重复累加     |
| 不同明确损伤类型合计                                                  | 上限0.08         |
| `sketch`、`lineart`、`monochrome`、`simple_background`等类型／风格标签 | 不扣             |
| `bad_anatomy`、`unfinished`等可能依赖目标定义的标签                      | 首版默认不启用，先验证误伤率 |

这里的具体token是**待对照本地标签词典确认的配置候选**，不是说你的附件已经证明这些标签都存在。

标签必须按完整token匹配。也不要用“没有损伤标签”反推“确认没有损伤”，它只能表示目前没有这项负面证据。完整token匹配、NULL与空串区分，都是你字段表已经明确要求的规则。

## 四、补救公式：主要看相对表现，画师只提供温和帮助

主公式得到前28%后，对剩余图片计算：

$$
\boxed{
R_i
=
100\,\operatorname{clip}_{[0,1]}
\left[
C_i
+
0.25A_i(1-C_i)
-
0.08V_i
-
T_i
\right]
}
$$

再按 \(R_i\) 取出约4.3%的原候选池名额。

与主公式相比，区别是：

**主通道依赖绝对热度 \(G_i\)，补救通道主要依赖条件化表现 \(C_i\)。**

所以，一张绝对收藏不高、但在相同上传年代和采集时帖龄下表现很好的图，可以绕过绝对热度门槛进入精筛。

### 画师先验 \(A_i\) 怎么计算？

我建议把画师信息从“全局加权因子”改成“只影响补救通道的正向先验”。

对同一画师、同Rating、上传时间前后各3年内的其他作品，统计 \(C_j\) 的平均表现。计算时排除当前图片，并对已知关联作品组限权，避免同一套大量变体制造虚假的支持量。

设这些其他作品的有效数量为 \(n_a\)，平均表现为 \(\bar C_a\)，同Rating总体平均值为 \(\mu_r\)，则：

$$
\widetilde C_a
=
\frac{n_a\bar C_a+50\mu_r}{n_a+50}
$$

$$
\boxed{
A_a
=
\operatorname{clip}_{[0,1]}
\left[
\frac{\widetilde C_a-\mu_r}{0.20}
\right]
}
$$

有效其他作品不足5张时，默认 \(A_a=0\)。多位真实画师标签共同出现时，使用有效画师先验的平均值；没有可用画师信息时也取0。

**这里的0表示“不提供额外帮助”，不是“差画师”。**

还要强调，\(A_a\)来自其他作品的元数据表现，它仍然只是“画师相关的正面先验”，不是经过视觉验证的画师审美水平。

例如：

$$
C_i=0.60,\quad A_i=0.80
$$

画师补救带来的提升是：

$$
0.25\times0.80\times(1-0.60)=0.08
$$

也就是从60分提升到68分。

而一张相对表现只有30分的图片，即便画师先验达到最高值，也只能提升到：

$$
0.30+0.25\times1\times0.70=0.475
$$

**不会因为“名画师”身份，就把明显弱势作品直接抬到高分区。**

另外，画师只能使用真实的画师标签解析结果，不能用 `uploader_id` 或 `pixiv_id` 替代。你的字段表已经说明：上传者不一定是画师，Pixiv作品ID也不是画师ID。

## 五、这套机制会怎样处理不同图片？

下面是假设输入特征后的机制演示，**不是全库实测，也不代表实际入选阈值**。暂时令负票和技术惩罚为0：

| 图片情况                 | \(G\) | \(C\) | \(A\) | 主分 \(S\) | 补救分 \(R\) |
| -------------------- | ----: | ----: | ----: | -------: | --------: |
| 绝对热度很高、相对表现也好        |  0.92 |  0.78 |  0.60 | **92.0** |      81.3 |
| 绝对热度偏低，但同条件下非常突出     |  0.35 |  0.92 |  0.00 |     52.1 |  **92.0** |
| 低曝光新图，同帖龄表现突出，画师先验较好 |  0.20 |  0.84 |  0.80 |     39.2 |  **87.2** |
| 绝对热度低，相对表现也不突出       |  0.16 |  0.28 |  0.00 |     19.6 |      28.0 |
| 画师先验很高，但单图相对表现较弱     |  0.12 |  0.30 |  1.00 |     17.4 |      47.5 |

这个例子展示了我最看重的分工：

**第一类走主通道；第二、第三类有明确补救路径；第四类自然沉底；第五类不会因画师身份自动入选。**

与此同时，也有一类图片，任何这样的公式都无法稳定识别：

> 画得非常好，但绝对热度低、同条件下相对热度也低、画师未知，而且没有其他可区分的元数据。

对于这一类，继续添加更多元数据系数，也未必能得到新信息。**随机审计就是为这种真正的信息盲区保留的入口。**

## 六、随机审计的1%，不是“无用图片配额”

在主通道和补救通道选完之后，从剩余图片中，在各Rating内均匀随机抽取相当于原候选池1%的图片。

这些图片同样进入后续LLM比较，**不是看完审计后就丢掉，也不增加33.3%之外的精筛预算。**

建议使用固定种子和稳定哈希实现可复现抽样。若图片没有可靠的字节哈希，就使用帖子标识构造独立抽样键，不能把所有NULL当成同一条记录。

这里最重要的是：

### 不只从分数边界抽样

仅检查排名30%～40%的图片，可以发现阈值附近的问题，却发现不了“某一类好图被系统性排到后80%”的情况。

所以默认审计应覆盖整个剩余池，再按年份、画师信息是否缺失、观察时间质量、图像类型等维度分析结果。

### 审计图片必须与正常入选图片发生比较

不能把审计样本全部分成互相隔离的16图组，然后只看每组第一名。否则一组整体很差的图片也必然有第一名，无法与主候选集建立共同尺度。

可以通过混合组图和重复参考图片建立连接；送给LLM时，不展示它来自哪条通道，也不展示收藏数和公式分数。

### “没入选”不等于“确定低质量”

最终输出建议区分：

```text
main_selected
rescue_selected
audit_selected
budget_rejected
metadata_unknown
technical_or_scope_excluded
```

特别是 `budget_rejected`：它表示在当前预算下没有优先获得精筛机会，不是一个经过视觉确认的“低质量”标签。

---

## 七、如何证明新版比简单收藏排序更好？

真正的评价目标应该是：

$$
\boxed{
\operatorname{Recall@33.3\%}
=
\frac{
\text{高质量图片中被初筛保留的数量}
}{
\text{全部高质量图片数量}
}
}
$$

不是元数据分与最终审美分的相关系数有多高，也不是榜单前100张看起来多漂亮。

尤其要避免一个验证陷阱：

> 只给已入选图片做LLM精排，再用这些图片来评价初筛公式。

那样永远看不到被筛掉的好图。

### 我建议的首轮验证方式

先从整个合格候选池建立一个约2万～5万张的独立验证样本。它需要覆盖低分区和元数据缺失区；采用非均匀分层抽样时，保留抽样概率，以便加权估计总体结果。

在这份样本上，用重复、互相连接的LLM排序和少量人工复核建立审美参考，再比较四个同预算方案：

| 方案                 | 验证目的         |
| ------------------ | ------------ |
| 同Rating按收藏数保留33.3% | 最简单且必须战胜的基线  |
| 新主公式直接保留33.3%      | 判断公式本身的增益    |
| 主公式28%＋补救5.3%      | 判断独立补救通道的增益  |
| 主公式28%＋补救4.3%＋审计1% | 完整方案的效果与可诊断性 |

重点看高质量验证图片的召回率，并分别检查老图、新图、低曝光图、未知画师、元数据缺失图等子集。

如果补救通道救回的好图，比它挤掉的主榜边缘好图还少，就减少补救比例；如果艺术家先验主要带来普通作品，而不是额外找回好图，就减小或关闭它。

**这版公式的复杂性必须通过额外召回来证明价值，不能因为公式更精巧，就默认它优于收藏排序。**

随机审计还有长期价值：它使你有机会发现某些子类持续被漏掉。之后可以针对实际漏图模式调整初筛，甚至用这些已获得的LLM结果拟合一个小型元数据分类器，而不用重新对全库运行视觉模型。

## 八、实现时，哪些细节不能省略？

### 先去确切重复，再分配LLM名额

可以按 `blob_sha256` 做字节级去重，保留帖子到图片的映射关系，不把多条记录的收藏数直接相加。

但不能仅凭相同 `parent_id` 或 `pixiv_id` 就删除图片，也不能把字段中的 `pixel_hash` 当作已经定义好距离函数的感知哈希。你的字段表只支持前者作为字节级去重依据，并特别提醒了 `pixel_hash` 的限制。

### 严格按名额截取，不用“分数大于66.7”代替

最终应该按排序后的数量取图。公式分数不是最终百分位，66.7分也不是前三分之一的固定门槛。

在截断边界遇到同分时，使用固定种子的哈希打散，避免总是优先较新帖子、较老帖子或某个存储批次。

### 固定输入快照和中间特征

至少保存：

```text
post_id / observation_id / asset_id
G / C / A / V / T
main_score / rescue_score
selected_route
missing_flags
config_version / sampling_seed
```

同时固定此次使用的输入记录集合、参考时间与统计表。不能只固定公式，却让后续重跑时读取不断变化的当前元数据和百分位分布。

你的 `posts` 当前记录也不是简单按最大 `updated_at` 选出的，不能在实现时自行换成另一套“最新记录”逻辑。

### 首版不开“增长速度”额外加分

新版确实有 `observations` 历史表，但字段简表没有证明：有多少图片拥有至少两次可靠、同口径、时间间隔合适的互动快照。

所以首版使用的是**时间条件化比较，不是真实增长率**。

以后确认历史观测覆盖率足够，再考虑把真实增长信号放入补救通道；不要把“累计收藏÷帖龄”包装成可靠的上升趋势。

## 我的最终建议

这一版的核心可以压缩为：

$$
\boxed{
\begin{aligned}
\text{主通道：}\quad
S_i&=100\operatorname{clip}
\left[G_i+0.30(C_i-G_i)_+-0.08V_i-T_i\right]\\[3pt]
\text{补救通道：}\quad
R_i&=100\operatorname{clip}
\left[C_i+0.25A_i(1-C_i)-0.08V_i-T_i\right]
\end{aligned}
}
$$

**按Rating独立运行，主通道28%，补救通道4.3%，全剩余池随机审计1%。**

相比继续修补旧式加权审美榜，我更倾向这套设计，原因不是它能从元数据里读出更多视觉信息，而是它**明确限制了每类代理信号的权力，并给可能被误杀的图片留下了可检验的补救路径**。

进入这33.3%之后，元数据分就完成使命：后续16图一组的比较应重新以图像为依据，通过跨组连接、重复曝光和允许并列的统计排序建立审美结果，**不要让初筛分数继续成为LLM精排的隐性先验。**
