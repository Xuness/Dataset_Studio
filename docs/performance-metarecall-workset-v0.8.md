# 0.8 性能排查：全湖排名与工作集首屏

2026-09-09，北京时间。基于用户实际任务、项目记录、当前源码、只读 SQL/API 检查及隔离微基准。此次排查没有修改引擎代码或运行配置；继续排查阶段未使用 Computer Use。

2026-09-10 后续：修复已实施并更新开发环境，结果见 [0.8.1 性能修复与验收](verification-performance-v0.8.1.md)。下文保留修复前的诊断依据。

## 结论与处理顺序

1. **先修工作集浏览。** 准备排序期间，每轮轮询都重复枚举工作集来源；当前实现扫描 1,149 万成员并持有项目数据库锁。首屏还必须等待全量排序结果构建，实际触发十分钟超时。
2. **改进保存入口的范围表达。** 当前工作集保存的是评分任务的全湖输入查询，没有关联排名成果或榜单过滤条件。同名操作入口容易造成误解。
3. **使用优化后的计算引擎。** 当前开发启动器固定使用 debug 引擎，SHA-256 是已实测的显著开销；只构建 release 文件还不够，启动器选择路径也需要支持。
4. **消除重复完整校验，合并中间写入事务。** 保留完整性和最终持久化要求，通过复用同一份校验证明、放大有界批次来减少重复工作。

### 重复校验已由执行路径确认

正式评分前的三次完整输入哈希：

1. `ranking.rs:204` 为新输入生成 SHA-256。
2. `ranking.rs:213` 调用 `worker::load_plan`，再次读取整个输入验证哈希。
3. 工作进程启动后再次调用 `load_plan`，再次验证同一输入。

评分后，`jobs.rs:399` 先调用 `worker::validate_output`；完成重命名后进入 `ranking.rs:619`，再次调用同一份 `validate_output`。每遍都会验证输入哈希、分页遍历全部输入和评分记录、检查分数/名次/名额，再计算输出哈希。

这一正常路径合计五次输入全文件哈希、两次输出全文件哈希，以及两次全行结果校验。恢复路径仍需要独立校验，优化时不能无条件绕过。

### debug 哈希与优化构建对照

当前引擎 PID 57996，实际加载开发构建缓存；`tooling/dev.mjs:140` 固定读取 `target/debug/studio-engine.exe`。根 `Cargo.toml:36` 的 dev 配置没有设置优化级别。

在相同机器上，用相同 `sha2 0.10.9`、相同 64 KiB 读取循环，对同一 128 MiB 缓存样本各测三次：

| 项目 | 中位吞吐 |
| --- | ---: |
| debug SHA-256 | 69.37 MiB/s |
| release SHA-256 | 1,583.32 MiB/s |
| 同一读取循环只读、不哈希 | 约 4,300 MiB/s |

两种构建的哈希完全一致，SHA-256 局部速度相差 **22.82 倍**。正式任务中三次启动前输入校验约占四分钟，与 debug 吞吐量相符。样本位于文件缓存中，因此这个测试用于分离 CPU 哈希开销，不是物理磁盘带宽测试，也不能据此声称整个任务会快 22 倍。

### 512 项事务带来的同步开销

`ranking_tables.rs:77` 使用 `journal_mode=DELETE`、`synchronous=FULL`；`append_members`、输入 `append` 和评分 `append` 每批最多 512 项并立即提交。千万级输入使每个完整写入阶段达到约 22,449 批，另外还要维护输入和评分索引。

隔离测试使用与评分表相同的建表语句、初始分级索引、131,072 条合成记录；三种批次均保持 DELETE/FULL，每种测两次：

| 每次提交项数 | 事务数 | 平均总耗时 | 备注 |
| ---: | ---: | ---: | --- |
| 512 | 256 | 1.350 秒 | 其中提交耗时约 0.94 秒 |
| 8,192 | 16 | 0.405 秒 | 相同记录与相同持久化设置 |
| 32,768 | 4 | 0.400 秒 | 本样本收益已接近 8,192 项批次 |

这是 Python SQLite 的隔离写入对照，局部约 **3.34 倍**；没有把该倍数套用到真实 Rust 全流程。合并事务时仍需保留内存/日志预算、取消响应及恢复语义。

只读 `EXPLAIN QUERY PLAN` 确认现有评分读取使用 `ordinal` 范围索引；分级读取使用 `(rating, ordinal)` 索引。此次没有发现评分分页依赖大 OFFSET 或每页从头扫描。

## 工作集为何迟迟没有图像

工作集 `Danbooru数据湖筛选`，ID `47df80cf-7bc2-4491-ac2b-234504d8ca47`，共 11,493,687 项。

项目记录证明它来自全湖输入查询 `f99a0280-615c-4207-a3ef-8dc62b8ea890`，`ranking_workset_requests` 中没有对应记录，也没有排名成果引用。当前排名草稿的榜单条件是 G 分级、合格候选、无前 N 名限制，工作集没有使用这些条件。

工作集保存成员，当前资料浏览的顺序由浏览器排序选项决定，不会自动沿用 MetaRecall 的排名顺序。若希望保存榜单过滤结果，应在“结果榜单”设置范围/前 N 名，再使用榜单内部的“存为工作集”。已经生成的分数可以继续用于这些筛选，不必因此重新计算分数。

### 首屏前发生了全量构建，并且轮询重复做重查询

1. 保存的浏览排序为 `post_id_desc`，界面名称为“Danbooru ID 从新到旧”。
2. `api.rs:579` 先调用 `scope_source_ids`。该函数在项目数据库锁内执行 `SELECT DISTINCT source_id FROM collection_members ...`。
3. 浏览接口创建内部范围排序结果，只有整个结果准备好后才返回首批图像；超过 4,096 项的范围会走通用全来源扫描及成员过滤路径。
4. 准备期响应包含 `result_id`，但前端继续轮询原始工作集浏览接口；`Browser.tsx:159` 的轮询间隔是 800 ms。没有复用已知来源信息，每次都会再次执行第 2 步。
5. 后台过滤与进度更新也使用同一项目数据库锁，所以来源枚举不仅使轮询昂贵，也会争用构建需要的数据库访问。

在这个真实工作集上，只读复现得到：

| 来源枚举方式 | 结果 | 耗时 | SQLite VM 指令数量 |
| --- | --- | ---: | ---: |
| 当前 DISTINCT 查询 | 1 个来源 | 2.402 秒 | 至少 80,455,000 |
| 从项目来源逐个做成员存在性索引查询 | 同一个来源 | 约 0.075 毫秒 | 小于 1,000 |

当前查询使用的是 `collection_id` 前缀索引，但仍遍历该工作集的全部成员。候选查询使用 `(collection_id, source_id)` 前缀后立即结束。这个对照证明本工作集上的重复扫描可以消除；推广到其他范围类型时仍需验证来源引用语义。

### 这次已经超时，原始原因在界面中被弱化

内部排序结果 `7d3ef9d4-9b60-483d-be1b-75b8dfad126d` 于 22:27:37 创建，在 22:37:39 记录 `SOURCE_TIMEOUT`。停止时已处理 10,984,960 项，尚未发布结果。

之后 `validate_result` 将非 ready 状态统一变成 `RESULT_NOT_READY`；再次请求返回“结果尚未完整构建或已释放”，没有保留清晰的十分钟超时原因。失败记录还会被再次查找到，需显式释放/重试，单纯继续等不会完成原来的构建。

### 已验证的临时浏览方式

没有修改用户排序设置，通过后台 API 对同一工作集测试：

- “图像身份升序”：HTTP 200，**504.6 ms** 返回首批 **48 项**，有下一页游标，无准备状态。
- “Danbooru ID 从新到旧”：HTTP 409，**3,299.4 ms** 后返回 `RESULT_NOT_READY`。
- 首批中的一张 360 像素预览：HTTP 200，JPEG **24,780 字节**，**56.4 ms** 返回；未清空缓存，不代表冷缓存全湖预览吞吐。

因此可以临时手动切到“图像身份升序”继续查看成员。它改变浏览顺序，不改变工作集成员。

## 建议的修复组合

| 优先级 | 改动 | 必须验证的边界 |
| --- | --- | --- |
| P0 | 来源枚举改为有界索引查询；准备期使用已返回的排序结果 ID 查询状态 | 多来源、空工作集、来源失效、切换范围、重连；轮询开销不随成员数线性增长 |
| P0 | 浏览接口保留失败原因并提供明确恢复路径 | 超时、取消、失效、释放各有正确状态；不会无声反复重建 |
| P1 | 利用现有帖子排序索引分页与工作集求交，避免首屏等待全量物化 | 稠密/稀疏工作集、多来源合并、未知帖子 ID、游标稳定性及扫描预算 |
| P1 | 开发界面与优化后的引擎构建分离，启动器实际选择正确产物 | 构建缓存身份、运行实例切换、开发刷新及发布构建一致性 |
| P1 | 结果只完整验证一次，并携带哈希与验证结果进入原子发布；中间写入合并到有界较大事务 | 损坏拒绝、输入变更拒绝、崩溃恢复、取消、重试、计数/名额一致；最终成果保持持久化保证 |
| P1 | 两个保存入口明确显示目标范围、条件和预计数量 | 用户能分清保存当前浏览范围与保存榜单过滤结果 |
| P2 | 增加阶段开始/结束时间、分级、进度心跳和组件耗时 | 不用估算值伪装实测值；优化前后可以重复对照 |

本轮止于诊断，没有部署上述性能改动，也没有调整用户现有工作集。工程上的下一步应把相关路径一起改好，再统一进行正确性、恢复和性能验收。
