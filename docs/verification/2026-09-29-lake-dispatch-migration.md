# 数据湖更新运行器：缺失调度表的迁移修复

基线：`8bb37a3`。用户启动前端后持续收到 `UPDATE_UNAVAILABLE`，请求编号 `56445526-5d02-4fc9-ac30-2ed51d253fed`。

## 原因与范围

本机更新控制库已经记录 schema 6，但缺少 `lake_dispatch` 表。只读执行真实调度查询得到 `no such table: lake_dispatch`；解释器依赖检查通过，运行器在握手后第一次调度时退出。

缓存的内置 worker 证实：16:07–16:16 的开发中间版本已写入 v5，尚未包含 `lake_dispatch`；16:29 的版本才加入该表，17:31 的版本升级到 v6。已经执行过 v5 的控制库不会再次执行后来修改的 v5 建表代码。这是此前验证遗漏的开发期升级兼容问题。

## 修复

- 新增 schema 7，幂等补齐调度表；已有按湖服务顺序保持。
- 继续使用初始化、运行器与任务执行锁，存在旧执行时拒绝升级。
- 建表和版本推进在同一事务中提交；中断回滚，重新启动可以重试。
- 保留任务、游标、幂等键、凭据、计划、固定输入及已完成的位置迁移。
- 保留历史迁移，后续补充结构使用新版本；[生命周期决定](../decisions/0047-lake-runtime-and-location-recovery.md)与运行环境说明同步更新。

## 验证

新增 8 项迁移回归，覆盖 v5/v6 缺表、完整旧版本保留顺序、重复打开、运行器/执行锁、中断回滚和并发升级。修复前，v6 缺表用例实际复现同一 SQL 错误；修复后 8 项通过。

从真实控制库只读备份建立隔离副本，迁移后逐表核对 17 张原有表的完整行摘要一致，调度查询成功且无待执行任务，数据库完整性检查通过。只复制控制库，没有复制三湖索引或媒体数据。

集成测试增加真实引擎重启路径：构造 v6 缺表状态，验证内置 worker 自动升级、调度心跳继续推进，并保留凭据、三湖登记、三个固定输入和已完成迁移。

- `pnpm check` 通过，包括类型、边界、契约、Rust 检查/测试和 **207 项 Python 测试**。
- `pnpm test:integration` 的 **26 个脚本全部通过**；新增的缺表引擎重启用例确认了持续心跳与原数据保留。
- 修改的 Python 文件通过 Ruff，4 份 Markdown 的相对链接检查通过。
- 本机发布构建完成后，正常停止旧引擎并启动新引擎；使用原解释器和原状态目录自动迁移至 v7。实际库的 17 张原有表与备份逐表摘要一致，完整性检查通过，原有 3 个完成、2 个带排除完成、1 个暂停任务的状态均保持。
