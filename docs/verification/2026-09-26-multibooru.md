# 2026-09-26：多站点数据湖接入验收

实现见 [ADR 0035](../decisions/0035-source-registry-and-dispatch.md)。本轮没有向用户现有项目登记来源；用户将在新项目中自行添加。

后续根据实际使用反馈补齐了继续添加入口、多湖查询编辑和工作集来源解析，见[补充验收](2026-09-26-multibooru-followup.md)。以下为初次接入的验证边界。

## 工程与集成

- `pnpm check` 通过：类型、模块边界、生成契约、Rust 格式、全目标 Clippy、217 个 Rust 测试及客户端基础/媒体测试。
- `pnpm test:integration` 全部 23 个入口通过，包括既有查询缓存、排名、项目生命周期、LLM mock、美学执行/恢复/采样与新增三站点集成。
- 新增集成覆盖注册/预检、错误类型和路径、字段能力、分页、特殊标签、原始 JSON/schema、存储尺寸、缺图、同图多帖、跨湖身份、工具限制及重启。
- Edge 无头浏览器通过 5 组 UI 检查：自动识别并加入新项目、站点名称、元数据/尺寸/标签、完整标签进入查询草稿，以及等待查询完成后的唯一结果。截图已检查。

模拟测试没有调用商业模型。浏览器验收不替代原生文件夹选择器或剪贴板验收。

## 正式湖的有界验证

使用独立临时 registry、项目和应用缓存读取正式湖。正式湖及 F 盘源索引的标识文件、大小和纳秒级修改时间前后保持一致。

| 检查         | 结果                                             |
| ------------ | ------------------------------------------------ |
| 元数据       | Yandere 3 条、Gelbooru 52 条，共 55 条           |
| 原始数据     | 标签逐项一致，原始 JSON SHA-256 与只读基准一致   |
| Schema       | 每条 schema 的 SHA-256 与保存的 schema_id 一致   |
| 特殊标签     | Gelbooru 49 条记录按完整原始标签精确命中预期图片 |
| 媒体         | 每湖 3 张，共 6 张读取校验及预览生成通过         |
| 媒体 I/O     | 2,259,340 字节、6 次包打开，没有扫描图片全湖     |
| 工作集和分页 | 样本保存为固定工作集，来源排序两页无重复         |
| 重启         | 来源登记及派生索引复用通过                       |

以下使用空的 **Studio 应用缓存**，没有清空操作系统/设备缓存。

| 来源     | 首次身份索引及元数据读取 | 首次排序索引及首屏 | 重启后元数据 |
| -------- | -----------------------: | -----------------: | -----------: |
| Yandere  |                 16.76 秒 |           13.59 秒 |     0.118 秒 |
| Gelbooru |                 54.67 秒 |           43.82 秒 |     0.301 秒 |

两湖共生成 4 个身份/排序索引文件，1,492,762,624 字节，约 1.39 GiB；其中 Yandere 为 345,341,952 字节。49 次精确标签查询限定在固定样本工作集中，单次约 0.30–0.52 秒，不能作为全湖任意组合查询的耗时承诺。

## 使用与证据边界

填写正式索引及图片目录，检查后加入项目。首次需要身份/排序信息时会显示准备状态，后续按来源版本复用；这些开销不涉及再次转换或复制图片。

Yandere 无图记录继续保存在湖内，不生成空白图片卡片。无图帖子独立浏览、API 补全与每日更新仍是后续功能，Danbooru 元数据排名保留来源要求。

完整日志、集成摘要、截图、真实样本输入/结果及清理清单位于 `.local/reports/multibooru-implementation-20260926/`，不随仓库分发。本次是上述样本和操作的验收，不是重新执行全湖完整性审计。
