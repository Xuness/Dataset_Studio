# Pinterest 长期归档容器验收

实施跨 2026-10-10 / 2026-10-11。范围是 Pinterest 的最终物理组织，设计见 [ADR 0074](../decisions/0074-pinterest-archive-containers.md)。未重新抓取 Pinterest，未转换 Danbooru、Yandere 或 Gelbooru 的现有文件。

## 实际结果

统计旧 `segments` 下的全部数据文件，对比转换后的容器；不含根目录的固定 SQLite/能力文件、在线索引、缓存、日志或备份。逻辑批次、元数据、回执和媒体均保留。

| 样本 | 图片 / 逻辑批次 | 旧数据文件 | 新容器 | 旧批次目录剩余 |
| --- | ---: | ---: | ---: | ---: |
| 1,000 Pin 图版，25 条/页、抽样 3 条 | 1,000 / 50 | 731 | 1，11,926,016 字节 | 0 |
| 外接容量盘，1,000 张 512 KiB 原始媒体 | 1,000 / 34 | 230 | 1，531,295,232 字节 | 0 |

前两项使用此前正式 Runner 离线夹具的独立复制品。每个旧文件的路径、长度和 SHA-256 在转换前后聚合比较一致；元数据和回执文件也包括在内。两项均通过媒体深验证、原始响应校验、独立重建及全部逻辑事实摘要比较。TAR 头部和填充会增加少量文件字节；没有将“减少物理文件”描述为压缩所有数据。

## 外接盘和有界内存

媒体根位于 E: 的 Lenovo Y700 USB 卷，索引和重建根位于 F: NVMe SSD。Windows 对该 USB 卷的介质类型报告为 Unspecified；本记录不据此声称已确认其内部 HDD/SSD 型号。

500 MiB 媒体样本的容器合并耗时 26.77 秒。Python 分配峰值为 8,708,738 字节（8.31 MiB），以 0.1 秒间隔采样的进程工作集峰值为 59,301,888 字节（56.55 MiB），私有内存峰值为 76,636,160 字节（73.09 MiB）。这些是该样本的观测值；实现的边界来自 1 MiB 复制块、最多 1,024 个逻辑批次及原有的元数据字节/行数限制，不按整个容器大小分配内存。

该计时包含测量开销且受系统文件缓存影响；不是冷盘持续吞吐、设备扇区写入量或真实网络下载性能。未做 4 GiB 单容器断电试验、百万图落盘或多日硬件压力测试。

## 三湖密度与百万图估算

2026-10-10 的三湖只读 journal 快照如下。对象数按归档对象行统计，可能包含历史语义，与当前可见帖子数不同。它们提供文件密度参照，不能直接作为相同图片大小、相同采集历史的性能对比。

| 湖 | 归档对象行 | 归档文件（含清单） | 每百万对象行文件数 |
| --- | ---: | ---: | ---: |
| Danbooru | 11,657,522 | 146,517 | 约 12,568 |
| Yandere | 1,157,019 | 11,199 | 约 9,679 |
| Gelbooru | 4,134,978 | 377,167 | 约 91,214 |

将实际 1,000 Pin 图版的 50 个批次结构重复 1,000 次，按 4 GiB / 4,096 文件 / 1,024 批次阈值计算，得到以下策略外推。它假设首次入湖、一 Pin 一张唯一原图、后台维护跟得上采集、旧文件没有被长期占用；不包括后续反复刷新、维护积压、复制时临时双份数据及缓存/索引/备份。

| 假设平均原图大小 | 合并前文件 | 已完成容器 | 尚未封装尾部文件 | 长期数据文件合计 |
| --- | ---: | ---: | ---: | ---: |
| 约 305 KiB | 731,000 | 178 | 1,644 | 1,822 |
| 1 MiB | 731,000 | 246 | 2,647 | 2,893 |
| 2 MiB | 731,000 | 493 | 1,168 | 1,661 |

约 305 KiB 来自现有 204 张图的小样本均值，不代表未来全集。这个算术模型说明设计有望低于“百万图几万文件”的目标；分界会随真实图片、批次组成和维护时机改变，以上数值不是百万图实跑结果或无条件上限。更大的图片主要增加容器数；尾部在显式 `--force --drain` 后可以进一步合并。

## 故障、兼容与读取

验证覆盖计划提交、复制中断、改名、校验、映射切换、旧文件回收各边界；其中四个边界使用真实进程强制终止。恢复不产生新的来源请求，旧文件逐步回收期间仍可读取全部已接受数据。文件被占用时保留并重试；路径重定向、非法对象范围、容器损坏或空间不足时阻止相应推进。旧单回执归档可以合并后继续接受新回执组批。

固定 generation、水位、发布摘要、对象位置、原始字节和回执均不改写。保留的 SQLite 读快照和查询结果继续可用；原生媒体读取验证了映射切换竞争、容器边界、路径限制以及按物理位置排序的批量读取。深验证另外核对外层容器头、尾和整体哈希。

合计 192 个不同 Python 用例通过，其中 26 个是本次容器专项；没有未解决失败或跳过。范围包含 Pinterest 的采集/分页/预算/恢复、共享媒体湖、独立归档重建及调度回归。来源 crate 的 49 个 Rust 测试通过。Pinterest HTTP/SDK 的 7 组集成检查通过，包含转换后固定元数据、已有查询结果与原图读取。Python Ruff、修改文件 ESLint/rustfmt 和 Git 空白检查通过。没有运行整仓全部测试或额外原生 UI 场景，也没有公共 DTO 结构变化。

## 现有 Pinterest 湖转换

归档位于 `E:\AI\AI_Dataset\Data Lake Archiving\Pinterest`，索引位于 `F:\Dataset\Data Lake Index\Pinterest`。转换前已深验证并从旧文件独立重建；转换按持久化计划执行，校验新容器、切换映射、核对全部引用和 5 条相关租约后，回收 2,076 个文件及空批次目录。

当前桌面引擎的健康、状态和任务接口返回 HTTP 200。经现有项目附件读取四个原图并核对 SHA-256，同时读取固定 generation / 水位的元数据，均通过。首次检查脚本误把 `online-v4` 输入版本当作应返回的元数据令牌；按实际接口的 `metadata-v4` 返回格式修正断言后通过，没有修改产品的版本语义。
