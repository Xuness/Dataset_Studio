# Astra 修复 R3/R4 收尾验收

日期：2026-09-29。实施基线：da891ff（R2）。组合负载通过，最终回归与清理结果见下文。

## 已实现范围

- F6：候选解释器先握手，受控更换，失败保留原状态，Rust 健康状态和有界退避，已配置时仍可修复。
- G1：持久迁移、冻结和执行交接、同身份副本的新旧及引用完整性核对、读写登记协调、引擎重启补完；不自动移动或删除用户的正式目录。
- R4：补正发布器的 SQLite 连接关闭；增加在线锁竞争指标；核对数据权威性、版本和资源预算职责。

协议与边界见 [0047](../decisions/0047-lake-runtime-and-location-recovery.md)，历史 R1/R2 见[阶段计划](../plans/astra-review-remediation-2026-09-29.md)。

## 组合负载镜像

用只读 SQLite Backup API 创建三湖在线投影副本，之后只写隔离镜像。该 API 支持在线一致性复制，避免把正在使用的主数据库文件当作完整快照直接复制。[SQLite 官方说明](https://www.sqlite.org/backup.html)

| 湖 | 对象数 | 观察数 | 索引字节 |
| --- | ---: | ---: | ---: |
| Danbooru | 11,599,603 | 13,510,479 | 82,669,940,736 |
| Yandere | 1,156,598 | 1,252,308 | 4,445,061,120 |
| Gelbooru | 3,929,983 | 4,028,308 | 17,301,344,256 |
| 合计 | 16,686,184 | 18,791,095 | 104,416,346,112 |

另复制 3 个媒体包，合计 12,705,669,120 字节，评审从中选择 192 个真实对象。只有选中的媒体包随完整索引复制，镜像不是正式湖的完整备份。更新使用隔离的模拟站点和图片响应，评审使用本机模拟回执，没有正式抓取或付费调用。OS 缓存不人为清空，复制过程会预热部分缓存，不把结果描述为冷盘 SLO。

本机为 Windows 10.0.26200、Ryzen 9 9950X（32 逻辑 CPU）、约 93.6 GiB 可见内存。镜像位于 D: 的 Predator GM7 4 TB NVMe，引擎使用 debug 构建；媒体副本也位于该 SSD，不能据此估算正式 HDD 的冷读延迟。完整索引保留真实规模，固定结果负载为 4,095 项明确工作集上 10 次数值筛选构建，评审使用 192 项、2 次曝光、并发 2；三湖各更新 400 条，保留流水线配置和有界缓冲。

### 结果

| 指标 | 单项基线 | 组合负载 |
| --- | ---: | ---: |
| 前台 HTTP 请求数 | 1,142 | 3,594 |
| 延迟 p50 / p95 / p99 | 48.0 / 79.6 / 98.6 ms | 43.8 / 86.9 / 105.1 ms |
| 最大请求延迟 / 错误数 | 119.7 ms / 0 | 141.2 ms / 0 |
| 10 次固定结果构建总时间 | 6.41 s | 8.03 s |
| 评审流程 / 接受回执 | 50.60 s / 26 | 50.53 s / 26 |
| 三湖更新合计 1,200 条 | 382.45 s，全部完成 | 379.70 s，全部完成 |
| 最老 queued 任务等待，采样最大值 | 69 ms | 86 ms |
| 控制写事务取得时间 p95 / max | 3.58 / 623.95 ms | 3.16 / 386.88 ms |

HTTP 延迟不包含 UI 渲染。采样间隔约 500 ms，事务时间包含调度开销，不是纯锁等待。6 个采样点同时观察到三个更新任务 running、Index 读取、NativeQuery 构建以及 Media/Decode 活动；不是把分别运行的结果当作组合验收。

Index 活动数达到默认上限 4，内部记录最大排队等待 51 ms，预留峰值 128 MiB；最终 active、queued、reserved 全部归零，started/completed 均为 4,786。引擎观测峰值约 124.4 MiB 驻留、106.2 MiB 私有内存；Python 更新进程的私有内存峰值分别约 869/811 MiB，驻留约 32 MiB，受 Windows 后台进程内存策略影响。

两轮更新暂存实际峰值约 75/70 KiB、预留峰值约 124/116 MiB；结束后实际及预留字节均为 0。模拟图片很小，这不是大图编码内存上限的压力测试。采样中归档与在线可见进度最大相差 1 个提交。新 SQLite 诊断累计 busy_errors、protocol_errors、lease_retries 均为 0，最大租约写入耗时 63 ms；这表示没有返回这些错误，不表示所有底层锁等待均为零。

### 验收中新发现并处理的路径问题

旧二进制在同一副本的两轮并发浏览中均出现 4 次 SQLITE_PROTOCOL，单次约 10.8 秒；租约重试计数为 0，说明问题发生在读取连接。检查实际捆绑的 SQLite 3.53.2 Windows VFS，并对本地扩展路径作安全简化后，独立对照 678 次请求无错误，最终负载 4,736 次请求无错误。没有增加许可、延长超时或把失败改成成功。

另加入真实连接的并发快照/租约回归：两种等价根路径、4 线程各 40 轮保持冻结读取，并验证结束后数据库文件可在 Windows 重命名。特殊超长路径、保留名称、真实 UNC 路径仍按原路径处理，不在本机普通路径的通过范围内。

### 已测边界及账本决定

全湖 `post.id <= 200000` 的未限定范围构建在一次观测时仍为 running、processed=42,294，随后主动取消，取消命令在 24 ms 返回 cancelled。此数值不是全湖完成吞吐；正式组合验收改用明确的 4,095 项工作集，不声称已经证明千万级全湖筛选的完成时间或优化了这条长扫描。

Resources._actual() 在真实更新中的扫描 p95 约 90 ms；隔离样本 100/1,000/10,000 文件的 p95 分别约 10.6/64.8/844.6 ms。万级保留暂存会显著增加扫描成本，暂停和待复核文件仍需保留，取消清理不能替代这些状态的策略。本轮决定保留精确扫描计费，不引入新的持久字节账本及跨进程对账协议：当前组合负载保持进展，配额归零得到验证；增量计费可以作为后续性能工作，但不能因此弱化取消回收的所有权和配额断言。
