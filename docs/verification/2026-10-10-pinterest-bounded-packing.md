# Pinterest 有界物理组批验收

日期：2026-10-10。范围：不可变逻辑结果、物理组批、控制回放、资源预留、兼容读取及待归档进度。实现边界见[组批方案](../plans/Dataset%20Scraping/pinterest-bounded-packing-plan.md)。本次不重打包既有归档，也没有向 Pinterest 发起真实请求。

## 结果

原来每个任务写一个物理批次；现在同一作业的独立结果可合并为一个包，每个任务仍有独立回执、claim、冻结输入和证据。最多 64 回执、8,000 行、24 MiB 元数据、128 MiB 媒体目标；120 秒窗口在请求/结果边界检查，在途传输不强制中断。合法超软目标单项可以单独提交，不能绕过硬资源限制。

相同构造的正式 Runner 测试：100 个指定 Pin、100 张不同字节的 8×6 PNG，均只发出 100 次模拟 API 请求和 100 次模拟图片请求。

| 指标 | 改动前 | 改动后 |
| --- | ---: | ---: |
| segment 目录 | 201 | 5 |
| 普通文件 | 1,403 | 31 |
| TAR | 100 | 2 |
| 改动后的 Parquet | — | 18 |
| segment 文件字节 | 5,708,445 | 746,689 |
| 对象 / 原始响应 | 100 / 100 | 100 / 100 |

两侧均完成媒体深验证、原始响应字节往返、独立重建及固定水位比较。归档和在线水位现在按物理包推进，逻辑进度仍按回执统计。

## 故障、兼容与共享资源

- Python 回归合计 **212 个不同用例通过**，包含 29 个新组批用例，以及 Pinterest 原有行为、共享暂存流水线、控制升级、其他采集恢复和生产者退役相关用例。首次综合运行的像素错误分类失败已经定点修复并复测；最终按用例身份合并报告无未解决失败。没有运行整仓库全部测试。
- 注册、冻结、TAR 写入、seal、rename、journal 接受、发布、控制回放和清理均有故障注入。冻结、写 TAR、接受、清理另有四项真实进程强制终止测试；恢复后四个 Pin 的八次物理请求没有重复。
- 回放分页读取物理 sequence，同包成员在同一控制事务中完成。140 个逻辑结果的回放中，在第 120 个成员注入失败，当前包全部回滚；重试后 140 个任务及 141 个回执（含意图）齐全。
- 验证跨时间片、暂停/取消、120 秒到期提交、pending 准入预算、采样配额和屏障、同 URL 多绑定、同字节对象去重、软行数/字节切批、合法超媒体目标单项、低暂存压力提前封包、额度下调与重启预留恢复。
- 旧 prepared 仍以单回执批次处理；新旧归档混排后旧 segment 文件哈希和在线 generation/pointer 不变。归档格式 3 新增必需能力 `receipt-bundles-v1`；在线格式 4 保持原能力集合。Rust 同时验证旧/新归档能力接受、未知能力拒绝与在线检查隔离。
- 共享模块会修改 Pillow 的全局像素阈值。Pinterest 现在在尺寸比较和解码前检查自身配置的实际像素上限；单项超限仍形成明确缺口，后续 Pin 可继续。

Rust 格式兼容单测、前端类型检查、修改文件 ESLint、Python Ruff、修改文件 rustfmt 均通过。Pinterest HTTP/SDK 集成六组检查通过，包含独立来源识别、固定版本读取、原始媒体、命令/分页/计划以及引擎重启。无公共 DTO 结构变化。全仓 rustfmt 另发现美学模块既有格式差异，本次仅验证并保留本次修改文件的格式。

## 现有控制库

开发运行器自动部署后，真实控制库从 v21 升至 v22，并生成升级前 SQLite 备份。升级前后的 20 张既有 Pinterest 表按全部旧列逐行计算摘要，全部一致；新增 outbox/batch 表为空。已有作业仍为 `completed_with_gaps`、revision 3、API 35 次、下载字节 70,420,757、archive/served sequence 486。

归档根能力文件和在线 pointer 哈希不变，已有归档没有自动转换。健康、Pinterest 状态和已有任务查询均返回 HTTP 200，新 pending 计数为零。本次没有恢复真实采集任务。
