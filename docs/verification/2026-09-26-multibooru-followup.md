# 2026-09-26：多数据湖交互与查询缓存补齐

用户在新项目添加 Danbooru 后发现继续添加入口消失。本轮以 `a60c777` 为基线，检查添加、查询编辑、范围解析、缓存复用、浏览身份及工具来源要求。前一次界面验收只覆盖首个来源的加入，未覆盖已有来源后继续添加的流程。

## 已修复

| 问题 | 改动与行为 |
| --- | --- |
| 添加按钮只在来源列表为空时显示 | 数据湖标题旁保留“＋”；顶部“项目 → 添加数据湖…”在打开项目后可用，隐藏项目面板也能添加 |
| 查询面板只能选择一个湖，已保存的多湖查询只读 | 支持勾选 1–8 个湖、编辑、保存、执行及恢复；查询历史显示具体来源 |
| 单湖字段目录不能表达站点差异 | SDK 合并各来源共同支持的字段类型、单位、操作、排序和观察规则；字段缓存键包含来源修订及语义版本 |
| 切换来源可能错误使用独有字段 | 保留已输入条件并标明不可用，阻止执行；不会默默删除条件而扩大查询范围 |
| 工作集筛选把项目全部来源带入查询 | 按固定范围或选择的实际成员解析来源，避免无关湖的离线、字段差异或更新干扰查询与缓存 |
| 新增来源后，旧“全部项目数据”筛选结果容易被误认为已更新 | 保留固定结果并提示重新应用；不把旧成员自动解释为新来源范围 |
| 分级缓存入口按原始元数据能力推断，错误文案限定 Danbooru | 与引擎现有来源索引能力判断保持一致，并使用中性文案 |

`core.query` 草稿改用 `sourceIds` 数组，兼容旧单湖 `sourceId` 和此前只读的多湖定义。已有查询定义、项目资产身份和缓存持久化格式不改变。`source-requirements` 接受空投影列表，用于只解析实际来源；仍使用项目索引的有界来源探测，不枚举全湖图片。

## 缓存与身份检查

- 查询成员及工作集以 `(source_id, asset_id)` 为身份，同 SHA 或同帖子编号在不同湖中保留为不同成员。
- 查询缓存指纹包含规范化来源集合、条件、观察规则和输入范围；复用还核对来源版本。交换来源选择顺序可复用，单湖与组合查询不会混用。
- 分级基础缓存、身份索引和帖子排序索引按来源保存；清理一个湖的分级缓存不影响另一个。
- 媒体客户端缓存键包含项目与来源身份；服务端共享预览命中前仍验证项目来源关系和媒体身份。
- Danbooru 专属排名继续按实际输入范围验证投影；通用查询没有改为放宽这些专属工具的来源要求。

## 使用

当前开发版前端会热更新；本轮也改了引擎的范围解析，因此完成正在进行的工作后，关闭并重新运行根目录的 `启动开发版.bat`。在原测试项目内使用数据湖标题旁“＋”或“项目 → 添加数据湖…”，无需重建项目或重新添加已有 Danbooru。
