## 合成规模测试

入口为 `tooling/benchmark-pixiv-archive.py --output '<new child of .local/test-runs>' --works 10000 100000`，使用项目 Python 环境。

它调用生产归档 writer、publisher 和独立重建/比较流程，每个单页作品包含详情、清单、原图三份逻辑回执，按当前 64 回执界限打包。所有 occurrence 共用一个小型 PNG，明确测量元数据与文件数量放大，不模拟网络限速、解码负载、整个控制调度器或大媒体吞吐。没有测量的控制库锁等待和下载暂存峰值以 null 表示。

| 指标                                   | 10,000 作品 | 100,000 作品 |
| -------------------------------------- | ----------: | -----------: |
| 逻辑回执（含意图）                     |      30,001 |      300,001 |
| 物理归档批次（含意图）                 |         478 |        4,763 |
| 归档批次文件数（不含意图）             |       5,726 |       57,146 |
| 归档批次文件字节（不含意图、在线库）   |   24.39 MiB |   243.50 MiB |
| 组装、写入与同步发布                   |   115.99 秒 |  1,372.59 秒 |
| 其中归档 writer                        |    53.63 秒 |    621.63 秒 |
| 其中同步发布                           |    55.74 秒 |    674.99 秒 |
| 单次同步发布耗时最大值                 |    0.203 秒 |     0.428 秒 |

| 规范表完全相等、raw 往返及归档深度校验 |        PASS |         PASS |

两档分别验证 20,000 和 200,000 个 capture。每档只有一个去重后的 79 字节 PNG，因此批次暂存峰值不能推导为真实图片下载的资源需求。耗时是本机本轮墙钟观测，期间有少量其他本地检查；未运行旧实现的性能对照。归档深度校验另外执行，不包含在“重建校验及逐表比较”的时间中。

## 正式数据与边界

修改前读到 6 个已完成 Pixiv 任务，没有活动采集。随后对正式 Pixiv 在线库只读检查：720 个当前作品，详情与清单依据不同的数量为 0，当前非 ready 数量为 0。没有触发新的正式源站下载。

开发运行器在空闲时通过现有热更新机制迁移到了控制 v11。之后保存了当前控制库快照并验证 SQLite 完整性和外键；该快照不是 v10 回滚副本。它包含加密账号状态，只保存在 `.local/backups/pixiv-review-20261003-control-snapshot/`，不提交、不随验收材料分发。

本机日志位于 `.local/logs/pixiv-review/`，长期验证证据位于 `.local/reports/pixiv-review-20261003/`；均不随仓库分发。已归档报告、日志、截图等 2,426 项证据，ZIP 为 2.27 MiB，通过 CRC 和 SHA-256 校验。按明确所有权及逐文件清单，清理本轮 99 个临时目录、131,756 个文件，逻辑大小约 11.78 GiB；目录与文件清单、归档哈希和清理回执均保存在上述证据目录。清理后 `.local/test-runs/` 仅保留 4 个既有共享目录。

本次没有验证真实源站在长期压力下的吞吐、账号续期周期或风控行为。归档接受继续依赖可用的 serving 校验库。训练样本选择视图和权威 catalog 的进一步拆分未实施，边界见 0055。
