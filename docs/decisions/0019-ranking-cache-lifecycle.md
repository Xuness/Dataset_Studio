# 排名范围复用与可恢复缓存清理

2026-09-13，开发版本 0.9.1。补充 0017 的固定范围索引设计。

真实项目中，查询层复用了同一个 family/member_revision，却为每次执行保留新 result_id。排名索引此前直接用 result_id 作为范围身份，因此相同的 G 成员被重复构建为四份约 951 MiB 的文件。之前的重启测试只重用了原来的结果 ID，没有覆盖再次应用相同筛选的路径。

## 排名成员与查看身份

存储层为查询的同一 family/member_revision 选择稳定的原始结果作为 canonical scope；后续 reused 别名不会改变该身份。不同成员版本分别生成索引，即使成员数量相同。工作集沿用自己的固定身份。排名索引键仍包括成果格式、工作集、成果文件身份、保存条件和成员数，所以 V1/V2、不同成果与不同成员范围不会混用。

构建读取 canonical scope 的固定成员投影，完成前检查发起请求的范围仍然有效。缓存文件的完成元数据、租约、构建状态与分页签名使用相同的 canonical scope。用户可见的查询 ID 与历史记录仍分别保留。已经释放原始结果的单个别名不会改变其他就绪别名的成员身份；清理成员时仍以整个成员版本的活跃视图及项目引用为准。

若旧键文件与当前成果和 canonical scope 可通过有限元数据查询证明等价，可以重绑定缓存完成元数据并重命名文件，无需复制成员或重新建立排序索引。读取中的文件不会被重绑定。只有应用拥有的派生缓存会被修改，原输入与评分文件不变。

读取固定排名页不再检查数据湖的最新版本。范围归属、固定成员就绪、成果有效、索引格式和游标归属检查仍保留；实时来源浏览、刷新与依赖当前来源的工具入口继续执行原来的来源检查。

查看设置使用独立的 view_key：工作集、成果、保存条件与规范化查询条件决定查看身份，不依赖某次执行的 result_id。前端最多保存 32 组查看设置，支持切换后恢复方向和排序。旧设置可通过原查询的排名信息迁移。来源范围变化时清除旧解析游标，避免把不同成员版本的位置直接复用。

## 清理请求与成员回收

查询成员是共享 SQLite 数据库中的行和索引，不是每份查询独立拥有的几个文件。原清理请求在一个同步事务里删除整组成员，前端等待响应期间仅显示禁用按钮；容量统计也可能再次访问大量数据库页。

手动清理现在先执行短事务：检查整个 family 的使用者、固定状态和项目引用，释放可清理结果，提交清理任务，然后立即返回。后台一次最多检查 16,384 条成员，通过固定范围游标继续；不从表头反复扫描已处理的前缀。任务进度与批次删除在同一个事务中提交。失败时保留最后成功的进度并显示错误，用户可以重试。

任务状态保存在现有 meta 表的 query_cleanup 前缀下，不需要项目数据库升级或复制项目数据库。queued、deleting、accounting、completed、failed 分别表达排队、成员删除、空间统计、完成和失败。保留最近 32 条结束记录。引用变化或成员版本变化会产生新的清理计划；同一个未变化的保留计划不会无休止地重新清理。

每个批次重新检查当前活跃和持久化引用，保护需要保留的成员版本。当前版本必须保留时使用过期成员索引跳过仍有效的巨大前缀。总量受限的后台维护入口负责继续调度，不把完整大组删除放回 HTTP 请求路径。

## 容量与磁盘空间

容量快照与存储修订一同持久化。仅删除的中间批次沿用保守的容量估计，全部成员批次结束后再刷新统计，避免每个批次重复访问整个成员存储。统计读取位于项目写锁与缓存租约锁之外；写入后的修订复核避免把旧快照当作新统计。

缓存列表通过只读连接读取成员及任务状态，不等待全库容量统计；尚无估计时显示“正在统计”。活跃状态按整个 family 汇总，防止当前查看的是别名时误把原结果的清理按钮显示为可用。

删除后数据库空闲页可以先供项目复用，磁盘文件缩小由增量空间回收继续执行。一次回收后仍有较多空闲页时继续安排后续批次，不再只依赖 30 秒一次的维护周期。设置页区分可复用空间与已归还磁盘的空间，并显示当前阶段。

`PRAGMA incremental_vacuum(N)` 会逐步返回结果行。当前 rusqlite 的 execute_batch 对每条语句只调用一次 step，因此原来的 incremental_vacuum(8192) 实际只推进一个页。现改为读取完该 PRAGMA 的有界结果，真正完成指定批次的页回收；单元测试独立检查一次请求确实减少 128 个空闲页，关闭项目后的集成测试要求最终收尾结束。

关闭项目后，持久化缓存目录仍记录待完成任务，后台可按原有项目文件锁机制继续处理。引擎重启后从已提交批次恢复；已关闭项目的空间统计也会持久化，避免每次短维护都重新扫描。正常项目打开/关闭历史不被维护环境改变。

## 验证要求

- V1/V2 × G/E：相同查询生成多个新 result_id，只保留一份对应排名索引，排序方向和页大小变化不触发准备。
- 项目重开和引擎重启后，再次执行相同筛选仍复用文件。
- 同数量、不同成员版本不得复用；保留旧版本引用时旧榜仍可读取。
- 来源版本变化后固定排名仍可阅读；原实时来源要求不降低。
- 清理请求必须先于完整删除返回；批次进度可见，读取排名不等待全组删除，重启后继续完成。
- 原项目成员引用与评分材料保持不变；完整检查、集成用例及真实 React 页面共同验证。
