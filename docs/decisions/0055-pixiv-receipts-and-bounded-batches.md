# 0055：Pixiv 结果隔离、稳定下载暂存与有界组批

日期：2026-10-03。继承 [0052](0052-pixiv-collections-and-canonical-media.md) 与 [0053](0053-pixiv-public-operation-and-incremental-refresh.md)。归档格式仍为 2，在线格式仍为 3，公开采集契约仍为 2；控制库升级到 11。实施与验证结果见[审查修复验收](../verification/2026-10-03-pixiv-review-upgrade.md)。

## 结果可以保存、接受和隔离的边界

采集结果在写入 prepared 前检查字段类型、记录数量、Arrow 元数据字节数、身份和本次结果内的媒体关系。归一化成功但形状不合法，也走 raw-only 路径：保留有界原始响应、capture 引用和错误类别，任务进入 `needs_review`。原始 JSON 没有因为规范化失败而丢失。

不完整清单是合法事实。空帧 Ugoira 可以保存 `complete=false / reason=empty_frames` 的清单及已观察到的媒体条目；只有完整动画清单才要求非空帧序列。已有帧必须连续且文件名唯一。Planner 仅从完整清单创建下载任务，旧的完整媒体仍可浏览。

prepared 回执本身不可修改。无法接受的旧结果通过 `quarantined` 状态明确隔离：原目录移到 `collection-quarantine/<job>/<receipt>`，保存原始 result 文件、预期哈希、实测哈希、文件清单和失败类别。缺失 result 时记录缺失事实，不伪造原文；哈希不符时同时保留两种哈希。移动中断可从持久化隔离说明恢复。被拒绝的未接受物理批次进入归档根下的 `quarantine/`，不会再次参与普通恢复扫描。

隔离不冒充归档成功：`control_applied` 和 `published` 仍为 0。对应任务可以复核和重试，成功的后续回执与隔离记录建立替代关系。取消清理跳过隔离证据，回收该作业的可删除 scratch；证据继续保留。已被 journal 接受的结果始终先按归档回放，不能再当成未提交 scratch 隔离。

目录所有权不明、执行 epoch 不符、归档损坏和在线库不可用不属于可自动隔离的来源结果。它们保持明确的完整性或读写错误，不通过跳过检查继续接受归档。

## 下载失败与一份活动断点

每个逻辑媒体任务使用 `collection-downloads/<job>/<task>` 保存 `.partial`、`.downloaded` 及下载回执。claim 目录只存本次执行的结果和待归档表示。领取任务的数据库事务只更新控制状态；建目录、接管旧断点、校验和图片处理均在事务之外执行。

同一作业的执行锁覆盖全部下载 future，返回锁前等待线程退出。稳定暂存记录固定输入指纹与下载 generation。恢复、资源等待和有限网络重试保留 generation；显式 `retry_failed` 增加 generation，下一次准入后清除旧下载，确实重新访问来源。旧版本 claim 内的断点在获得资源预留后以同卷移动接管，不复制可变文件，也不使用硬链接共享 partial。

图片识别、解码和 ZIP 内容错误是 `COLLECTION_MEDIA_INVALID`，不会进入磁盘资源等待。网络故障最多自动尝试 8 次；实际空间不足才进入 `waiting_resources`。一般路径或权限错误保留为 `COLLECTION_IO` 待检查。下载内容与冻结尺寸或帧表不同继续报告 `COLLECTION_SOURCE_CHANGED`，通过新建快照重新获取详情和清单。

不可接受的图片保存下载哈希、大小和 generation 作为任务诊断；失败结果接受并发布后回收坏文件，不无限保留其副本。成功或取消也回收稳定暂存。没有回执消费者的失败 attempt 及时删除，无需等整个作业结束。资源统计同时覆盖稳定下载目录和 attempt 输出。

## 逐回执身份与物理组批

新 prepared 文件版本为 2，不预先绑定一个物理批次。每个回执仍有自己的 receipt ID、task ID、claim token、执行 epoch、固定输入指纹和结果哈希。旧版 v1 prepared 继续单独接受并保留其原始 batch ID；旧归档无需重写。

`collections/batches.py` 在同一作业内组批，当前界限如下：

| 界限           | 当前值                                         |
| -------------- | ---------------------------------------------- |
| 单批回执       | 最多 64                                        |
| 分组记录预算   | 90,000 行，给最终资产和对象留出余量            |
| 分组元数据预算 | 48 MiB                                         |
| 分组媒体字节   | 128 MiB                                        |
| 等待时间       | 1 秒后可提交；空闲、运行片退出和恢复时强制提交 |

单个合法大回执可以独占一批，仍受既有 100,000 行、64 MiB 规范元数据预算以及共享下载限制约束。意图回执、旧 v1 回执单独成批；相同 checkpoint stream 不进入同一批，保持 compare-and-swap 次序。

组装器先在短事务里冻结 `collection_batches` 成员列表和 outbox 的批次映射，再写物理文件。中断之后复用这份映射；seal、rename、journal 接受、控制回放、发布和 scratch 释放均可重复恢复。新 replay 的每个 task outcome 带 receipt ID，因此同一批里的新下载和历史复用仍分别计数。发布按逻辑回执确认，只有成功媒体结果增加发布计数，失败回执不会因后来任务成功而被再次计入。

旧 v10 控制库中尚未确认发布的回执，首次确认前从归档补回各自的 outcome。补回过程校验归档 replay 的哈希，以有界分页读取证据，再用短事务保存结果；不从任务后来的状态推测旧回执是否成功。发布已完成、控制确认丢失的情况仍可重复恢复，历史失败回执不会计作成功媒体。

模块职责现在是：`tasks.py` 管理领取与下载暂存，`failures.py` 定义错误分类，`validation.py` 做前置校验，`batches.py` 冻结和接受物理批次，`receipts.py` 保存逻辑结果、回放、隔离和回收，Runner 协调这些边界。`PreparedReceipt` 与 `VerifiedSession` 使用明确的内部数据类型。

## 内容版本与增量判断

详情保留一个可重算的 `pixiv.content_revision`。它由来源内容修订时间、作品类型、页数、尺寸和原图定位信息等生成，排除收藏数、浏览数、标题和说明。清单已有 `detail_observation_id`，因此直接绑定当时的版本依据。

新详情与清单依据不相容时，投影返回 `needs_refresh`，仍保留旧完整清单供浏览。只有内容版本相容，才允许快照沿用。相容性规则同时用于新发布、归档重建和增量复用；统计更新不会单独使同内容失效。旧观察缺少指纹时可从原始 capture 推导，无需改写历史事实。

增量入口再次校验内容相容性，保护旧版本在线库已经保存成 `ready` 的行。旧库的既有展示投影不会在原水位原地改写；有受影响历史的库可用现有归档重建流程重新生成投影。新的观察发布后使用新规则。本次正式库检查没有发现详情与清单依据不同的当前作品。

指纹表示已观察到的来源证据，不承诺检测到同 URL、同来源标记之下未显式报告的远端字节变化；需要 HTTP 重新核验时仍选择全量刷新/重新下载策略。

## 调度和账号

周期调度在 SQL 中先排除未结束前置作业，再排序和 LIMIT 100。暂停、凭据、预算或复核阻挡某个计划时，后面的独立计划仍有机会运行。

浏览器登录保存和手动 probe 使用同一身份确认与 Cookie snapshot 流程。身份、验证时间、轮换 Cookie 和验证结果在同一 revision 条件下提交；探测期间用户导入或清除凭据仍会导致冲突，不覆盖新状态。

## 保留的约束与后续独立工作

归档确认与发布确认是分开的，但归档接受仍依赖可用的 serving SQLite、在线指针和锁，以执行真实外键及跨批次不可变性校验。这次保留这项约束。没有引入第二套权威 catalog，也没有声称在线库丢失时仍可继续接受新归档。

训练导出中 original/derived/poster 的选择、跨作品 SHA 去重以及 dataset-ready view 属于独立产品规则，这次不改变。Rust 应用端的通用 JSON 操作端口也保留；本次强化的是实际产生故障的 Python 持久化和执行边界。
