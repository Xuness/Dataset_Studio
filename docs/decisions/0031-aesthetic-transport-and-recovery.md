# 0031：评审图片传输、原始回执与项目恢复

日期：2026-09-23。承接 [R2 路线图](../plans/architecture-improvement-2026-09-19.md)与 [ADR 0027](0027-aesthetic-recovery-and-admission.md)。验证见 [本轮记录](../verification/2026-09-23-aesthetic-transport.md)。

## 图片身份与请求预算

本地图片身份与当批短 ID 分开。批次保存有序的候选映射，发送前校验实际图片 SHA-256；原生请求按 ID 文本、对应图片内容块交替编码。新阶段冻结 `aesthetic_labels_v2` 指令，明确短 ID 对应紧随其后的图片，禁止改用文件名或附件编号。旧阶段继续使用原来保存的模板，不因软件升级更换指令。

原先 12 MiB 是本地规划预算，不是远端 API 的统一限制。新创建请求增加可选 `max_request_mib`，范围 8–48，省略时默认 32。界面提供 8、12、16、24、32、48 MiB。阶段把所选值冻结为 `config.max_request_bytes`，旧阶段的 12 MiB 保留。capabilities 分别公开默认值 32 MiB 和可配置上限 48 MiB。

最终约束针对供应商编码后的完整 JSON 请求体，包含文本和 Base64 图片。通用 LLM 输入预算同步为 64 MiB，本机 LLM HTTP 路由预算为 66 MiB；两者不代表供应商端点支持相同大小。HTTP 413 单独报告请求过大，不隐式重试。

创建阶段以有界页面冻结候选，并在不调用模型的情况下检查图片读取、文件签名、格式和 SHA-256。异常图片进入待处置状态，不能静默遗漏或按低质量计分；派发前仍重新验证版本和字节。批次物理读取保留来源分组和有界 read_many，模型消息恢复固定展示顺序。

超限且从未发送的批次保存为 `superseded`，保留原成员，生成更小的替代批次；公开父批次与直接替代批次序号。每个子批次重新编码并检查实际大小。孤立尾图交回调度器寻找同 Rating 对手。任何已有 attempt 的批次禁止改成员或拆批；恢复失败不会伪装成模型调用。图片规格仍是单张最多 2 MiB 的原始 PNG/JPEG/WebP，不静默缩图。

基础预检提供可用磁盘与完整曝光所需调用次数的理论下界；Rating 分组、尾批、按字节拆分、重评会增加实际次数。创建、启动和发送承诺点检查项目卷至少留有 256 MiB 空间。这是最低运行余量，不是保证整个阶段或备份一定有足够存储。

请求准备与在途继续共享 512 MiB 的内存准入池。每批依据图片登记大小与冻结配置估算序列化副本，加上回执保留空间进行准入；不是统一按用户配置的最大请求体占满额度。估算覆盖拆批前原批次的准备。该预算是并发策略，进程总 RSS 和生产吞吐仍需 R4 验证；上传准入节奏也不是 TCP 流量整形。

## 原始回执与本地重解析

评审使用显式 ReceiptSink 路径，一次账本 attempt 对应一次 HTTP 请求，连 429 都不在传输层自动重试。拿到响应后先保存 HTTP 状态、允许保留的头、request ID、协议/适配器版本、响应体、完整性和摘要，然后才进行供应商解析与业务校验。

响应体最多保留 16 MiB。超限、连接中断、读取超时或取消时，保存已收到的前缀，`complete=false`；摘要只覆盖保留部分。`complete=true` 仅表示 HTTP 内容读取到结尾，不表示 HTTP 成功、业务 JSON 有效或模型正常结束。取消和超时终止网络读取，不取消已经收到内容的持久化。尚未收到响应头的网络失败没有可编造的原始回执。

原始 body 单独存为 BLOB，摘要随保存写入；读取时复核摘要。只保留 content-type、request ID、retry-after 等允许的响应头，不保存请求认证头。原始响应属于项目证据，不进入普通日志或一次性缓存。保存失败沿用 R1 的保留内存、关闭派发准入、重试持久化机制；全存储不可用且进程被强制结束时仍可能留下结果不明。

新增单批本地重解析 API/SDK/界面入口。它使用原始回执和冻结快照，不读取 API Key、不依赖当前供应商配置，也不发送网络请求。解析尝试单独记录；修复未接受的归一化结果时保留上一版本，校正用量投影，不重复累计。已接受 evidence 不覆盖。恢复后阶段仍保持原有暂停/待处理状态，其余批次继续执行须显式开始。

评审库升级至 v6：v5 增加原始回执、解析记录和批次替代关系，v6 增加解析版本的归一化内容。开发期间已存在的 v5 也可升级。升级前通过 SQLite Backup API 备份，迁移在事务内验证；项目库仍为 v12。历史没有原始 HTTP 回执的记录保持缺失，不能把既有归一化结果当作原始回执。

## 写入与恢复包

关键回执/状态与普通投影采用分开的有界队列，各保留 64 MiB 准入容量，每项最多 32 MiB。关键写入优先，但连续最多处理八项后给等待的普通写入一个机会。确认在 COMMIT 后发出。指标包括排队字节/条数、最老等待时间、最近写入事务耗时和关键写入占用；事务耗时包含操作和提交。

保留旧的单独账本备份 API。新增项目恢复包 API，界面“创建项目恢复包”调用新入口。首版要求项目静止：评审、在途返回、普通任务和离线分析均已暂停或结束。活跃时明确返回 PROJECT_BUSY，由用户利用现有暂停/取消入口停靠；本轮不自动更改这些任务的状态。

恢复包在持有项目写入锁及评审 writer 屏障时，通过 SQLite Backup API 保存两库，并复制 project.json、artifacts、.staging。清单记录版本、证据/复核水位、文件大小和 SHA-256，验证两库引用、冻结配置和成果摘要。文件遍历拒绝越界、符号链接及 Windows 重解析点。必要的模型/Prompt 配置引用和数据湖定位另存 dependencies.json，不带凭据引用或密钥；冻结配置仍以评审库为准。

恢复只能写入不存在的新目录，同身份项目需先关闭。逐文件校验复制结果后才发布 project.json；恢复不会注册/打开项目，更不会自动派发。之后通过原有打开项目入口使用该目录。外部数据湖不复制进包，来源身份/内容版本在原有来源检查和派发检查中验证。换机器时需要显式重新关联数据湖、配置连接与凭据；dependencies.json 供核对，不能静默覆盖应用现有配置。

这轮是 R2 的传输和恢复实现。R3 的完整排名有效性、分析读取预算和历史释放，R4 容量声明，以及 R5 真实模型审美校准仍分别验收。
