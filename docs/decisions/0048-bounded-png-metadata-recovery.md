# 0048 — 有界 PNG 元数据兼容处理

日期：2026-09-30–2026-10-01。状态：已实现。

## 问题与证据边界

Gelbooru 更新队列中 5 张原始 PNG 均通过来源 MD5 校验，其中 4 张含错误的 iCCP/eXIf/tEXt/iTXt 校验码，另 1 张的 ICC 解压后为 1,086,888 字节，超过 Pillow 12.2.0 使用的 1 MiB 元数据解压上限。直接重新下载不能解决已存在于来源文件的问题。此前更新流水线在编码准入前调用普通 `Image.open`，使保存配方中的兼容处理无法被触达。

CRC 不匹配仍表示元数据完整性没有被该 CRC 证明。本方案是一种明确记录的兼容解码，不声称恢复了作者原先想表达的元数据内容。PNG 结构和 CRC 的依据见 [PNG 第三版错误处理](https://www.w3.org/TR/png-3/#13Decoders.Errors)，Pillow 行为以固定版本的[实现](https://github.com/python-pillow/Pillow/blob/12.2.0/src/PIL/PngImagePlugin.py)为准。

## 决定

- 统一使用 Studio 自有 `png_compat` 模块。下载后的资源准入、可配置保存策略和旧保存策略采用同一 PNG 检查/解码规则。
- 只有 `iCCP`、`eXIf`、`tEXt`、`zTXt`、`iTXt` 可以在解码副本中重算 CRC。块内容不修改、不丢弃；原始完整块字节、偏移、原 CRC、计算 CRC 和动作列表写入资产处理详情。
- IHDR/PLTE/IDAT/IEND、透明度 tRNS、动画 acTL/fcTL/fdAT，以及其他未获准恢复的块仍严格校验。截断、关键结构缺失、重复头、未知关键块与 IEND 后多余数据均不自动修复。
- ICC 解压单独限制为 4 MiB。超过 Pillow 默认上限的 ICC 从解码副本中取出，经有界解压后放回该图片的 `info`，自定义策略的后续颜色处理和输出编码仍使用该配置；旧策略保留原有编码规则。原始压缩块同时保留在处理详情中。
- 单文件原始附加元数据总量上限 16 MiB，块数上限 100,000，需恢复的块数上限 128；像素与动画数据不计入附加元数据预算。编码内存和磁盘估算计入原始元数据与恢复后的 ICC。
- 不修改 `LOAD_TRUNCATED_IMAGES`、`MAX_TEXT_CHUNK` 或 `MAX_TEXT_MEMORY` 等全局变量；其他 PNG 文本块仍受 Pillow 自身解压限制。并行编码互不改变解码器设置。
- 原图策略与保留动画策略仍返回原始下载字节，兼容处理只用于解码副本和来源描述。自定义处理版本为 5，旧策略处理版本为 3；已有配方身份、数据湖格式和已发布资产不变。

普通有效 PNG 直接使用原数据，不创建修复副本。新增检查为顺序读和有界元数据解压，不需要读取正式媒体湖或重新扫描历史图片。

## 验证

覆盖原始块保留、ICC 边界、透明通道、关键块拒绝、截断/尾部数据、动画与原图字节不变、多线程隔离，以及流水线准入到归档。5 张正式异常文件在隔离缓存执行完整生产编码路径并检查输出，原始正式断点未改动。详见[验收记录](../verification/2026-09-30-png-compatibility.md)。
