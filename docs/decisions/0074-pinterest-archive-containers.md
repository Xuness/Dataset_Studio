# 0074：Pinterest 逻辑提交与长期归档容器分离

日期：2026-10-10；实施与验收于 2026-10-11 完成。

图版分页、采样和恢复屏障仍按已接受批次提交；这些批次不再各自永久占用一套小文件。长期归档把多个批次、多个作业的元数据、回执、清单和媒体包按原字节聚合到较大的容器中。

## 物理格式与版本

每个容器是未压缩的 USTAR，位置为 `containers/<UUID 前两位>/<UUID>.tar`。成员名是原来的 `segments/<batch_id>/<filename>`。Parquet、`replay.json`、`run.json`、`manifest.json` 和原媒体 TAR 都逐字节复制；不重新序列化元数据、不重新编码图片，也不把每个逻辑批次展开成新的目录。

`journal.sqlite` 的扩展表保存容器状态、大小、整体 SHA-256、成员偏移/长度/原文件 SHA-256、复制与回收进度，以及引用检查回执。原 `commits`、运行意图、任务回执、提交序号和清单内容不修改。在线索引中的 `pack_path` 与对象偏移仍表达旧逻辑文件内的位置。

归档格式仍为 3，新增必需能力 `archive-containers-v1`。先事务建扩展表，再原子更新根能力文件；旧程序必须拒绝这个新能力。旧单回执、已有回执组批和容器能力可混合读取。在线格式仍为 4，其事实模式、generation、已发布水位和固定版本令牌保持不变。

## 流式合并与调度

单次最多选择连续的 1,024 个已发布逻辑批次；4 GiB 是容器字节目标，累计 4,096 个待合并文件也会触发封装。单个合法批次可以超过软字节目标。小尾部跨分页、时间片和作业保留，等待后续批次；不会因为每个小任务完成就强制制造小容器。显式维护命令可封装最后的尾部。

媒体和元数据以 1 MiB 缓冲复制、散列和复核，不加载整个容器或所有图片。计划、成员集合和元数据读取各自有批次数/行数/字节边界。临时容器直接写在归档盘，不占用采集 SSD 暂存区；开始和恢复前要求剩余容器空间外加 128 MiB 余量。

统一运行器的独立维护通道每 30 秒轮询一个可维护的 Pinterest 湖，与既有回收通道共用一个工作槽。该湖的采集时间片和维护不会同时调度；其它湖保持原调度。维护遵守位置锁、湖写锁和设备 I/O 锁；停止在有限复制块边界响应。进度不依附于采集任务是否已完成，重启后可以继续未完成的容器。维护结果保存在控制库 `settings` 的 `pinterest_archive:<lake_id>`，活动和最近结果进入 heartbeat；错误不会改写已结束的采集任务。空间/占用问题等待 5 分钟，完整性问题等待 1 小时后再检查。

## 切换、引用与回收

1. 冻结已接受、已发布的前缀及每个原文件的哈希。拒绝非受管文件、目录或链接。
2. 写 `.part`，按有限成员组同步文件并保存复制进度。重启重写未确认的后缀；不重新请求来源。
3. 原子改名为最终容器，重新读取所有成员、头部、填充、尾部并核对整体哈希。
4. 核对原提交清单、在线发布摘要和全部受影响对象范围；记录保留租约。映射覆盖每个原逻辑文件，固定版本继续引用相同路径。
5. 在单个 journal 事务中将容器映射切换为 `active`。容器一旦激活不再重写、移动或自动回收。
6. 再次验证容器和引用，逐文件检查旧文件字节后回收，只删除空的受管批次目录。忙碌文件保留并重试；中途退出通过逐成员回执恢复。

打开的文件句柄完成当前读取；尚未打开的旧路径在删除竞争后重新查询已发布映射。Python 的有界文件视图不能越过成员范围；Rust 校验原对象范围和容器大小，并在批量媒体读取时按实际容器及偏移排序。历史固定版本与重建不需要新的物理 generation 租约，因为已发布容器映射永久保留。

切换前原文件一直可用；切换后即使旧文件逐步回收，所有旧逻辑路径仍可解析。容器保留原始文件名及字节，可作为迁回原物理布局的材料。本实现不自动回收容器、不合并已完成容器，也不删除历史事实。

## 维护入口与验收口径

使用配置好的 lake-worker Python：

```text
python -m studio_lake.pinterest.lake.compaction --media-root <Pinterest 归档目录> --index-root <Pinterest 索引目录> --force --drain
```

不传 `--force` 时，只处理达到正常阈值的前缀或未完成的操作；不传 `--drain` 时最多处理一个容器。深验证同时校验容器和原逻辑文件，归档独立重建继续逐逻辑序号发布。

文件密度以 TAR、Parquet、回执和清单的物理文件总数衡量；SQLite 中的成员行数不是文件数。与三湖比较时统一排除在线索引、缓存、日志和备份。正常归档目标是百万图几万文件以内；估算需计入少于一个触发窗口的松散尾部及受占用保护的旧文件。具体样本、内存和故障恢复证据单独保存，不能用外推代替百万图实跑。
