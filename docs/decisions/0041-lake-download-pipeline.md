# 0041：数据湖下载流水线与共享调度参数

日期：2026-09-27。承接 0038–0040，保留规范湖、在线投影、冻结任务范围与图片配方。

## 问题

单湖旧执行器交替获取最多 200 条元数据与逐张处理 8 张图片。连接在每张图片后关闭，编码全局串行，下载和编码互等；进度还会由最后一个采样覆盖其他工作。“待处理”包含异常，而“已处理”也包含异常，使两列并非互斥集合。

## 决策

1. 候选记录继续使用持久控制库。元数据线程、站点下载池、编码池分离；同湖只有一个元数据扫描工作，检查点单调推进。
2. 元数据 HTTP 与标签字典请求不持有发布协调锁。元数据/媒体的归档提交及队列重放共用短协调步骤，E 盘设备锁仍确保归档写入顺序。
3. 每个下载线程独占并复用 HTTP Session。API 请求和图片请求使用独立起始速率及共享冷却；失败/重试也消耗额度。HTTP Retry-After 不会因关闭本地限频被绕过。
4. 在途图片数量、暂存预留字节、编码并发和解码内存估算共同约束准入。完整原件、编码结果各有校验收据；没有足够资源时保留可恢复产物。编码输出在落盘前核对实际占用，不能仅按源文件大小假设压缩结果更小。
5. 发布按条数、字节或等待时间触发；队列尾部和暂存压力下可提前发布。暂停停止新准入并等待在途工作退出，未发布完成产物留给续跑。
6. 重放成功媒体批次后清理相应收据；重查最后一个已应用批次，覆盖控制库已提交、清理尚未完成的中断窗口。路径由任务和观察身份重新计算，不使用归档中的绝对临时路径。
7. 调度设置与任务定义分离，存于控制库 `settings.pipeline_v1`。公开 GET/PUT 接口使用修订 CAS，验证全部参数后原子保存；运行器周期热读。降低并发不取消已开始工作，新的工作按新限制准入。
8. 保留“边扫描边下载”和“先建立清单”两种模式。后者只改变调度，不改变任务范围和每轮扫描预算。范围的确定末端已到达时直接结束扫描；本地过滤页同样计入扫描页数，不遗漏最后一批待刷新 ID。

## 兼容性

控制 schema 4、在线 schema 2、图片配方版本和已有任务定义不变。旧 `.ready` 结果仍能恢复，新增 `.downloaded` / `.download.json` 只用于暂存阶段。更换或调节调度参数不会修改历史媒体、查询范围、API 原文、版本租约或既有任务身份。现有单图字节/像素默认上限继续保留并变为可配置。

每站点建议 4 路下载、全局 2 路编码作为起步配置；不是性能承诺。限速使用请求起始频率，字节吞吐和入湖图率分别观测。用户历史实测的 2.75 图/秒不等于已经验证的 Danbooru 固定 IP API 请求限额，不能据此推断 Yandere/Gelbooru 限额。

## 可观测性

单任务聚合器合并所有工作项，保存有界在途列表、累计字节、请求数量、限流次数和阶段时间。速度为最近最多 30 秒的窗口值，退出时清零；旧任务此前缺失的统计不推算。主列表将成功完成、待处理和异常分列；详情进一步展示各流水线阶段。累计阶段时间允许大于墙钟时间，因为工作可以并行。

验证使用隔离湖与受控 HTTP/编码夹具，涵盖连接归属、阶段重叠、阻塞元数据时继续入湖、热调参、内存/暂存背压、限流冷却、暂停续跑与归档重放。真实站点速率上限和正式任务吞吐需要后续实际运行观测。
