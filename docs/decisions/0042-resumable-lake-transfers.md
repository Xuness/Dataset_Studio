# 0042：数据湖图片断点续传与后台任务恢复

日期：2026-09-28。承接 0041，不改变规范湖、在线库 schema、任务身份或图片保存配方。

## 问题

旧执行器可以复用完整下载和编码产物，但传输失败会删除未完成文件。数十 MiB 的图片在低速或不稳定线路上反复重下，浪费已经收到的字节。后台监督器已有重新拉起 worker 的能力，但异常退出后的旧遥测可能继续显示下载状态，也缺少接续记录。

## 下载检查点

独立的 `updates/transfer.py` 负责传输协议，`media.py` 继续负责来源选择、复用和编码。SSD 上新增 `.partial` 与 `.partial.json`，按约 4 MiB 或 2 秒记录检查点；正常中止也尝试保存当前进度。数据先 flush/fsync，随后原子发布字节数与 SHA-256 前缀校验。强制退出最多回退到最近成功发布的检查点，不把尚未确认的尾部当成可靠数据。

收据绑定 URL 摘要、来源类型和已知原图 MD5。恢复时重新校验前缀，截去未提交尾部；不保存请求 URL、凭据或任意服务端异常文本。存在原图校验和或强 ETag 时才接续不完整内容，没有可靠验证依据则重新下载。

HTTP 请求使用 identity 编码、Range 和可用的强 ETag If-Range。206 必须满足起点、总长、区间长度及验证器一致；200 表示完整响应，从头替换部分文件；416 清理过时断点后仅追加一次无 Range 请求。所有请求都经过既有请求额度与冷却，恢复的旧字节不计入本轮网络吞吐。语义依据 [RFC 9110 的范围请求](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests)。

完整传输后继续核对原图 MD5；源内容不符进入待检查，不能发布拼接错误的图像。完整原件的校验收据先发布再重命名，覆盖完成下载和进入编码之间的进程退出窗口。已入湖或确认复用的结果清理自己拥有的暂存文件，失败项保留可接续内容；所有暂存继续纳入共享空间预算。

## 服务恢复

引擎监督器继续自动重启退出的 worker；调度器从现存 queued/running/waiting 状态接手原任务。执行锁和湖生产者锁保证单一所有者，先恢复归档和队列，再处理未完成条目。正常服务退出把任务放回 queued，保留 `UPDATE_INTERRUPTED` 标记，重新启动无须额外等待一分钟。

协调器发生异常时先通知在途工作停止，再等待线程池退出，避免监督器无法接手一个仍活着但已失去调度循环的进程。手动暂停、取消和已完成任务不会自动重新启动。

控制库首次打开使用独立的短初始化锁，覆盖开启 WAL 和检查/升级 schema。它不覆盖日常读写事务；用于避免 daemon 与首个 RPC 同时建库时的 journal-mode 锁冲突。连接设置失败也会关闭连接。并发初始化回归以 25 轮、每轮 4 个同时打开者验证。

基础 `FileLock` 先取得 OS 锁，再初始化空锁文件中的标记字节。Windows 允许锁住 EOF 之后的区域；原先先写标记再加锁，在多个进程/线程首次创建文件时可能写到另一个所有者已锁住的字节，导致 EACCES。

公开遥测增加接续请求次数、后台恢复次数/时间，以及最近一次网络中断的异常类别、已收/可接续字节和尝试时间。不把无执行锁的 running 任务旧帧当成实时下载；界面显示等待后台自动接续。阶段下载耗时包含失败和中止，不再只统计成功收到整张文件的尝试。

## 前端崩溃边界

桌面页面、引擎与下载 worker 是不同进程。仅重开页面不会重新创建任务，后台进度仍以持久控制库和归档检查点为准。此次现场记录不足以判断灰屏原因，不能将退出时的窗口注销错误当成已确认的崩溃原因。没有修改 WebView2 全局配置，也没有宣称修复未知的渲染故障。

## 验证方式

使用隔离湖和本机 HTTP 服务器，在下载已经写入检查点后真正终止子进程；重新启动生产调度循环，验证 Range 接续、只入湖一次、暂停任务不被唤醒。其他夹具覆盖正常服务关闭、200/206/416、错误区间/验证器、短响应、损坏检查点和完成收据中断窗口。真实下载任务只读核验，不向正式湖注入故障。
