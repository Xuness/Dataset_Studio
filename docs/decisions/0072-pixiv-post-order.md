# 0072：Pixiv 作品 ID 与页码排序

日期：2026-10-09。

Pixiv 开放现有 `post_id_asc` / `post_id_desc` 浏览排序，界面称为“帖子 / 作品 ID”。作品 ID 按数值比较，同一作品内页码始终递增；没有来源关联的图片在两种方向下都放在最后。多来源先按 ID、来源身份排序，再按页码和图像身份稳定排序。

浏览身份仍是 `source_id + SHA-256`。同一物理图片关联多个作品或页时，使用当前保留水位以前所有已归档关联中的最小 `(作品 ID, 页码)`，不重复显示相同字节，不按每次 Tag 筛选重新选择排序 ID。最多 20 位的十进制 ID 在 SQLite 使用补零文本，在 Rust 使用 i128，避免字典序错误、i64 溢出和 JavaScript Number 精度损失。

在线格式仍为 3，新增可重建的 `pixiv_object_order` 派生索引。发布者随对象和资产关联增量更新有效区间，并与发布水位原子提交索引覆盖水位；旧保留快照按自己的水位读取。旧发布者推进事实后留下的过期索引会隐藏并重建。升降序各有覆盖索引，分页将同作品同页、后续页、后续作品、无 ID 对象分成独立索引范围，不使用大 OFFSET 或每页全湖排序。

已登记旧湖由受控 worker 启动时在后台补建索引，每 256 个对象提交检查点，完成后才写就绪标记。补建和正常发布共享位置门闩及发布锁，不修改归档和图片内容；中断后继续。原发布者的 `Publisher.prepare_post_order()` 或 `sync_online()` 也能准备尚未在本机登记的旧湖。读取层保持只读，准备期间哈希浏览仍可用，ID 浏览等待就绪。

查询结果、工作集和选择沿用范围来源能力判断。为兼容旧项目成员缓存中缺失的 Pixiv ID / 页码，包含 Pixiv 的固定查询浏览从其保留来源版本投影排序，而不信任旧成员表的单个 i64 帖子字段。现有 Booru 缓存格式无需迁移。会话继续使用原 `booruOrder` 字段保存支持 ID 排序的范围偏好，包含 Pixiv；不支持该能力的范围仍使用 `order`。

验证入口：`pnpm test:lake tests/test_media_post_order.py tests/test_media_lake.py`、`pnpm test:integration pixiv-order`、`node tooling/smoke-pixiv-ui.mjs`。覆盖数值与页码顺序、重复对象、空关联、Tag、固定结果、工作集、选择、多来源、发布后历史快照、重启、旧索引中断续建及归档重建。
