# 0010：范围浏览与排名执行的性能边界

2026-09-10。项目数据库格式保持 v8，接口版本保持 1。

- 工作集保存成员，浏览顺序与榜单排名分别表达。纯浏览不应要求重新物化全部成员；已有帖子索引用于有界扫描与成员求交。
- 一次浏览请求至多前进 8,192 个索引候选，另有每来源最多 129 项的预读批次；此路径最多合并 8 个 Danbooru 来源。稀疏范围通过绑定来源版本、范围和排序的游标继续扫描；没有结果的中间响应明确标记为准备状态。混合适配器继续使用通用排序路径；更多来源可按图像身份浏览，帖子排序仍受查询协议的 8 来源上限约束。
- 小范围至多 4,096 个成员可直接解析排序键；多来源采用统一排序比较器，未知帖子 ID 始终放在最后。
- 榜单读取复用旧成果已有的表达式索引：前 N 名谓词匹配 `coalesce(rank, max)`，同时保留空名次排除；分页分别读取游标所在分组、后续分组和空分级，再合并至多三个小页面。原有空值、同名次及分级顺序保持不变。完整人数和普通合格人数使用已验证摘要，其他计数仍按实际过滤条件计算。
- 异步查询准备通过已有结果 ID 跟踪，不在状态轮询中重新解析大型范围。准备期暂停下一页缩略图预取。失败、取消和释放保持明确原因，重试先释放失败结果。未准备好的查询浏览保留原错误消息；取消与中断使用各自错误代码。
- 新生成输入的校验哈希直接构成计划，不在父进程再次读取新文件。工作进程仍独立验证输入。输出完整校验生成进程内发布凭据，绑定文件身份、哈希、大小、修改时间、输入身份和执行计划；Windows 共享模式拒绝验证到发布之间的输入和输出写入，重命名后重新持有不可删除的最终文件。凭据存活至成果提交完成；恢复已有输出时仍需完整校验。
- 排名材料仍使用 FULL 持久化，内部每 8,192 行提交一次；读取/回调批次保持 512 行。在切换阶段、写入检查点与最终发布前显式提交。
- 任务观测信息扩展已有进度 JSON，记录真实阶段时长、当前分级、更新时间和执行器心跳；旧记录缺少这些字段时不推算历史耗时。
- 阶段用时是墙钟时间并包含排队、等待和恢复间隔，同名同分级阶段累计；不是 CPU 时间。执行器每 2 秒更新心跳，前端明确显示“引擎响应”，不将其视为评分进度。重试从新的执行计时开始。
- 开发界面可继续热更新，计算引擎默认使用 release 构建；实际二进制内容决定运行缓存身份。
