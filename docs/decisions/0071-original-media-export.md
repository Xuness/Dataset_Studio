# 0071 — 原图读取、另存与文件导出

日期：2026-10-09。状态：已实现。

## 问题

浏览和排名只能通过预览接口读图，预览边长上限 1600 px。放大到适应窗口以上时看到的是放大的缩略图。数据湖中的原图在包文件内，没有可直接打开的文件路径，因此也无法“在资源管理器中显示”或保存单张原图。工作集、选择和查询结果没有导出到普通文件夹的方式，只能生成 JSONL 数据清单。

## 决定

### 原图读取

- `GET /v1/projects/{pid}/sources/{sid}/assets/{aid}/original` 返回存储的原始字节和来源报告的类型，无缓存。读取先按 Index 类核对媒体身份取得大小，再按该大小申请 Media 类读取额度；单张上限 64 MiB（即 Media 类总额度），超出时返回 `READ_BUDGET_EXCEEDED`，不做部分读取。项目归属沿用 `store.source(pid, sid)` 检查。
- `POST …/original/save {path}` 由引擎把原图写到用户在原生“另存为”对话框中选择的绝对路径。目标所在文件夹必须存在，且不在项目任何数据湖的索引或媒体目录内；数据湖保持只读。写入先写同目录临时文件再改名，不留下半张图。
- 前端在用户放大到适应窗口以上或请求 1:1 时，用原图替换当前预览。复制图像先读原图，再转 PNG 写入剪贴板。浏览器开发模式没有原生对话框，“另存原图”改为浏览器下载。

### 文件导出任务

- 新算子 `core.export_files`（导出原图），参数为目标文件夹、元数据级别（`none` / `tags` / `full`）、标签格式（`comma_spaces` / `comma` / `space`）和是否写 `manifest.jsonl`。输入范围与其他工具相同：工作集、项目选择、查询结果或数据湖；提交时按现有任务机制固定成员。
- 算子本身只计算每个成员的计划文件名，仍然不访问来源或文件系统。文件读写在引擎的导出服务中执行，不经过独立执行器进程，因为执行器没有来源读取能力。计划行写入任务成果（类型 `file_export`），与其他任务一样通过逐行重算校验后发布。
- 文件名为 `{序号:06}_{原文件名}`。序号是固定成员的顺序，即图像身份（来源、图像 ID）顺序，从 1 开始；不是排名顺序。Booru 湖的存储文件名是内容哈希。非法字符替换为 `_`，名称截断到 120 字节，扩展名使用来源记录的扩展名。
- 同名文件已存在时：大小与媒体身份一致，并且（图像 ID 为 SHA-256 时）内容哈希一致，视为已导出并跳过；否则依次使用 `_2`、`_3`…。因此中断后重试只补写缺失的文件。
- `tags` 为每张图写同名 `.txt`，内容取各记录来源观察中的 `tags` 字段。没有标签时不写文件，也不算失败。`full` 写同名 `.json`，包含图像身份、读取版本、每条记录及其来源观察的全部字段（每张图最多 20 条记录，超出时 `records_truncated` 为真）。元数据读取失败记在该图的清单行，不影响图片导出。
- 目标文件夹的 `manifest.jsonl` 每行记录序号、实际文件名、状态（`written` / `existing` / `failed`）、图像身份、名称、来源和写入字节数，按本次执行完整重写。
- 有图片失败（例如超过 64 MiB、来源不可读）时，其余图片照常写完，失败项写入 `export-errors.jsonl`，任务以 `EXPORT_PARTIAL` 失败结束，便于重试。全部成功时删除旧的 `export-errors.jsonl`。
- 读取以每批最多 16 个对象、32 MiB 为单位，后台优先级；任务调度仍是串行的，长导出期间其他工具任务排队等待。

### 提交校验

提交导出任务时，引擎检查目标存在、是文件夹、可写入，且不在项目数据湖目录内。任务列表中的导出任务提供“打开文件夹”（`POST /v1/projects/{pid}/jobs/{jid}/export/reveal`），通知中也有同样的入口。

## 影响

- 新增任务算子与成果类型，旧项目和旧任务不受影响。操作员列表增加一项；通用工具面板不显示它，导出使用专门的对话框（可选文件夹）。
- Tauri 能力增加 `dialog:allow-save`。
- 原图读取共享 64 MiB 的 Media 类额度，并发为 1。导出与交互预览会互相排队；导出使用后台优先级。
- 未实现：按排名顺序编号、超过 64 MiB 的流式原图、Ugoira 等压缩包的展开、把图片直接拖到系统文件夹。
