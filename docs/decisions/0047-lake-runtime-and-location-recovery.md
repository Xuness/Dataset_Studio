# 更新运行环境与数据湖位置恢复

日期：2026-09-29；位置关联流程于 2026-10-02 简化。对应 Astra F6、G1；补充 [0046](0046-update-command-handoff-and-cancel-cleanup.md)。

## 运行环境

Rust 控制器区分解释器更换和控制状态目录迁移。普通配置入口允许更换 Python，已配置时必须保留原 state_root；任务、凭据、计划、湖登记和固定输入保持原身份。状态目录迁移不在本接口范围内。

候选解释器先通过无状态 check：导入依赖、检查 Python/WebP 能力并核对 worker/protocol 版本。此时不打开控制数据库、不读取凭据、不启动抓取。然后核对状态目录的 studio-owner.json，停止原 worker，启动候选并等待它取得 runner.lock 后报告就绪。候选等待激活字节期间不调度任务；配置原子保存后才激活。

一个 Rust 读写门控制配置、监督器和 RPC 的代次交接。配置和停止使用写门，正常 RPC 使用读门，取消不必排在其他 RPC 后面。旧进程超过 8 秒尚未退出时，更换请求返回冲突，保留进程及原配置，不并行启动另一个代次。引擎退出仍采用既有最终终止策略，持久检查点负责后续恢复。

启动失败保留旧配置，候选首次创建的所属标记会回收；原工作运行器可重新启动。配置成功仅证明本次握手与启动成功，后续运行失败由监督器处理。控制器提供已保存路径、健康状态、脱敏错误、失败数和下一次重试时间；自动重试从 10 秒退避到最多 300 秒，最多保留 32 条不包含原始 Python 输出的启动事件。设置页始终提供验证和更换入口。

## 位置迁移

更新控制库升级到 v6，新增持久 lake_relocations；v5 的原子命令和取消回收保持。已登记更新服务的湖禁止从旧“重新关联”入口单独修改读侧位置。统一入口位于设置 → 数据湖 API → 迁移数据湖位置，并通过公开 API/SDK 操作。

设置页默认直接显示原媒体、索引路径。文件手动搬好后填写新路径，点击一次“重新关联”，界面通过既有 prepare/apply API 自动完成冻结和读写位置交接。已经搬走的原目录无需先搬回，也不会被重新创建。尚未搬文件时，可展开“搬动文件前暂停写入”先冻结新写入；长任务仍需在任务页暂停。

内部保留 draining → prepared → verified → writer_committed → complete，以支持互斥和中断恢复。取消只允许在 draining/prepared，释放本次冻结并保留原登记路径；不搬回文件，也不要求原目录在线。切换开始后只允许继续完成已经选定的位置。

1. 持久冻结该湖的新领取，等待位置准入和湖写锁的现有持有者退出。不会抢占正在执行的更新。仍有持有者时返回等待状态，界面保留路径输入供重试或取消。
2. 对仍在线的原目录保存轻量检查点：library_id、site、generation、served_seq、min_seq、最后一个归档提交的序号和 batch_id，以及已有生产者退役标记。通过 SQLite 主键读取末条提交和发布记录，不读取历史 manifest_json，不枚举媒体、暂存或输入文件，也不调用 Library.recover。
3. 在新目录取得写锁，核对归属、指针和数据库身份、在线版本范围，以及最后发布记录对应的归档 batch_id。原位置有检查点时保持归档末条提交、索引代次和版本保留范围；旧索引已经离线时要求目标索引已发布到目标归档的最新提交。新位置仍不能与旧位置嵌套或混入其他湖、控制器。
4. 写侧更新发布反向链接、cache_owner、UPDATE-CONTROLLER 和 lakes，记录 writer_committed，继续冻结写入。Rust 原子更新共享 source_locations，通知打开的项目，最后确认 complete。引擎重启自动补完 writer_committed；设置页可继续其他阶段。改变阶段前在同一位置门下重读状态，防止旧取消覆盖新切换。

原索引仍在时保留 LAKE-RELOCATION 标记，阻止旧副本继续发布。准备后搬走索引再取消时，随目录搬走的标记可在下次关联时接替，但必须能在同一控制器中确认它属于同一湖的已取消记录；未知或仍有效的其他标记继续拒绝。只移动媒体时，共用索引的 cache_owner.root 拒绝旧媒体位置。外部生产者应停止后再搬文件。新索引保留一个 relocation 版本租约，沿用已知旧版本下界；原索引离线时保护目标当前仍保留的全部版本。旧副本不会自动删除。

### 轻量关联的验证边界与兼容

旧实现会先恢复归档、读取全部提交清单计算摘要，再递归生成文件校验清单；所有工作都放在 90 秒同步 RPC 内。真实 Gelbooru 的准备请求因媒体盘大量访问而超时，状态停留在 draining。2026-10-02 去除这些与路径关联无关的全量工作，未通过延长超时掩盖问题。

新检查点标记 version=2，无控制库或公开 DTO 升级。旧 draining 记录可以直接重新准备；旧 prepared/verified 记录继续保留其身份、归档序号、代次与版本下界，但不再计算 archive_digest 或读取旧文件清单数据库。历史清单文件保留在原位置，不在关联时清理。

路径关联不证明整库复制完整、不检查所有归档文件或可恢复暂存的内容，也不能在两个旧目录都已离线时证明目标不是一份自洽的旧备份。正常搬迁应保留完整目录；归档恢复和内容完整性验证使用已有独立工具。生产者退役标记仍检查，但 retirement 目录不再逐文件扫描。

## 连接生命周期与诊断

Python 发布器读取 journal.sqlite 使用显式关闭，避免依赖垃圾回收释放 Windows 文件句柄。普通 sqlite3 的连接上下文仅管理事务，不能作为已经关闭连接的证明。

资源 API 的 online_sqlite 提供进程累计 busy_errors、protocol_errors、lease_retries、max_lease_write_ms；统计包含被成功重试恢复的错误。错误计数不等同于失败请求数。Rust 的 Index/Media/Decode/NativeQuery 准入以及 Python 更新资源预算仍各自独立，不宣称构成全应用共享的总内存上限。

真实规模副本上，四个并发浏览请求稳定出现约 10.8 秒的 SQLITE_PROTOCOL，发生在读取连接而非租约重试。检查当前 libsqlite3-sys 0.38.2 所带 SQLite 3.53.2 源码，Windows VFS 的 winIsUNCPath 把任何双反斜线前缀都视作 UNC，因此 Rust canonicalize 产生的本地扩展路径也进入共享句柄分支。

在线数据库仍先使用完整规范路径检查目录边界，再用 dunce::simplified 为 SQLite 选择等价且安全的普通本地盘符路径。读取与租约写入使用同一个结果；不改变只读打开标志、不新增常驻连接池，也不延长锁等待。相同大规模副本的前后对照从每轮 4 次协议错误变为零。超长路径、保留名称和真实 UNC 路径不能安全简化时保留原路径；本次实测结论限于当前本地卷和普通路径，不外推到网络文件系统。

验收记录见 [R3/R4 收尾](../verification/2026-09-29-astra-r3-r4-closeout.md)。

## 2026-09-29：开发期控制库的补充升级

本机开发服务曾热重载 v5 的中间实现，并在 `lake_dispatch` 加入前保存了版本号。后续 v6 只执行位置迁移建表，未补齐调度表，导致运行器握手成功后在第一次调度查询退出。完整版本的新建与升级测试没有覆盖这一已有状态。

新增 v7 迁移，使用 `CREATE TABLE IF NOT EXISTS` 补齐 `lake_dispatch`，保留已有服务顺序及其他控制数据。沿用初始化、运行器和执行锁，建表与版本号在同一事务提交；失败回滚，重复打开不重置数据。未来为已执行的迁移补充结构时新增版本，不能仅修改历史建表脚本。启动验收须确认调度心跳继续推进，不能仅确认握手成功。

故障复现、迁移回归及本机恢复见[补充验收](../verification/2026-09-29-lake-dispatch-migration.md)。
