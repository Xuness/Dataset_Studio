# 0043：独立阶段执行、动态暂存和局部扫描重试

日期：2026-09-28。承接 0041–0042；正式 Gelbooru 长任务暴露了发布阻塞调度、候选扫描随历史增长和暂存过量预留的问题。

## 决策

1. 元数据扫描、站点下载和编码保留各自的线程池；每个湖新增一个异步媒体发布执行器。协调线程只收集完成结果、补充阶段任务和执行资源准入，不再同步等待 TAR/Parquet、归档 journal 或在线发布。Pillow 编码本轮保持现有线程实现，不引入尚未验证收益的进程池。
2. 每湖同时只有一个媒体发布 Future。元数据提交、媒体发布和覆盖确认共享串行发布锁；标签参考归档继续受同湖归档/设备锁保护。网络请求不在发布锁内。元数据提交等待写入通道时，图片协调线程仍能继续工作。
3. 待发布批次按条数、字节、最大等待时间触发。尾部或暂存压力可提前发布。发布中的图片仍计入在途数量和资源额度，提交并重放成功后才释放、清理；不能因移出 ready 列表而绕过预算。
4. 候选队列按 pending、failed、pending_metadata 分别使用已有的 `(job_id,state,post_id)` 索引，在同一个短只读事务内有界取数，再按帖子 ID 合并。保留 retry_at、尝试次数和稳定顺序，不遍历已完成历史，也不新增全湖索引。
5. API 临时网络错误或可重试服务错误只停止当前扫描阶段；重试时间与安全错误摘要保存在遥测中，现有持久图片队列继续下载、编码和发布。重试等待至少 60 秒并尊重 Retry-After；已有远端共享冷却仍有效。凭据、内容完整性、归档等错误继续按原安全边界停止执行，不能当作普通网络抖动忽略。

## 暂存预算

`staging.py` 将磁盘估算与解码内存分离。单张下载上限继续是硬限制，但不再将该上限乘四后分配给所有图片。

- 初始原件按有效的元数据大小估计；缺失时从最多 8 MiB 起步。
- 获取 HTTP 响应后按已验证的响应长度重新申请；长度未知时每 4 MiB 扩容，写入新块前先取得额度。响应长度、文件硬上限、Range/MD5 校验均继续执行。
- 静态输出按有效像素和编码范围保守估计；可能保留动画原件时计入原件大小。下载完成后按实际文件长度收缩，编码前再用真实图片头核对尺寸和输出预留。
- 峰值覆盖“原件 + 编码输出”和“编码输出 + TAR 副本”两种阶段，并给收据和批次元数据留余量。编码完成后只保留实际产物、打包副本及小额开销的额度。
- 共享预留包含尚未删除的断点文件。检查物理磁盘余量时，仅把尚未写入的承诺字节加到剩余空间要求，避免把已在磁盘上的文件重复扣减。
- 响应/输出纠正需要更多额度时，保留已完成原件或部分下载，暂缓该图片并让其他工作继续；这种资源等待不增加下载失败尝试数。没有其他工作能释放空间时，任务仍进入可恢复的 waiting_space。

解码内存仍按源像素和输入缓冲估算，与 SSD 预算独立。设置热更新不撤销已经发放的额度；新增长和新任务受最新限额约束。

## 生命周期与兼容性

控制 schema 4、在线 schema 2、已有任务范围与配方、文件收据及归档幂等键保持兼容。暂停后停止新准入，等待已有阶段到达安全边界；发布 Future 的错误必须由协调器接收，不能静默丢失。进程中断仍通过持久收据、归档检查点和既有控制队列恢复。

新增可选遥测字段显示发布中图片、暂存等待、扫描重试及下一次时间，以及共享暂存实际/预留/上限和解码额度。旧任务缺失这些字段时正常显示。无执行所有权的旧运行帧不再显示发布活动或有效资源预留。

## 验收要求

- 阻塞发布器时，后续下载和编码仍持续推进，在途数量不越界。
- API 扫描临时失败时，已获取页面继续入湖；重试成功后完成原冻结范围。
- 1 万条已完成历史不增加候选查询的 VM 步数数量级，重试过滤和排序保持正确。
- 8 GiB 暂存可接纳 16 张小图，不再为它们虚占 16 GiB；未知长度扩容、预算纠正和输出收缩可验证。
- 真正缺空间、暂停、服务退出、强制终止、Range 接续、归档成功后控制重放失败等既有恢复场景继续通过。

隔离测试证明调度行为和资源边界，不承诺真实站点的端到端速率；正式任务恢复后的吞吐仍需独立测量。
