# 0065：四源空湖创建与显式来源身份

日期：2026-10-07。承接 [0040](0040-owned-lake-worker-and-image-recipes.md)、[0050](0050-archive-rebuild-and-producer-retirement.md) 和 [从零建湖计划](../plans/zero-lake-collection-2026-10-07.md)。

## 决定

三种 Booru 增加受控空湖创建命令，沿用归档 1 / 在线 2；Pixiv 沿用已有归档 2 / 在线 3 创建服务。工作台统一提供“创建新的空湖”和“核验并登记”两种操作。创建没有网络副作用，也不要求已下载发行归档、旧生产者索引或外部 Store 仓库。

`POST /v1/lake-updates/lakes/create` 与 SDK `lakeUpdates.createLake` 接收请求 UUID、站点、图片归档目录与在线目录。两个绝对目录必须独立且为空。同一请求内容重试使用相同湖 UUID 与在线代次；同键不同内容拒绝执行。创建命令复用现有请求账本，以独立操作名隔离 Pixiv 请求。

归档的 `initialization.json` 先固定目录、站点、身份与在线代次。归档 journal、库说明、在线 schema 和双向指针按顺序建立；只有指针和身份验证后才登记可执行任务的湖。中断重试沿用固定身份，未知非空目录不被接管。已发布指针对应的数据库或归档 journal 缺失时拒绝重置为空湖，交由独立恢复入口处理。

空在线库发布序号 0 的 `empty-baseline`，使普通浏览、租约与来源挂载使用同一版本协议。它不声明任何远端元数据覆盖。首次新帖任务仍需明确起点；指定 ID 或其他部分采集不会推进全站新帖水位。

## 来源识别与兼容

新 Booru 的 `library.json` 增加可选 `site` 声明。读取端从显式声明识别来源；旧湖缺失此字段时继续检查原 HF 转换清单，旧 Danbooru 保持兼容默认。两个声明同时存在且冲突时拒绝读取。不能为原生空湖伪造 HF 导入记录。

新库不建立 `CURRENT.json`、native DuckDB 或目录 SQLite。图片 TAR、Parquet、归档提交、在线发布与内容去重继续使用现有实现。归档独立重建核对显式站点，禁止按另一个站点重建新库。

## 验证

隔离 Python 回归覆盖三站空湖后的稀疏元数据与选择性补图、三处初始化中断、目录冲突、重复/并发请求、缺失已发布数据库以及独立重建。SDK 集成覆盖新湖创建、重复请求、空湖项目挂载和既有更新/恢复流程；Rust 检查原生声明与旧导入清单冲突。所有请求使用离线夹具，真实源站可用性不由这些回归证明。
