# 工程基础架构草案

状态：已采纳为工程方向。首版实现范围和当前边界见 foundation-status.md；本文保留完整设计意图，不代表所有规划能力均已实现。

日期：2026-09-07。

## 已明确的产品基础

- 项目：长期持久化的工作空间。
- 工作集：项目内具体组织和操作的数据对象。
- 工作区布局：视图、面板和工具的呈现方式。
- 项目引用完整的数据湖；切分、筛选、组织与加工发生在项目内部。
- 一个项目可以引用多个数据湖，同一个数据湖可以被多个项目引用。
- 项目中的数据与项目积累的成果保持连续，各工具可以按照用户自己的顺序使用。
- 公式、标注、审美评估等均是可加入的功能；核心领域模型不预设固定业务流水线。
- 页面构图、视觉风格、具体组件皮肤和功能区排列留待后续设计。

## 1. 建议技术组合

| 部分 | 建议 | 职责 |
| --- | --- | --- |
| 桌面宿主 | Tauri 2 | 窗口、本机对话框、原生集成、引擎连接和安装更新 |
| 前端 | React + TypeScript strict + Vite | 应用框架、功能模块、交互与视图 |
| 前端异步数据 | TanStack Query | 通过 SDK 获取结果、缓存有限页面、同步后端变化 |
| 前端会话状态 | 按项目隔离的 store；实现库待骨架阶段确定 | 当前视图、焦点、布局、工具草稿及选择引用 |
| 本机后端 | Rust + Tokio + Axum | 项目、资源访问、查询协调、任务、结果发布 |
| 应用持久化 | SQLite | 项目权威状态、工作集定义、任务记录、成果目录 |
| 分析及批量结果 | DuckDB / Arrow / Parquet，按用途使用 | 元数据查询、批量表格结果、计算与交换 |
| 算法执行器 | Rust 或 Python 独立进程 | 图像、模型和其他耗时任务 |
| 接口定义 | Rust API DTO + Utoipa / OpenAPI | 统一接口契约，生成 TypeScript 类型 |
| 仓库 | 一个 monorepo，pnpm workspace + Cargo workspace | 原子修改契约与两端实现；统一检查和版本管理 |

React + Vite 是这里针对桌面客户端作出的选择。React 官方说明了这种构建方式及需要自行安排数据访问、路由等能力的取舍：[React 构建文档](https://react.dev/learn/build-a-react-app-from-scratch)。

前端状态库、路由库、虚拟化实现及控件库在具体基础能力需要时确定；保持清楚的状态归属比增加依赖更优先。

## 2. 运行时：桌面客户端、本机引擎、执行器

```text
React 功能模块
    ↓ Studio SDK
版本化本机 API
    ↓
Rust Engine
    ├─ 项目与工作集服务
    ├─ 选择与结果服务
    ├─ 数据源适配器与读取协调
    ├─ 任务与资源调度
    └─ 执行器管理 → Rust / Python workers

Tauri 宿主 → 原生能力 + 引擎启动/连接 + 生命周期协调
```

引擎是独立可执行程序。发布时作为桌面安装包的一部分交付，由应用管理启动和连接。Tauri 提供捆绑和启动外部程序的能力：[Tauri sidecar 文档](https://v2.tauri.app/develop/sidecar/)。

同一个用户、同一个应用数据根下，只有一个引擎实例拥有应用数据库的写入权。该实例可管理多个项目和客户端窗口，并统一分配 CPU、内存、机械盘与 GPU 资源。

独立进程增加了启动握手、连接恢复和版本兼容的工作。它换来明确的数据库所有权、与界面分开的生命周期，以及无界面验证核心能力的入口。

Tauri 和 Axum 都位于外层。领域与应用服务不导入窗口对象、HTTP 路由或 React 概念。后续可以在同一服务接口上增加 CLI 或其他宿主。

### 生命周期规则

- 切换功能、卸载前端组件和关闭项目视图不取消已提交任务。
- 关闭窗口、停止引擎、取消任务是不同操作；具体默认产品行为后续确定。
- 引擎重启后读取任务记录，识别中断的执行尝试，按照执行器能力恢复或重试。
- 启动过程检查引擎实例、PID、握手信息与 API 版本；陈旧发现记录可清理，存活实例不能仅因连接暂时失败被替代为第二个写入者。
- 升级需要协调引擎与执行器。正在运行的旧引擎保留自己的契约与结果版本；发生不兼容时返回明确错误，不能静默连接或重复打开同一项目为可写状态。

## 3. 前后端边界与契约

前端模块仅依赖 `@studio/client` 的业务接口。Tauri 引擎发现、HTTP 传输、认证、错误转换和媒体加载集中在 SDK / 平台适配层。

首版本机 API 使用 HTTP + JSON；事件采用带游标的流式订阅，媒体采用鉴权二进制响应。引擎只绑定回环地址，连接使用临时凭据；生产窗口与开发窗口的来源分别配置。凭据不进入项目文件和媒体查询参数。

图片由统一媒体客户端获取，受可见范围、预取窗口和字节预算限制。浏览器版本可以使用受控 Blob URL 缓存，销毁时释放；原生媒体代理可在性能验证需要时加入。组件不拼接磁盘路径。

### 单一契约源

Rust 的专用 API DTO 和端点定义生成 OpenAPI，再生成 TypeScript 类型。领域对象、数据库行和 API DTO 分开。响应事件使用同一契约注册机制。

Utoipa 提供 Rust 代码生成 OpenAPI 的能力；openapi-typescript 从 OpenAPI 生成类型：[Utoipa](https://github.com/juhaku/utoipa)、[openapi-typescript](https://openapi-ts.dev/introduction)。

生成的 TypeScript 类型提供编译期检查，不能代替运行时校验。请求由后端解析并验证业务约束；SDK 校验握手与事件等边界消息，worker 输出经过结果模式校验。

生成物不手改。CI 重新生成并检查差异，检查不兼容接口变化及版本调整。API 版本、项目格式版本、数据源适配器版本、执行器协议版本分别管理。

### 最小公共对象

| 对象 | 语义 |
| --- | --- |
| ProjectId | 项目的稳定身份 |
| SourceRef | 引用一个完整逻辑数据湖，位置由本机注册表解析 |
| ItemRef | 数据湖身份 + 湖内逻辑条目身份；来源条目可以具有多次观察和多个媒体版本 |
| AssetRef | 数据湖身份 + 湖内媒体资产身份；与文件内容哈希、来源条目身份分别表达 |
| ObservationRef | 元数据观察记录的稳定身份，明确某项元数据来自哪次观察 |
| ScopeRef | 项目全部数据、工作集、查询结果或选择对象的引用 |
| QuerySpec / ResultRef | 查询定义及有限分页结果的引用 |
| SelectionRef | 后端维护的选择对象；包含范围引用与必要的增删成员 |
| InputSnapshotRef | 某次计算固定的输入成员、元数据依据和依赖 |
| JobRef / AttemptRef | 逻辑任务与某一次执行尝试 |
| ArtifactRef | 带类型、模式和来源的项目成果 |

这些对象表达数据和操作边界，不要求工具具有固定执行顺序。

集合与查询必须声明成员类型。图片暂不可用、条目只有元数据、同一图片具有多次观察、不同条目引用相同内容，都是可表达的状态。重复内容的识别通过内容身份关联，不自动合并来源事实。

例如 SDK 可以提供以下接口形状，具体字段在契约实现阶段细化：

```ts
client.projects.open(projectLocator)
client.sources.attach(projectId, sourceRef)
client.queries.create(projectId, scopeRef, querySpec)
client.results.page(projectId, resultRef, cursor, pageSize)
client.selections.update(projectId, selectionRef, change, expectedRevision)
client.jobs.submit(projectId, operatorId, inputSnapshotRef, parameters, idempotencyKey)
client.artifacts.list(projectId, scopeRef)
```

### 通用协议约定

- 请求与日志带 request ID；项目命令必须携带项目身份。
- 错误包含稳定错误码、可读说明、关联字段或对象及重试语义。
- 并发修改携带预期版本；冲突返回当前版本信息，交由用例定义合并或重试。
- 创建任务和发布结果使用幂等键；连接中断后的重试不能重复创建工作。
- ID、哈希及可能超出 JavaScript 安全整数范围的值使用字符串；计数值限定类型与精度语义。
- 分页使用稳定排序与游标，显式包含结果版本。总量区分精确值、估计值和未知。
- 有昂贵排序或跨湖聚合时，先创建可追踪的计算，再分页读取结果。
- 请求取消、停止事件订阅、取消后台任务具有独立接口和语义。
- 事件包含流身份、序号和资源版本；断线后续接，游标过期则重取权威快照。
- 生命周期事件可以持久化；高频进度聚合并限速，避免每张图片都形成数据库事件。

## 4. 后端内部模块与依赖

建议采用模块化单体的业务核心，并用独立执行器承载耗时或依赖复杂的算法。

| 模块 | 拥有的数据与职责 |
| --- | --- |
| projects | 项目身份、项目版本、数据源引用、打开/关闭与保存用例 |
| sources | 适配器能力、来源字段说明、读取会话、资产定位 |
| collections | 工作集定义、选择对象、成员关系与集合操作 |
| queries | 查询规划、结果生命周期、分页与预算 |
| jobs | 输入固定、任务状态、执行尝试、调度、恢复与取消 |
| artifacts | 成果类型、来源记录、文件清单、验证与发布 |
| sessions | 可恢复的工具草稿与会话描述；不作为计算结果 |

模块通过公开的应用服务或端口协作。模块之间不读取对方私有表，不导入对方内部实现。

依赖方向：

```text
desktop / engine host → application services → domain
storage / source adapters / executors → application ports + domain
```

宿主负责组装具体实现。核心模块通过端口描述需要什么，基础设施实现这些端口。没有需求支撑时，不为每个小函数增加接口或单独 crate。

Tokio 处理异步 I/O；同步数据库与 CPU 工作进入有上限的专用执行资源。并发数量、任务队列与输出缓冲都有预算，避免在异步执行线程上进行无界阻塞。

## 5. 持久化与数据归属

| 层 | 保存内容 | 生命周期 |
| --- | --- | --- |
| 应用级注册表 | 最近项目、逻辑数据湖到本机位置的映射、用户设置 | 本机长期存在 |
| 项目 SQLite | 工作集定义、项目修订、选择、任务、成果目录、草稿 | 项目的权威状态 |
| 项目成果文件 | 大型成员清单、列式计算结果、向量等 | 与其成果版本共同保存 |
| 可重建缓存 | 缩略图、分页缓存、临时计算数据 | 有空间预算和淘汰机制 |
| 原数据湖 | 归档图片与来源事实 | 按数据湖自身的存储及发布协议管理 |

项目使用清晰的目录格式：一个小型项目清单、项目数据库和受项目管理的成果目录。项目清单保存项目 ID 与格式版本，数据库保存主要业务状态。缓存默认可外置，本机路径映射不作为项目身份。

项目保存引用与加工成果。移动项目或重新关联磁盘时，依靠稳定的来源和资产身份恢复关联。项目包含某个成果的索引记录，不代表其文件可以作为普通缓存随时删除。

大型标注、分数与向量采用带模式的批量成果，例如 Parquet / Arrow。项目数据库保存成果清单与关联；频繁编辑的小规模修正作为项目覆盖层保存，按需要合并为新成果版本。

所有项目写入通过引擎应用服务完成。执行器只写本次任务的暂存输出；引擎验证文件清单、内容模式和来源后发布。

文件与数据库无法依靠单一数据库事务同时完成提交。发布采用可恢复协议：暂存完成并验证 → 固定最终成果位置 → 数据库事务登记发布。启动恢复程序处理未登记文件、未完成发布及孤立暂存；成功状态只在发布完成后出现。

项目数据库升级通过版本化迁移执行，升级前生成一致的可恢复备份；备份与复制不直接复制活跃 WAL 数据库的单个主文件。每个项目拥有串行写入边界，可并发读取。

## 6. 数据源适配器与 Danbooru 接入

适配器应提供：

- 来源身份、格式版本与能力声明。
- 字段名称、类型、缺失值语义和来源说明。
- 查询下推能力与读取会话。
- 稳定资产引用到媒体内容的解析。
- 可用于任务固定输入的版本依据；无法提供所需一致性时明确返回限制。

跨数据湖通用字段可以映射到统一语义，来源特有字段保留命名空间。未提供某字段与字段值为空要能够区分；不同来源同名的评分不能直接假定可比较。

每个来源必须明确枚举单位和视图能力，包括逻辑条目、媒体资产及历史观察的关联。接入完整数据湖时不能静默用“当前帖子视图”替代全部归档资产，也不能把全部历史观察直接计作独立图片；首个适配器需要分别验证这些枚举范围。

首次 Danbooru 适配器以已有归档为来源。项目加工写入项目成果，后续归档维护能力通过独立的写入用例和来源发布协议接入。

### 必须实现的读取版本边界

generation 名称和 CURRENT 指针本身不能证明该代索引不可变，单一 seq 也不能证明所有查询都可以回溯到那一时刻。

适配器必须根据来源真正支持的协议取得一致读取：例如不可变发布代，或与写入者协调的读取租约及数据库事务。原生 DuckDB 的进程内模式支持一个读写进程，或没有写入者时的多个只读进程；SQLite 的 WAL 经验不能直接套用到它上面：[DuckDB 并发说明](https://duckdb.org/docs/current/connect/concurrency)。

在确立发布协议前，来源繁忙或版本边界不可靠时返回 `SOURCE_BUSY` / `SNAPSHOT_UNAVAILABLE` 等明确状态。需要可追踪固定输入的作业，必须取得有效读取会话后才能固化输入；无法证明一致性的临时读取不能冒充不可变快照。

任务输入记录每个来源的有效版本、成员引用及用到的元数据观察记录。必要时把实际输入投影物化成项目清单。仅保存筛选表达式，或者对不断变化的 current_posts 追加 commit_seq 条件，都不足以构成历史快照。

Rust DuckDB 驱动、底层库与现有文件的兼容性，需要用只读真实样本验证后锁定。未来版本升级必须包含已有归档格式的兼容测试。

## 7. 执行器与扩展规范

一个处理算子声明：

- 稳定 ID、版本、参数模式。
- 支持的输入类型与必需字段。
- 输出成果类型与模式。
- CPU、内存、磁盘、GPU 等资源需求。
- 是否支持取消、检查点恢复、确定性执行和局部结果。

核心负责解析输入、生成 InputSnapshot、创建任务和执行尝试、提供资源、接收结果与发布成果。算子负责自己的计算语义。

Rust / Python 执行器使用独立的版本化控制协议。首版可以通过标准输入输出传递小型结构化消息，日志走独立流；大批量数据采用有上限的流或项目暂存文件引用，图片及向量不塞进 JSON 日志。

进程隔离用于故障和依赖隔离，本身不等于对第三方代码的安全沙箱。运行时第三方插件的信任与权限模型，在引入该能力时另行设计。

Python 依赖使用独立的 pyproject 与锁文件；模型运行环境可以按执行器能力安装。应用基础启动不依赖已安装所有模型或 GPU 算法。

### 任务与结果语义

- 逻辑任务固定输入，重试创建新的执行尝试。
- 中断后恢复必须符合算子声明的恢复能力；有副作用的输出通过暂存与幂等发布避免重复生效。
- 取消采用明确的协作边界；未支持暂停的执行器不显示为已暂停。
- 部分失败按算子的成果契约记录；单项失败与整个任务失败分别表达。
- 结果记录算子、参数、模型标识、输入版本及执行信息。非确定性计算保留实际结果版本，不能只凭相同参数声称输出必然相同。

调度统一到本机引擎。对机械盘的批处理按物理包和偏移组织读取，前台预览请求有独立优先级和有界预取。任务通过资源服务访问来源，避免各算子独立扫描同一磁盘。

## 8. 前端基础与功能模块

前端分为应用组装、功能模块、SDK、基础控件与样式变量几个层次。

功能模块可以贡献入口、中央视图、上下文面板、命令和版本化工具草稿。模块描述不编码业务先后顺序。一个后端算子可以被多个界面入口使用，一个视图也可以组合多个服务。

业务模块依赖 SDK 的公开接口，不在组件里散落 HTTP 调用或 Tauri API。模块间依靠公开对象和命令协作，不直接修改对方 store。

状态按以下方式分开：

| 状态 | 归属 |
| --- | --- |
| 项目内容、工作集、选择实体、任务、成果 | 后端权威状态 |
| API 查询页、对象属性、任务快照 | TanStack Query 缓存 |
| 当前功能、焦点对象、滚动位置、临时交互 | 按项目 / 工具会话隔离的前端状态 |
| 工作区布局、显示偏好 | 布局与偏好服务 |
| 尚在编辑的工具参数 | 前端草稿；通过草稿服务恢复保存，不能混作已提交任务参数 |

大型选择由后端保存，前端持有 SelectionRef、版本和摘要。少量交互更新可以即时反馈，但以服务端确认的修订为准。项目切换时，响应和缓存键必须包含项目及结果身份，避免晚到响应进入另一个项目。

TanStack Query 负责异步数据获取、缓存和同步：[官方说明](https://tanstack.com/query/latest/docs/framework/react/overview)。查询键包含项目、输入版本及结果身份。昂贵查询不能无条件套用窗口聚焦重取和无限页缓存等默认行为，需要明确失效与预算策略：[默认行为文档](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)。

图片列表的数据分页和控件虚拟化分别处理；仅渲染可见项并不能限制已经加载到内存的数据页。媒体 URL、解码图片和预取队列都需要释放与字节上限。

基础控件提供键盘、焦点和交互行为，视觉变量集中管理。其余审美与页面布局不在本草案中固定。

## 10. 工程规范与有价值的验证

- TypeScript strict；跨模块只使用公开导出；不使用 any 绕开公共契约。
- Rust 错误统一映射为公共错误码；业务与 I/O 失败返回可处理的 Result。
- ESLint / 格式检查、rustfmt / Clippy、类型检查进入统一检查入口。
- 依赖方向通过包导入规则及 crate 依赖限制检查，不依赖口头约定。
- pnpm-lock、Cargo.lock、后续 Python 锁文件纳入版本控制。精确工具与库版本在实现和兼容验证时锁定。
- 日志关联项目、请求、任务和执行尝试；大批量诊断写日志文件，界面订阅摘要。
- 数据库访问与迁移集中管理。模块不能自行创建旁路数据库或修改另一个模块的私有表。
- 每项较难逆转的决定有简短 ADR，记录问题、选择、代价和重新评估条件。

优先验证真实边界：跨项目隔离、跨数据湖身份、契约生成一致性、分页与选择稳定性、取消与重试、执行器崩溃、结果发布中断、项目迁移及来源繁忙。性能验证记录数据规模、冷热缓存、内存与查询条件；测试素材构造与完整数据湖压测分别执行。

## 11. 第一阶段工程落地范围

第一阶段建立可验证的底座：

1. pnpm / Cargo workspace、检查入口与契约生成。
2. Tauri 最小窗口、本机引擎启动发现、版本握手和连接恢复。
3. 项目创建、打开、关闭和重新打开；应用注册表与项目数据库分离。
4. 一个真实的只读 Danbooru 适配器探测及一个小型模拟来源；验证来源身份与多来源引用。
5. 一条有界的数据查询和媒体读取通路，以及后端选择引用。
6. 一个有可控中断点的演示执行器；验证输入固定、任务持久化、恢复和成果发布。

这里的顺序是工程依赖顺序，不是用户工作流。正式视觉设计与具体模型功能通过后续独立工作扩展。

以上为设计阶段的工程计划。当前开发启动、构建和数据接入的验证情况以 foundation-status.md 及实际检查记录为准。
