# Astra 审查后的并发与生命周期修复计划

日期：2026-09-29。评估基线：`58ad70bf772b1138d54cee3a4e9f5ce96274fb7b`。状态：R1 已完成并通过阶段验收；R2–R4 待实施。

依据：[本机复核与验证边界](../verification/2026-09-29-astra-review-validation.md)。原审查六项缺陷均成立，读写位置迁移缺口记为 G1。R1 的实现及验证见[查询可靠性验收](../verification/2026-09-29-astra-r1-query-reliability.md)，许可与无状态分页方案见 [0045](../decisions/0045-query-admission-and-merge-progress.md)。

## 阶段划分

| 阶段 | 内容 | 相对改动规模与风险 | 交付门槛 |
| --- | --- | --- | --- |
| R1 查询可靠性 | F1 许可复用、F2 多湖分页进展 | 中；F1 较集中，F2 涉及续页协议和顺序正确性 | 饱和并发可退出，慢湖与稀疏命中不会无进展循环或漏项 |
| R2 更新任务生命周期 | 先 F5 原子命令，随后 F3 调度与 F4 回收，一起验收 | 较高；跨执行锁、控制事务、归档回放及暂存所有权 | 取消不可复活、空闲槽公平补位、终止任务最终释放暂存 |
| R3 恢复入口 | R3A F6 运行环境修复；R3B G1 读写位置迁移 | R3A 中，R3B 较高；分成两个可独立验收的交付 | 配置失败可正常修复；迁移中断后可恢复且不回退数据版本 |
| R4 组合验收与文档 | 真实规模副本负载、指标、版本与数据所有权说明、针对性职责提取 | 测量工作为主；重构规模由结果决定 | 关键并发场景通过，资源范围和性能边界有实测记录 |

这里的规模是依赖与风险判断，不是已验证的工时估算。继续沿用在线版本化发布、固定成员封存、归档优先恢复和各自的执行器，不改变它们的基本职责。

R1 和 R2 是下一轮长期无人值守多湖运行前的主要门槛。R3A 是新配置或运行环境修复前的门槛；R3B 是搬盘、换目录前的门槛。R4 用来确认组合负载，而不是替代前面确定性缺陷的修复。

## R1：许可所有权与分页进展

### 实施范围

1. 将“调用方已经准入”和“需要自行准入”变成明确接口。`assets()`、创建视图及相应失败回收沿调用链复用已有 `SourceRead`；检查 `retain`、`retain_created`、`retain_job`、`release_versions` 等入口的实际持有关系。不能只改一个读取端点或扩大 Index 预算。
2. 让取消和截止时间贯穿续租。除了资源排队，复核 `studio-sources/src/query/mod.rs` 中版本续租打开 Snapshot 时使用独立取消信号及 `None` 截止时间的路径。
3. 定义可恢复的多路合并检查点：已扫描到哪里、哪些头部尚未输出、哪些湖已耗尽、对应什么冻结版本。预算退出后这些信息必须足以推进下一页，同时保持全局排序和精确一次输出。
4. 为续页状态确定大小上限、期限、版本和失效行为。当前限制是 1–8 个来源、每页最多 128 项、游标最多 8192 字节，不能不加估算地把所有预取页塞入游标。

可以选择有界服务端合并状态，也可以调整无状态分页的预算边界；方案必须先证明不丢弃全部有效工作、不会越过未消费命中。单纯提高 200 ms、轮换首湖、只改变游标字符串、或把 after 推到丢弃的缓冲末端，均不能作为正确性证明。

### 验收

- 4 个请求在真实默认 Index 配额下同步进入续租、创建视图和失败清理，不形成嵌套等待环；取消、到期、正常退出后活动数和预留量归零。
- 1、2、3、8 个湖，慢首湖/慢中间湖、连续空命中扫描、工作量预算耗尽、最终尾页均可完成。逻辑扫描或合并状态单调推进；不以“游标字符串发生变化”代替进展证明。
- asset/post ID 升降序、相同帖子 ID 分属不同湖、重复命中和版本保留期间的更新均保持正确排序，无重复、无漏项。
- 翻页重试、游标过期和引擎重启给出明确结果或可识别的重新开始要求，不能静默切换查询范围。

## R2：任务命令、执行交接与资源回收

### 先修 F5，再启用自动回收

恢复、重试、重放必须在写事务内重新读取并验证状态/执行代次，用条件更新领取新的执行意图。items 重置、cursor 修改和 execution 增量属于同一个原子命令；失败时不能只回滚部分副作用。普通 `update()` 现有的 paused/cancelled 保护应保留，并检查其他直接 SQL 的状态写入入口。

执行锁和数据库事务的取得顺序需要统一，避免“检查未运行 → 旧执行者重新领取 → 新命令覆盖”的窗口。已确认的取消应保持关闭；重复取消幂等，重复恢复不会无意增加多次执行。不要只把字符串状态改成枚举。

### 联合实现 F3 与 F4

调度先取得每个可执行湖的队首，再对湖应用候选限制和活动槽位；已有活动湖不能占满全局候选前缀。保留单湖执行互斥，并明确重试到期、异常退出与长期队首任务的调度规则。修复的最低保证是：存在空闲槽时其他可执行湖能在下一轮参与，而不是承诺抢占正在运行的长任务。

取消需要持久记录清理责任，形成以下可恢复的过程：停止发放新工作 → 等待下载/编码/发布执行者退出 → 核对已接受归档及控制回执 → 回收经过验证的任务暂存 → 记录清理完成。业务上的 cancelled 可以先成立，但不能被当作已经没有执行者或已经释放磁盘的证明。

暂停、服务退出、可重试失败和待人工复核仍保留可恢复文件；终止取消有独立回收策略。清理只能作用于确认归属的任务目录和文件，检查路径逃逸/重解析点，不删除湖的 updates 总目录或已归档对象。崩溃、文件占用和重复执行清理均须可恢复；旧取消任务也需要补做核对与回收。

F5 是 F4 的安全依赖：若旧恢复命令仍可把 cancelled 写回 queued，自动清理就可能与重新启动的执行者竞争。两者应在同一阶段完成后共同验收。

### 验收

- 固定“恢复读旧值 → 取消提交 → 恢复写入”的交错，resume/retry/replay 均不能覆盖取消；取消与任务领取、结束、归档回放同样有确定性测试。
- A 积压 100/1000 项且保持活动，B/C 仍能利用空闲槽；加入第 4 湖、到期重试和异常 Future，不导致全局调度退出或永久遮挡。
- 取消发生于下载中、编码中、发布前、归档已提交但控制回执未完成时，均无丢失正式数据；所有执行者退出后可回收的暂存归零。
- 清理各步骤注入崩溃后重启可继续；暂停任务仍能断点恢复。用 10 MiB 配额、8 MiB 旧取消暂存和 4 MiB 新请求验证跨湖背压最终解除。

## R3A：运行环境可修复

将“更换解释器”和“迁移状态目录”拆成不同操作。解释器更换应保留控制库、任务身份、凭据和湖登记；状态目录迁移仍需独立协议，不能顺带放开。

候选运行环境先做无抓取副作用的依赖、worker 版本和协议握手，验证通过后再原子保存；切换失败恢复上一可用配置，并处理配置所属标记的生命周期。并发配置请求和监督器不得分别启动不同代 worker。

增加由 Rust 控制器提供的健康结果，使 worker 不可运行时仍能展示已保存配置、最近错误、修复入口与受控的重试状态。保留有界、脱敏启动日志，避免每两秒无声失败。UI 在已配置和配置损坏两种情况下都应允许更换解释器。

验收覆盖无效可执行文件、缺少依赖、协议不匹配、启动后立即退出、状态目录冲突、进程正在停止和成功替换。错误路径不丢失已有任务；故障信息不得泄漏站点凭据。

## R3B：读写位置协调迁移

先定义一个显式迁移命令和持久迁移记录，再串联当前两套位置登记。流程至少包括：

1. 冻结该湖的新写入领取，等待实际执行者退出，记录任务与归档/发布检查点。
2. 核对新位置的 library_id、site、generation、归档提交进度、served_seq 及保留版本边界，确认不是同身份的过旧副本；核对暂存和固定输入等仍被引用的文件。
3. 分步更新读侧 source_locations、写侧 lakes、发布反向链接和控制器所属标记，并标记每一步完成情况；更新打开项目的可见位置。
4. 每个中断点都能重新进入并补完，或明确回退到一致的旧状态，完成后才允许恢复写任务。

不要求跨多个数据库和 JSON 文件实现一个大事务，但要求中间态可识别、幂等和可恢复。仅有 `library_id` 一致不足以接受一个落后的备份副本。

验收覆盖旧路径已离线、只移动媒体、只移动索引、两者同时移动、跨盘、过旧副本、身份错误、迁移中途崩溃，以及任务/项目仍引用旧版本。迁移完成后浏览、更新、固定输入准备与发布均使用同一位置集合。

## R4：组合验证和维护性收尾

在真实规模副本上组合运行“三湖更新 + 前台浏览 + 固定结果构建 + 评审”，先记录单项基线，再测组合负载。评审使用离线/模拟回执验证调度；真实付费请求另按具体任务范围执行。

记录前台延迟 p50/p95/p99、最老可执行任务等待时间、Index 排队/许可占用、各湖发布滞后、暂存实际/预留字节、进程内存和数据库事务等待。结果必须附硬件、数据量、冷热缓存和并发设置。性能门槛基于这些场景定义，不把 200 ms 合并软预算直接当作真实查询 SLO。

先完成取消回收，再测 `Resources._actual()` 的目录扫描和锁内开销，决定是否引入账本与周期对账。大文件拆分围绕本轮已经稳定的任务命令、配置管理、查询续页职责进行；没有测量依据时不追加缓存或更换数据库。

同步 README 的 v13 升级描述，复核 members.sqlite、project.sqlite、evaluation.sqlite 的权威性与备份恢复说明，并写明 Rust 和 Python 各项资源预算的作用范围。同步 API/SDK 与 UI 的故障和迁移入口说明。

## 各阶段的工程检查

将本次一次性缺陷探针转成正式回归测试，并让断言要求修复后的行为。耦合功能构建完成后统一运行检查，不以一次局部绿灯代表阶段完成。

- 公共 DTO 或路由变化：运行 `pnpm contracts`，不手改生成文件。
- 每个实现阶段：运行 `pnpm check`。
- 任务、存储或协议变化：运行 `pnpm test:integration`，补上对应故障注入与恢复场景。
- UI 配置/迁移阶段：执行真实入口的成功和失败操作验证。
- 阶段验收记录保留提交、测试命令、结果、数据规模与未覆盖边界；必要本机证据归档后清理本阶段临时目录。

优先完成 R1，再完成 R2；R3A、R3B 分别交付，最后进行 R4。无需先做一轮全项目机械拆文件。
