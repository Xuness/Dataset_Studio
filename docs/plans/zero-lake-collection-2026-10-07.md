# 从空目录建湖与按需采集

日期：2026-10-07。实施基线为 `b95808c`，承接现有三站更新与 Pixiv 采集。目标是在没有任何既有数据湖、发行归档或外部 Store checkout 的情况下，经 Studio 创建湖并采集用户选择的数据，保留现有高效归档和在线读取架构。

## 约束

- 三种 Booru 保持归档 1 / 在线 2，Pixiv 保持归档 2 / 在线 3。图片对象、来源资产、元数据观察、远端覆盖与任务进度分别表达。
- 按需采集是普通用户路径，不以全站元数据扫描为前置条件。ID、作者或角色标签、Tag 的包含/任选/排除条件可以限制采集范围。
- 远端选一个或多个正向条件获取候选，完整组合条件在同一条元数据观察上求值。不能把不同时间的 Tag 命中 ID 集合直接求交后当作当前结果。
- 有效响应的完整元数据可以入湖，只有匹配的条目进入媒体队列。复用保留原观察时间，失败或预算耗尽不能写成完整覆盖。
- 新帖全站水位、限定查询的扫描检查点、图片下载进度、归档提交序号独立。稀疏采集不会推进全站水位。
- 跨任务复用要求查询条件、边界、访问条件与新鲜度相容；只拥有部分帖子不构成完整查询覆盖。
- 测试使用隔离数据和模拟源站，按影响范围执行。正式湖、真实凭据、既有任务和 `.local/dev` 不参与测试。阶段通过后提交本地 Git。

## 验收重点

1. 每个来源从两个空目录创建、登记、挂载；Booru 不建立旧生产者索引。非空目录、身份冲突、初始化中断、重复提交均有明确行为。
2. 从没有任何帖子开始按 ID/标签或 Pixiv 作者/作品采集，浏览与详情能读取已发布结果。仅元数据任务随后可以只下载选定子集。
3. `A AND B` 后运行 `A AND C`，在接受原扫描新鲜度时复用 A；`B AND C` 不能误用不完整 B 覆盖。并发、暂停/恢复与源站错误不造成遗漏或虚假完成。
4. 不连续 ID、不同观察时间、旧帖标签变化、访问条件变化和媒体失败分别验证；全站新帖水位不受限定采集影响。
5. 记录 API 请求、复用条目与媒体下载，验证重复请求实际减少。维持批量封存、有界查询和已有版本保留协议。
