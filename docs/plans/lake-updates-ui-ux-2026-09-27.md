# 三站数据湖更新：前端 UI / UX 规划

日期：2026-09-27。状态：**已按用户确认推进并接入 A/B/C**，具体实现与边界见 [ADR 0039](../decisions/0039-lake-update-workbench.md)及[验收记录](../verification/2026-09-27-lake-updates-ui.md)。没有制作交互草图。核对基线为 Studio `31b5dc7`、Danbooru-Store `991613b`；下文保留设计依据，最终交付以验收记录为准。

承接[增量更新计划](lake-incremental-updates-2026-09-26.md)、[后端验收](../verification/2026-09-27-lake-updates-backend.md)与[现有工作台设计](../design/frontend-workbench.md)。图片默认保存策略继续待定，原有 Danbooru 自动化不在本次前端规划中变更。

## 1. 产品入口与对象

建议新增应用级“数据湖”编辑器，与“资料浏览 / 美学排序 / 计算工具”并列。它在未打开项目时也可进入；切换、关闭项目或关闭此编辑器标签，不改变更新任务的执行。

主要入口是“工具 → 数据湖”，同时在“打开功能”和起始页提供入口。已有项目中的来源行增加“管理此数据湖更新”，定位同一全局湖及其任务。依据 `library_id` 复用登记，不能把同一湖在不同项目中的来源 ID 当作多个更新目标。登记为可更新湖与添加为项目来源是两项操作；登记校验湖身份及路径，不复制或重新迁移数据。

三个业务对象分别表达：

- **数据湖**：持久来源、连接状态、更新任务和已验证范围，所有项目共享。
- **更新任务**：一次已冻结的范围与图片策略，可暂停、续跑及处理异常。
- **定时计划**：产生任务的规则，编辑规则不改变已经创建的任务。

“项目资源”继续承载项目工作集与成果。任务的来源项目可记录为来源说明，但更新任务不归该项目生命周期管理。

关闭标签与退出应用分别处理：运行器由引擎监督，不能承诺退出 Studio 后一定继续抓取。界面显示运行器状态；退出时说明当前托管运行将停止并保留检查点，重新启动后依照后端状态恢复。以后如加入常驻服务，应作为单独能力接入。

## 2. 延续 UE 5 工作台

沿用现有 Starship 风格主题、编辑器标签、`Workbench` 停靠区和 `WorkbenchDialog`。以选中对象驱动详情，操作属于当前对象；参数按分类折叠。这与 Epic 的[编辑器、大纲和详情职责](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-editor-interface)相对应。高级选项使用[属性分类与逐级展开](https://dev.epicgames.com/documentation/en-us/unreal-engine/reordering-and-hiding-properties-in-details-panel-customizations-in-unreal-engine)的逻辑。

| 区域           | 内容与职责                                                                              |
| -------------- | --------------------------------------------------------------------------------------- |
| 顶部编辑器标签 | “数据湖”作为一个全局工作标签，保存上次选中的湖、任务、视图和布局                        |
| 上下文工具栏   | 新建更新、适用于当前任务的暂停/继续等操作，以及“更新任务 / 定时计划”视图切换            |
| 左侧数据湖大纲 | 全部数据湖、Danbooru、Yandere、Gelbooru；显示简短的执行或待处理标记。点击湖限定中央列表 |
| 中央主工作区   | 默认是任务表格；切换到定时计划后是计划表格。选中行驱动右侧详情                          |
| 右侧详情       | 随湖、任务、计划显示属性分组；任务配置只读，计划修改有明确保存按钮                      |
| 底部活动抽屉   | 项目任务和数据湖更新分组，查看活动摘要与待处理问题；从任意编辑器定位到对应任务          |
| 状态栏         | 紧凑显示运行数、待处理数和连接状态，点击展开抽屉；不会弹出遮挡图片的持续进度窗口        |

中央任务表格的首批列为：任务、数据湖、范围、状态/阶段、已处理、待处理、开始时间。速率、下载量、详细计数和冻结策略放到详情，避免横向堆叠。任务名称先从范围生成，例如“补充新帖”或“创建日期 09-20 至 09-26”；不把尚不存在的可编辑任务名称当成后端能力。

左侧建议默认 260 px，右侧沿用工作台约 380 px，均可调宽、隐藏、移动和恢复。继承紧凑工具栏、细分隔线、凹陷输入框、2–3 px 控件圆角与中性深灰层级。蓝色表达活动和选择；警告与错误同时有文字和图标。所有面板使用公共主题角色，不建立第二套颜色常量。

首要基准继续为 **2560×1440、100% 缩放**，并检查实际可用窗口高度；150% 缩放与较窄窗口通过收起面板和列优先级适配。首轮复用现有停靠菜单，不增加拖拽停靠或独立浮窗。

## 3. 新建更新的操作流程

点击“新建更新”打开一张分组配置表，依次填写目标、范围、内容和执行方式。高频字段直接可见，预算与站点特定条件折叠。草稿不会触发抓取；关闭后可恢复非敏感草稿。

### 目标与范围

| 用户意图                   | 呈现与准确语义                                                                             |
| -------------------------- | ------------------------------------------------------------------------------------------ |
| 补充新帖                   | 从明确基线继续获取新 ID；首次没有已验证基线时要求选择起点。HF 最大 ID 不能当作完整覆盖证明 |
| 刷新已有记录               | 按本地已有帖子刷新，可限制 ID 范围或“上次获取早于”某时刻                                   |
| 补齐缺图                   | 以本地缺图记录为范围，重新确认元数据和图片地址后补抓                                       |
| 指定日期                   | 明确选择“创建日期”或“最后修改时间”；选择一天或一段时间，显示时区                           |
| 指定 ID                    | 单帖、列表或区间；列表按当前湖解释，不能把不同站点的同一个 ID 当作同帖                     |
| 从选择/工作集/查询结果更新 | 后续接入固定成员引用，按来源拆分为独立任务；见实施阶段 C                                   |

Yandere 的变更序号放在高级范围中，仅在能力允许时出现。“最后修改时间”说明它筛选当前 API 记录的最后修改时间，不能承诺还原某天发生过的全部历史修改。

日期控件按用户习惯包含所选的最后一天，提交时换算为该时区下一天起点的半开区间；ID 区间也统一处理界面包含末端与后端排除末端的差异。摘要写出准确边界。不支持的条件给出原因，避免提交后才把不支持解释成空结果。

可以同时选择多湖。公共设置可复用，但每湖保留独立基线和能力检查；ID 列表须分别填写。提交摘要按湖列出最终定义，依次创建独立任务。每湖保存稳定幂等键，某湖创建失败后只重试未成功的创建；已有任务不能重复创建。不宣称多湖创建是一个原子操作。

### 图片策略

明确选择“仅元数据 / 保存原图 / WebP（最长边 2048，质量 95）”。默认策略尚未确定，因此首轮表单要求明确选择，而不是依赖接口省略值。可记住用户已确认的草稿，但不能把它表述为已确定的全局默认。

另设“已有图片如何处理”：保留可复用版本、只补缺图；或补入与所选策略匹配的版本。选择原图不会隐式重抓所有 HF WebP。“允许备用图片”单独解释，仅在策略支持时可用；原图任务不允许用备用图冒充原图。

### 执行与检查

先完成本地字段校验，再通过现有 preview 接口核对标准化定义和扫描方式；摘要显示来源、时间/ID 范围、图片策略和候选数量是否已知。它目前不提供可信的全范围耗时或磁盘用量估算，不显示虚假的精确 ETA。

主动作是“开始更新”；预约和周期计划复用同一范围/策略编辑器，并明确创建的是任务还是计划。网络响应不确定时保留提交键，查询或重试同一提交，不生成新键重复派发。

高级预算用“每轮最多扫描页数 / 处理记录数”解释。预算耗尽意味着暂停等待续跑，不意味着该范围已完成。

## 4. 进度、异常与热更新体验

元数据进度与图片进度分别显示。已下载不等于已发布；只有有可靠分母的局部工作才显示百分比。未知总量显示“已扫描、已匹配、已保存、待处理”等计数和当前阶段，不用 ID 跨度计算图片完成率。旧任务没有遥测时显示未提供，不用零填补。

| 情况                        | 呈现与操作                                                           |
| --------------------------- | -------------------------------------------------------------------- |
| 排队 / 正在运行             | 当前阶段、帖子或文件进度；运行中提供暂停                             |
| 已暂停                      | 展示原因、已保留进度，提供继续；预算暂停使用普通提示                 |
| 等待重试                    | 原因与下次尝试时间，必要时提供立即重试                               |
| 等待空间 / 凭据             | 直接定位到存储信息或凭据设置；任务进度保留                           |
| 需要检查                    | 按问题类型查看有界记录，提供适用的处理动作                           |
| 已完成但有未获取项          | 显示已完成范围与未获取数量，能进入问题列表；不能只显示绿色“全部成功” |
| 已取消                      | 明确只停止后续工作，已发布数据仍可使用；再次执行创建新任务           |
| 引擎断开 / 运行器无近期心跳 | 显示最后更新时间与状态未知，避免把陈旧速率或状态当作实时值           |

暂停/取消区分“请求已接受”和“在途批次已经结束”；前端不能仅凭按钮回执声称磁盘已经停止写入。需要按后端确认状态更新提示。

任务详情按“执行状态 / 范围与策略 / 已验证范围 / 问题”分组。重试从源站重新获取失败项；“使用已保存响应重新解析”放在高级操作中。当前接口是任务级重试，首版不能伪装成支持任意选中若干项重试。记录未返回不自动标为已删除。

覆盖信息先展示任务级范围和边界。HF 导入的已有记录、API 已确认范围、图片缺口、尚未验证的范围分开表达；暂不制作宣称全湖完整性的覆盖率或日历。没有覆盖证明不等于没有数据。

更新时保留资料浏览的当前图片、滚动位置、固定结果和选择。沿用现有“数据湖已有更新”提示，由用户点击读取新版本；后台发布不自动重置网格、抢焦点或重建项目查询。显式刷新时尽量恢复图片身份锚点，无法恢复时说明位置变化。

底部活动抽屉复用视觉组件，但数据湖任务与项目计算任务各自保留真实协议和状态。待处理问题可按需打开；不为每批数据发布弹通知。

## 5. 设置、计划与服务边界

凭据进入“设置 → 数据湖 API”，与当前 LLM 的“API 与模型”区分。显示“已保存 / 未配置”，连接检测另行显示结果和时间；已保存不能等同于当前连接正常。Yandere 当前使用匿名方式。密钥输入只用于替换，不回填、不进入草稿或诊断；清除使用明确操作。

湖的图片目录与在线目录在详情中只读展示。运行环境与控制目录配置放到高级设置或未配置时的引导，普通更新表单不要求用户理解 Python 路径、SQLite 水位或恢复日志。

定时计划中央表格展示湖、更新内容、首次/下次执行、间隔、启用状态和最近任务。使用明确的“保存”和启用开关，显示并发修订冲突。计划默认不启用，已有 Codex 自动化也不能显示成新调度器管理的计划。

首版兑现现有能力：单次预约、固定间隔。`every_seconds=86400` 表达每 24 小时，不等于任意时区下的日历“每天某时刻”。若后续要求跨夏令时的每天固定时刻，先补完整日历调度协议；“每天抓前一天”也需要执行时解析相对日期，不能重复提交同一固定日期范围。

## 6. 现有基础与接入前需补齐的接口

现有 `EditorTabs`、主功能渲染、`Tasks` 与 `TaskActivity` 都受项目存在条件控制；`ModuleContext.projectId` 必填。应在宿主明确应用级与项目级功能上下文，保留已有项目模块约束，不能塞入空项目 ID 规避类型。全局布局和非敏感草稿复用应用偏好服务；浏览和工作集状态留在原项目会话。

前端功能模块只调用公开 SDK/UI；网络继续归 SDK，文件选择/打开等本机能力归 platform。范围标准化、能力规则、任务状态文案集中处理，不散落在各表单。

| 当前核对结果                                                       | 设计所需补充                                                                                        |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| jobs 按随机任务 ID 分页，没有按湖、状态或时间过滤                  | 后端增加稳定的时间排序游标及湖/状态过滤，避免前端只在已加载页中假筛选或假排序                       |
| status 没有全局活动计数，jobs 首页不能代表所有运行任务             | 增加活动及待处理摘要、有限活动列表；状态栏不遍历完整历史                                            |
| items 只有帖子 ID 分页                                             | 增加状态/问题类型过滤及摘要，直接定位稀疏失败项                                                     |
| pause/cancel 改变控制状态，在途执行可能尚未退出                    | 明确请求状态、执行确认或等价的在途信息，用真实停止边界驱动提示                                      |
| preview 多数范围的数量未知，只有基本扫描方式                       | 如实呈现未知；增强预估属于另行测量，不作为开始更新的强制全范围扫描                                  |
| inputs 支持分块 ID/SHA，尚无项目成员引用到封存输入的完整服务端桥接 | 工作集/全查询入口由后台固定版本并流式生成输入，带准备进度和恢复；不能让浏览器下载百万成员再逐个上传 |
| 计划支持固定间隔，coverage 是单任务记录                            | 先呈现对应能力；日历调度、相对日期与全湖覆盖汇总不靠前端推断                                        |

新增筛选和摘要应读取持久计数或有索引查询，保持有界分页。无需每秒开启大量短 RPC：共享应用级订阅，活动页面建议约 2 秒更新，隐藏或空闲时退避，终态停止高频详情查询；断开期间保留最后快照并标记陈旧。实施时按运行器 RPC 成本调整节奏，不新增全湖扫描。

相关源码：`apps/desktop/src/app/App.tsx`、`EditorTabs.tsx`、`workspaceState.ts`；`packages/ui/src/modules.ts`、`Workbench.tsx`；`packages/client/src/lakeUpdates.ts`；`crates/studio-protocol/src/lake_updates.rs`。Store 对应 `updates/state.py`、`__main__.py`、`runner.py`。这里列出的是接入边界，不表示这些前端补充已经实现。

## 7. 建议实施顺序

| 阶段                    | 连贯交付                                                                                          | 验收重点                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| A：全局工作台与可靠读取 | 应用级入口、三湖大纲、任务/详情布局、状态摘要、凭据设置；一起补齐时间分页、筛选和活动摘要         | 无项目可打开；切换项目不丢状态；近期任务和稀疏异常能直接找到；全局摘要准确     |
| B：手动更新完整闭环     | 同一范围/策略表单、预检、多湖独立提交、进度、暂停/继续/取消、任务级重试与重新解析、浏览新版本提示 | 幂等与部分提交恢复；状态/进度准确；日期/ID 边界正确；三湖后台更新时持续浏览    |
| C：计划与项目范围联动   | 单次/周期计划、修订处理、固定成员后台准备、选择/工作集/查询结果入口和统一活动抽屉完善             | 相对日期限制明确；超大输入不进浏览器内存；多来源完整映射；重启及关闭项目可恢复 |

阶段 A/B 联系紧密，适合一次构建后统一验收；C 基于同一编辑器和任务闭环扩展。每阶段交付可用操作链，不按几个按钮分别开发和测试。

验证覆盖：2560×1440 和缩放/窄窗布局、键盘及焦点、面板隐藏/恢复、旧会话兼容、无项目与跨项目、三站能力差异、未知总量、陈旧遥测、稀疏失败筛选、多湖部分提交、暂停安全边界、凭据错误、空间不足、预算续跑、网络中断、草稿恢复、计划修订与引擎重启。沿用 `pnpm check`；公共 DTO/路由变更先生成 contracts，任务/协议变更运行集成测试。

UI 验收优先使用隔离湖和模拟服务，完成后再按明确小范围验收三湖真实链路，不通过 UI 测试启动全量补抓或新的每日计划。性能验收区分列表/详情热读取、冷图片与更新吞吐，不能把任务列表刷新当作整个浏览体验的替代指标。

## 8. 讨论后再确定

推荐以全局“数据湖”编辑器和任务列表作为默认入口；三湖状态通过大纲及所选湖详情表达。首轮保留现有面板密度与停靠方式。

图片默认策略、首次补充新帖的起点以及实际定时时刻仍由后续使用决定。界面通过显式策略、起点与计划配置表达这些选择，没有替用户选择默认值或启用正式计划。
