## 已执行的架构与协议检查

- pnpm check：通过，包含类型、ESLint/依赖边界、契约漂移、格式、Clippy、149 项 Rust 测试和 SDK 检查。
- pnpm test:integration：17 组通过，使用隔离引擎、合成来源和本机 mock。
- 新增的一次性审查探针：6 种供应商/协议组合，均通过 prepare、generate、stream 的 16 图交错编号/图片顺序与 JSON Schema 参数转发检查；使用同一张合成 1 像素 PNG，不测试视觉质量。
- 探针确认：即使要求 JSON Schema，上游返回普通文本时，基础层仍以文本结果返回；它没有替业务解析排序。已完成的 invocation ID 可以再次发往上游；它不是持久账单幂等键。LLM 路由可以接受 2 MiB 输入，超过 16 MiB 的序列化内容被拒绝。
- 源码审查与少量生产元数据只读核查覆盖了主要链路；未进行真实百万图评审、长时间内存压测或新统计方法质量验证，也未将历史浏览性能当作该次审查性能测量。
- 该次审查没有发现基线测试失败；发现的是新功能接入前必须处理的边界和已有的扩展债务。不能因此宣称整个项目没有其它缺陷。

## 已执行的存储微基准

独立 Rust 探针固定使用 rusqlite 0.40.2 / libsqlite3-sys 0.38.2，与项目依赖一致，实际运行 SQLite 3.53.2。Release 构建，在 D 盘的专用临时文件上运行 WAL + FULL，未关闭同步换取速度。

每个场景预置 100 万候选，启动 100 个提交线程；每个线程等待提交确认后立刻提交下一份模拟结果，没有模型推理等待。另有 4 个读线程，每约 10 ms 发起一次有索引的 64 行分页查询。单场景写入 10,000 份结果，每份包含约 8 KiB 占位响应、16 条成员关系及 16 次候选摘要更新。

| 场景                         | 结果写入速度 | 提交确认 P95，含队列 | 分页读取 P95 | 写事务数 |
| ---------------------------- | -----------: | -------------------: | -----------: | -------: |
| 一份结果一事务               |  364.3 份/秒 |             317.7 ms |      1.76 ms |   10,000 |
| 最多合并 16 份已有结果一事务 |  618.8 份/秒 |             199.7 ms |      1.79 ms |      625 |

两场景均无读取错误，结果数、16 图成员数、总曝光增量及关闭后重开计数一致，quick_check=ok。观察到的 WAL 峰值分别约 4.91 MiB 和 12.71 MiB。后者不是硬上限，也不能外推为任意长读负载下的上限。

这里的“16 份结果”是最多 16 个 API 结果合并提交，每个 API 结果各对应 16 张图。写入队列容量为 256，100 个提交者最多产生约 100 个待处理结果；只合并已到达结果，不等待单个结果凑满一批。

这是一组饱和到达、热缓存条件下的存储微基准，不是现有产品任务执行器的实测：未包含真实 HTTP、图片读写、业务解析、统计拟合、请求领取/租约/费用状态迁移、断电、长期碎片或数百万历史返回。每个场景只有 1 万份结果，并未把 100 万图各评审 4 次。它支持继续采用 SQLite 的工程判断，不承诺正式系统也能达到同样吞吐。

聚合数据已保存到 [evidence-summary.json](evidence-summary.json) 的 storage_probe；原始报告、日志和探针源码位于下方本机证据目录。首次运行通过存储检查后，在测试文件辅助文件清理断言处失败；修正最终重开方式后两场景完整通过。该测试夹具问题与产品数据无关，早期日志也已保留。

## 建议的实施顺序与验收标准

1. 架构准备：固定观测与成果契约，拆分任务执行/恢复策略，明确付费证据归属、输入快照及短事务发布边界。先处理与新功能直接耦合的代码，维持旧工作集、缓存、排序和恢复回归。
2. 统计与 Prompt 试验：建立人工参与的分层样本和本地模拟器，比较均衡采样/主动采样、并列解释、输入规格和候选估计器。全量稳定性为主要指标，顶级漏检和中段分离为分层指标。模型调用另行选择端点及预算，本轮未执行。
3. 端到端第一版：新增“美学排序”入口，从 1 万图规模验证固定候选、16 图评审、Rating 隔离、跨年联系、账本恢复、全量榜单、保护池及结果工作集派生。完整打通相关模块后统一验证，不以“能发出 API 请求”作为交付完成。
4. 多轮与复核：模型独立榜单、父快照选择、Top 百分比/区间/冲突集合、强模型复评、人工裁决、复评证据和费用统计。
5. 扩容：先用合成/重放证据做 10 万、100 万到 500 万对象的调度和存储压测，再逐级扩大真实模型调用。性能数据合格之后再考虑按 Rating 或阶段拆分账本与计算，不提前引入分布式依赖。

工程验收包括：在发送前、上游已受理但本地未保存、响应已保存但未更新统计、成果发布中四类中断点恢复；接受证据不重复计数；暂停与取消可解释；无效/拒绝不当作低质量；来源更新不改变冻结分组；工作集成员绑定确切快照；保存百万成员时其它项目写入和交互的等待时间可观测；磁盘满、额度不足、限流和图片解码失败有明确状态。

容量验收记录 RSS 峰值、在途请求体/解码字节、队列深度、数据库与 WAL 增长、写锁等待、首屏/翻页 P95、恢复时间、拟合时长与临时空间。具体通过阈值须按本机资源和试点基线确定，不在缺少测量时拍一个百万图 SLA。

统计验收除了整体秩相关，还需检查各质量分段尤其是中段近邻的一致性、分位段迁移、跨年校准、连通性、展示顺序敏感性、顶级候选召回与模型分歧。整体相关系数可能被头尾明显差异掩盖。模拟真值、真人偏好、强模型判断和算法重放稳定性分别汇报，不互相冒充。
