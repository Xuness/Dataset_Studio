## 当前代码的支持与缺口

- 项目库已经使用 WAL、synchronous=FULL、单写连接和独立读连接，基础方向适合本机持久数据。[lib.rs:77](../../../crates/studio-storage/src/lib.rs#L77)
- 排名工作集保存会从获取写锁开始，持续处理成员直到整笔事务提交。任务输入固定也存在同类长事务。数据库文件再快，评审结果仍需要等待同一个写锁。[ranking.rs:164](../../../crates/studio-storage/src/ranking.rs#L164)、[job_scopes.rs:212](../../../crates/studio-storage/src/job_scopes.rs#L212)
- 读池最多保留 4 个空闲连接，这不是“最多 4 个活跃读者”。已有重查询另有资源控制；新增评审查询仍应明确限制活跃读连接和并行重查询。[read_pool.rs:16](../../../crates/studio-storage/src/read_pool.rs#L16)
- WAL 同一文件仍只有一个写者；长读事务可能阻止 checkpoint 完成。现有 journal_size_limit=32 MiB 不是运行期间 WAL 大小的硬上限。需要监测 WAL 大小、checkpoint 进度、读事务年龄和写入排队时间。[SQLite WAL](https://sqlite.org/wal.html)、[journal_size_limit](https://sqlite.org/pragma.html#pragma_journal_size_limit)
- 当前 LLM 单连接并发配置上限为 32，全局活动/等待容量为 128。单供应商跑到 100 个在途请求需要扩展这些设置，并同时加入全局上传带宽、准备字节、在途字节和供应商配额控制。[http.rs:10](../../../crates/studio-llm/src/transport/http.rs#L10)、[limits.rs:20](../../../crates/studio-llm/src/transport/limits.rs#L20)
- 当前调用快照包含完整 messages，远端调用还会生成 JSON 请求体。若直接序列化整个调用结果落库，内联图片可能随快照反复保存。评审账本需要自己的持久格式，只记录图片引用、哈希、配置版本与模型输出。[inference.rs:79](../../../crates/studio-domain/src/llm/inference.rs#L79)、[runtime.rs:236](../../../crates/studio-llm/src/runtime.rs#L236)

## 现有图片读取边界

审查基线中的 Danbooru `read_many` 每批最多 16 个对象，总读取上限为 64 MiB，并按数据包路径和偏移排序。现有预览的单图源字节上限也为 64 MiB；缩略图长边限制在 96–1600 像素，输出 JPEG quality 86。这些是当前预览路径的规则，还没有被验证为审美评审的最佳输入规格。[danbooru.rs:300](../../../crates/studio-sources/src/danbooru.rs#L300)、[lib.rs:172](../../../crates/studio-sources/src/lib.rs#L172)

评审图片变体需要固定尺寸、缩放、压缩、透明背景、方向、色彩及多帧处理策略。缓存键包含资产内容和完整变换版本，记录实际发送字节的哈希；需要精确保留输入字节时，使用独立容量规划的去重文件存储。

物理读取可以对一个有界待执行窗口预取和按偏移合并，再恢复原定组批与展示顺序。不能因磁盘文件相邻而长期把同一批图片封闭比较；扩大预取窗口也不能绕过现有读取和解码预算。

## 推荐的数据归属

| 数据                                                      | 建议位置                          | 写入与读取方式                                   |
| --------------------------------------------------------- | --------------------------------- | ------------------------------------------------ |
| 项目、评审计划目录、工作集及成果引用                      | 现有 project.sqlite               | 低频控制状态；继续治理大成员长事务               |
| 固定阶段配置、批次、attempt、原始输出、接受证据及费用记录 | 项目内独立 evaluation.sqlite      | 专用写入线程、短事务、唯一约束与持久事件序号     |
| 调度摘要、统计中间状态、处理水位                          | 独立可重放投影或状态库            | 消费已提交证据后更新；重拟合不占评审账本写锁     |
| 用户浏览和派生工作集所依据的排名                          | 不可变 ranking-snapshot 文件      | 有索引的分页；新版本发布后显式切换               |
| 图片变体                                                  | 独立受容量管理的文件缓存/证据存储 | 资产内容和变换规格去重；不重复塞进每条数据库记录 |

第一版可以每个评审计划拥有一份评审账本；不为每个请求创建一个数据库。Rating 本来独立，后续确有写入瓶颈时可按 Rating/阶段分区，但分库不能消除同一物理磁盘的 I/O 竞争，仍需统一资源预算。

原始付费结果和接受证据属于项目权威数据，必须备份和保护引用；统计状态可以由它们重建。统计重放失败不应重新请求模型。

不同数据库之间不假设有原子提交。评审账本同时提交结果和待同步事件，项目目录/统计投影按序号幂等更新。界面展示“已落盘结果”和“排名已处理到的水位”，不把投影暂时落后误报为结果丢失。正式成果沿用可恢复文件发布与目录登记机制。

## 高频写入的具体约束

API 协程通过有界队列提交结果，数据库写连接由一个专用线程持有；同步 SQL 不占异步运行时线程。每批按条数、字节和执行耗时预算约束事务，优先处理付费返回结果。接收者必须在 COMMIT 成功后才能确认“结果已持久保存”；入内存队列不等于完成。

写队列同时限制条数和总字节。排队接近上限时停止领取新的远端任务，保留正在返回的请求的接收/写入额度。磁盘空间不足、写入错误或 checkpoint 堵塞需要停止派发，不能一边无限积压 RAM 一边继续购买 API 调用。

账本保留 WAL + FULL。NORMAL 在 WAL 下可以在断电或系统崩溃后回滚近期已提交事务，因此不适合作为付费结果默认的提速手段。任何持久保证仍以操作系统及存储设备兑现同步语义为前提。[SQLite synchronous](https://sqlite.org/pragma.html#pragma_synchronous)

发送前先持久记录尝试；返回后先保存原始输出，再进行可重试的业务解析和统计应用。同一接受证据用持久唯一键防重复计入。上游已执行、本地尚未保存时仍有不可避免的结果不明窗口；数据库设计不能代替上游的账单幂等保证。

长时间导出/拟合不在热库持有一个读事务读完整个百万规模历史。使用不可变接受序号的截止水位，有界读取追加证据，或读取已发布文件。备份使用 SQLite Backup API 等一致备份路径；跨多个库的项目备份同时记录应用水位，不能只复制正在使用的主 .sqlite 文件。[SQLite Backup API](https://www.sqlite.org/backup.html)

## WebP 的实测大小与 40 Mbps 约束

只读访问当前图片湖 catalog.sqlite，使用 2,048 个确定性的 SHA 阈值索引探针，取相邻对象并去重；EXPLAIN 确认使用主键查找，没有 ORDER BY RANDOM() 或全湖扫描。未读图片字节、未传输图片，统计仅基于存储索引记录。该方法是分散近似样本，既不是全库精确分布，也不是最终候选工作集的严格均匀抽样。

| 样本指标 |                        大小 |
| -------- | --------------------------: |
| 样本数   | 2,048；stored_ext 均为 webp |
| 平均     |                   250.7 KiB |
| 中位数   |                   195.6 KiB |
| P95      |                   624.7 KiB |
| P99      |                 1,088.2 KiB |
| 最大     |                 1,660.7 KiB |

WebP 已经在减小文件体积，但不能据此假设上传不构成瓶颈。还要检查最终发出去的 MIME、尺寸和字节数。现有 thumbnail 函数会解码后转为质量 86 的 JPEG，不应直接将浏览预览链作为美学评审输入。[lib.rs:172](../../../crates/studio-sources/src/lib.rs#L172)

以样本平均大小原样内联上传估算：每批 16 图约 3.92 MiB 二进制，base64 后约 5.22 MiB。40 Mbps 的理论速率是 5 MB/s；暂按 70% 的持续带宽预算，即 28 Mbps / 3.5 MB/s，每批上传约 1.56 秒，可持续发送约 0.64 批/秒或 38 批/分钟。这是算术估算，不是实际网络测速，尚未计提示文本、HTTP/TLS、失败重试与限流。

| 平均每图大小 | 16 图 base64 体积 | 28 Mbps 下每批上传时间 | 30 秒平均请求周转对应的在途数量 | 180 秒平均请求周转对应的在途数量 |
| ------------ | ----------------: | ---------------------: | ------------------------------: | -------------------------------: |
| 64 KiB       |          1.33 MiB |                0.40 秒 |                           约 75 |                           约 451 |
| 128 KiB      |          2.67 MiB |                0.80 秒 |                           约 38 |                           约 225 |
| 256 KiB      |          5.33 MiB |                1.60 秒 |                           约 19 |                           约 113 |
| 512 KiB      |         10.67 MiB |                3.20 秒 |                            约 9 |                            约 56 |

在途数量按“带宽所允许的平均发送率 × 请求周转时间”估算，不是推荐立刻启用几百并发。实际还受账户 RPM/TPM、超时、图像 token、CPU、内存及模型能力约束。100 个在途请求完全可能成立，但如果模型 20–30 秒就返回、图片仍接近 250 KiB，继续增加并发主要会延长上传等待；如果推理需要 2–3 分钟，较多在途请求有助于覆盖等待时间。

若 100 万图各曝光 4 次、每次都重复内联上传，按当前样本平均估算，图片 base64 总量约 1.25 TiB；28 Mbps 下仅这部分传输约 109 小时。真实候选大小可能不同，模型等待可与上传重叠，因此不能简单把所有阶段耗时相加。减少重复上传或建立合适的评审图片规格，可能比进一步提高数据库插入速度带来更大的收益。

## 图片管线应独立限流

```mermaid
flowchart LR
    A[待执行批次：仅图片引用] --> B[有界读图与变体缓存]
    B --> C[有界编码与请求体准备]
    C --> D[全局上传带宽与字节预算]
    D --> E[供应商调用与等待模型]
    E --> F[有界结果提交队列]
    F --> G[独立评审账本]
    G --> H[异步统计与排名快照]
```

至少分开管理读图并发、解码/编码内存、已准备请求体字节、正在上传的数量/速率、等待模型的在途请求数、以及结果落盘积压。100 个等待模型的请求不要求同时进行 100 套读图和编码。

按样本平均，100 份 base64 请求体单份副本就约 522 MiB；计划、原生 JSON、序列化缓冲和解码图像还可能产生额外占用。这只是请求体算术，不是本轮测到的 RSS。当前输入内容限制 16 MiB，批次准备必须根据实际编码字节提前检查，不能只按 16 张和平均大小放行。

先复用符合模型格式和尺寸要求的 WebP；需要变换时按固定、可审计的规格生成评审变体。目标大小必须结合审美判断质量试验，不能为了追求 100 并发把影响质量判断的细节压掉。记录输入规格和哈希，避免不同规格的结果被无条件混为一套证据。

本地缓存可以减少重复读图和编码，但每次发送 data URL 时仍会重复上传。远端支持文件引用时，应增加按供应商/账户、资产哈希和变体版本管理的文件上传与引用缓存，处理有效期、权限、额度、重传和回收；不预先把全部百万图片一次性上传。现有 Gemini 适配器能编码已经准备好的文件 URI，但没有负责上传和生命周期管理。[gemini.rs:18](../../../crates/studio-llm/src/protocols/gemini.rs#L18)

Gemini 官方文档提供图片文件复用方式，Files API 文件默认在 48 小时后删除；是否适用于实际选用的模型/端点还需验证。文件引用降低重复传输不等于模型图片输入免计费，也不能将某一家供应商的文件 ID 直接用于另一家。[图片输入文档](https://ai.google.dev/gemini-api/docs/image-understanding)、[Files API](https://ai.google.dev/gemini-api/docs/files)

## 何时选择 PostgreSQL

单机、单引擎控制、可排队的小事务，是独立 SQLite 评审库的合理起点。需要多台机器直接共享调度与写入、多个独立写入服务，或贴近实际模式的压测显示串行写者无法满足延迟/积压目标时，再选择 PostgreSQL 评审后端。SQLite 官方也将无法排队的多写者场景列为客户端/服务器数据库的适用条件。[SQLite 适用场景](https://sqlite.org/whentouse.html)

在 application 层定义评审仓储接口，使评审数据库可以独立替换，现有 project.sqlite 不必随之整体迁移。PostgreSQL 会引入服务部署、认证、备份和项目迁移方式的变化；它也不能解决 40 Mbps 上行或图片重复传输。

下一阶段应以独立账本、异步统计投影、不可变榜单、字节背压和上传预算为同一组基础工程。完整验收再加入实际图片准备、真实端点的小预算样本、100 个结果同时返回的突发、磁盘变慢、进程中断，以及带宽限制下的长时间运行。本轮结论保留在容量方向判断，不把微基准成绩当作已完成的生产能力。
