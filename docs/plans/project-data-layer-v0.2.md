# 下一阶段计划：项目数据层

状态：本次收敛范围已实现并完成本机验收。结果见 [0.2 验证记录](../verification-project-data-layer-v0.2.md)，读取和升级边界见 [架构决定](../decisions/0002-project-metadata-layer.md)。

日期：2026-09-07。

## 目标

让项目中的数据具备可供各工具共同使用的身份、元数据与版本依据。数据湖作为整体接入，查询、组织和处理均围绕项目中的数据对象展开。

以下顺序是工程建设的优先级。用户可以自由选择工具、组合功能和安排自己的工作顺序。

## 整体优先级

| 优先级 | 建设内容 | 预期价值 |
| --- | --- | --- |
| 1 | 项目格式升级与一致备份 | 增加功能时保留已有项目、选择、工作集和成果 |
| 2 | 数据对象与元数据服务 | 明确图片内容、来源条目、历史观察和派生结果的关系 |
| 3 | 查询结果与作用范围 | 使用结果引用支持跨页选择、全部结果选择及排除项 |
| 4 | 功能模块与算子注册 | 统一声明入口、参数、输入、输出及运行和恢复能力 |

性能验证贯穿各阶段。先记录真实索引的查询耗时、冷暖缓存表现和内存，再据此发展持久预览缓存、预取、取消与调度策略。

## 本次实施范围

本次收敛到一个可验收的版本：

**项目升级机制 + Danbooru 元数据只读接入 + 简单元数据检查模块。**

完整查询结果引用、批量筛选、公式工具、模型工具和通用算子注册体系后续分别实施。本次接口应为这些能力保留清晰接入点。

### A. 项目升级机制

迁移对象是应用自己的项目文件与数据库。

- 建立明确的项目数据库版本和迁移记录。
- 从已有 v1 项目平稳升级，保持项目 ID、来源引用、选择、工作集、任务、事件和成果关联。
- 升级前使用 SQLite 一致备份机制，包含已提交的 WAL 内容；验证备份有效性。
- 数据库迁移在事务中进行。失败时保留可用的原状态和恢复材料，并提供明确错误。
- 处理重复打开、重复迁移、未知未来版本与已有项目锁。
- 项目清单与数据库版本分别管理，说明两者的兼容关系。
- 新建项目直接使用当前模式；已有项目通过同一版本机制打开。

### B. 数据对象与元数据只读服务

先检查当前数据湖的表、索引、关联和读取版本边界，用少量真实样本验证后落实接口。

- 保留现有储存对象身份及工作集成员；把图片内容、来源条目和元数据观察分别表达。
- 根据储存对象查到相关来源记录及观察，明确一对多、多对多和缺失关系。
- 相同内容的多次观察不自动当作多张图片；多条来源记录也不隐式压成唯一真相。
- 返回带来源和类型说明的常用字段，例如标签、评级、尺寸、来源地址和时间。
- 区分来源给出的尺寸和实际存储图片尺寸，未确认的数据保持未知。
- 提供读取版本及观察身份；数据更新、来源忙碌、缺失和不支持分别返回明确状态。
- 原始元数据按需读取并设定分页或大小边界，避免默认加载大字段。
- 使用只读连接与可证明的读取会话。单凭 CURRENT、generation 或相同水位不宣称取得历史快照。
- 先检查查询计划和样本成本；若原索引缺少高效关联，在应用侧考虑可重建索引或缓存，保持现有归档只读。
- 新工程自行管理需要的运行依赖，不依赖归档 runtime 中的 Python 环境。

跨数据湖公共字段遵循统一语义，来源特有字段保留命名空间。SDK 和功能模块不直接读取数据库文件。

### C. 元数据检查模块

利用现有 Photoshop 风格基础框架，增加一个实际可用的检查入口。

- 对当前项目中的焦点对象检查元数据。
- 展示常用字段、来源记录和观察依据；多个候选关联可辨认和切换。
- 页面切换、元数据加载和查看其他记录，不隐式改变项目选择或任务输入。
- 加载、缺失、来源不可用、版本变化和错误均有清楚反馈。
- 数据经过公开 SDK 与生成契约访问；视图与数据获取逻辑分开。
- 保留现有浏览、工作集和任务能力。

具体构图与视觉细节可继续迭代，不在本计划中固化。

## 验收标准

### 项目升级

1. 使用真实 v1 模式的测试项目，覆盖非空选择、工作集、来源、任务与事件。
2. 升级后逐项验证成员、身份、数量、关联及成果文件。
3. 验证重复打开不重复迁移，备份可独立读取和检查。
4. 注入迁移失败，验证事务回滚与恢复材料。
5. 未知未来版本明确拒绝；项目独占写入规则继续有效。

### 元数据服务

1. 用已知答案的小型夹具验证关联、缺失、重复内容、多次观察及分页边界。
2. 来源字段与返回值一致，字段来源和版本能够解释。
3. 验证来源更新、忙碌、不可用、无效引用及跨项目访问边界。
4. 真实 Danbooru 使用少量只读样本验证完整调用链并记录耗时与资源限制。
5. 不把小样本正确性验证表述为千万级全量性能已经通过。

### 前端与工程

1. 在实际 Tauri 开发窗口中完成元数据查看与错误状态验证。
2. 现有项目创建、来源管理、选择、工作集和可恢复任务继续工作。
3. 生成契约、类型检查、模块依赖检查、Rust 检查和相关测试通过。
4. 开发启动脚本与热更新继续可用；不构建发布版或安装包。
5. 日志写入 .local/logs，报告与截图使用 .local 下的专用目录。
6. 更新实现状态、验证记录与使用说明，完成可追踪的本地 Git 提交。

## 实施步骤

1. 只读审计现有项目格式与 Danbooru 元数据关联、索引和版本边界。
2. 使用隔离的验证运行目录建立 v1 夹具和迁移测试，避免未经验证的热重载直接升级当前开发项目。
3. 实现并验证升级机制。
4. 实现元数据领域模型、来源能力与 API，生成 SDK 契约。
5. 接入元数据检查模块。
6. 完成真实只读样本、原生窗口和回归验证，记录实际边界。

范围调整必须基于读取成本、数据语义或运行验证等具体证据，并在本文及实现状态中说明。

## 本轮落实情况

- A：项目数据库 v1→v2 的一致备份、事务迁移、账本、回滚、重复打开和未来版本拒绝已完成；真实开发项目升级后逐项一致。
- B：增加独立 MetadataAdapter，保留存储对象身份，按页返回来源记录、历史观察、类型化字段与原始 JSON。使用应用管理的 DuckDB DLL，数据湖只读。
- C：属性面板增加元数据检查，支持记录和观察切换、分页、字段依据、版本信息及明确错误状态。检查操作不改变选择或任务输入。
- 成本决定：真实索引没有 SHA 反向 ART 索引，但四个位置的投影查询可用于本次单对象检查；本轮未建设应用侧全湖反向索引。当前数据不用于宣称全量性能通过。
- 已知边界：真实存储尺寸仍显示未检查；跨库读取不是历史快照；复杂查询、结果引用、算子注册、公式和模型工具保持后续范围。
