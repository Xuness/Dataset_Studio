# Pixiv 后端与数据湖契约 v1

创建日期：2026-10-02。定稿日期：2026-10-03。状态：设计基线已用于阶段 1–3 实现。本文及附带 SQL、JSON 保留设计期版本；实际实现调整见 [ADR 0052](../../../decisions/0052-pixiv-collections-and-canonical-media.md)，运行证据见[阶段验收](../../../verification/2026-10-03-pixiv-stages-1-3.md)。生产 API 以 Rust DTO 生成的 OpenAPI 为准。

按已确认的方向新增独立 Pixiv 数据湖，沿用统一归档和后台架构。常规内部选择在本契约中确定，前端页面继续暂缓。

## 三份契约

1. [数据关系与 schema](data-model.md)：身份、记录字段、归档格式、在线投影、查询与旧湖兼容。
2. [写入与恢复](publication-recovery.md)：结果收据、批次、检查点、发布水位、恢复与资源回收。
3. [后端任务与读取接口](backend-api.md)：任务范围、状态、凭据、路由、DTO、错误和分页。

配套文件：[归档日志 SQL](journal-v2.sql)、[在线库 SQL](online-v3.sql)、[控制库增量 SQL](control-v8-additions.sql)、[JSON Schema](contract-schema.json)、[正反例](examples.json)。JSON 文件是设计期契约，不替代由 Rust DTO 生成的 Studio OpenAPI。运行 schema 随 `services/lake-worker` 打包。

[隔离校验记录](verification.md)：45 项数据与恢复模型检查、17 组 API 正反例通过；实际采集与生产实现的验收边界另行列明。

## 已确定的选择

- 新湖采用统一归档格式 2、在线格式 3；控制库由当前版本 7 增量升级到 8。旧湖继续使用归档 1 和在线 2，新读取端同时支持两代。实现前若其他工作已占用迁移编号，只顺延迁移编号，不复用已执行迁移。
- 工作集图片身份保持 `source_id + 文件 SHA`。作品、媒体位置、媒体观察和来源资产记录各自有身份；相同字节的多页仍保留多条来源关系。
- 原文及关系全部进入不可变归档。在线库、检索索引和运行队列不能成为唯一事实来源。
- 初版采用有限的快照采集任务：作者目录补全、显式作品验证、受深度和预算约束的作者扩展。后续定期更新通过新快照任务执行，不在一个任务中无限改变已捕获的作品与媒体清单。
- 单个受控 lake-worker 进程协调旧更新和新采集；复用 Python 环境、设备预算、编码配方、Windows 凭据保护和 Rust 生命周期控制。新任务使用独立类型及控制表。
- 浏览器是可选登录助手。后台使用 Cookie 会话；凭据保存、账号身份验证、目标内容可见性分别表达。
- 验证任务默认示例保存原件、不扩展作者；正式任务的保存配方和扩展范围是显式参数。没有修改三个旧来源的默认策略。
- 动画首版保存网页提供的帧包、帧时序及首帧封面，记录实际来源变体。完整动画播放和帧展开界面不属于本阶段。

## 与现有代码的接入点

| 现有位置                                                    | 实现时的工作                                                                 |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `services/lake-worker/src/studio_lake/library.py`           | 按归档版本分派，复用包写入与封存，增加格式 2 记录集和收据                    |
| `metadata.py`、`online*.py`、`archive_rebuild.py`           | 保留旧格式逻辑；增加新 schema、发布、版本回收及同规则重建                    |
| `updates/state.py`、`dispatch.py`、`locations.py`           | 新迁移、跨任务族调度、同湖写入和搬盘互斥；已有任务保持原义                   |
| `updates/credentials.py`、`image_policy.py`、资源与传输模块 | 抽取并复用明确端口；新来源不复用帖子 MD5 作为媒体身份的假设                  |
| 新 `studio_lake/collections` 与 `collectors/pixiv`          | 前者负责控制、收据和计划，后者负责网页请求与站点语义；CLI 与服务共用         |
| `studio-domain`、`studio-application`                       | 新增采集控制及作品成员读取端口，核心层不依赖 HTTP、SQLite 或 Tauri           |
| `studio-engine`、`studio-protocol`、`packages/client`       | 新路由、DTO 和 SDK；复用同一个运行器控制对象，执行 `pnpm contracts` 生成接口 |
| `studio-sources` 的注册、规范湖、元数据及查询模块           | 识别 Pixiv 与在线 3，保留旧版读取，扩展逐页关联和精确标签语义                |
| 位置重连、迁移和维护工具                                    | 同步支持新版本与记录集，不能只改日常读取而遗漏恢复入口                       |

旧 `/v1/lake-updates/*` 仍只返回其支持的 Booru 任务、湖与凭据；不能直接将 Pixiv 行塞进旧 `LakeUpdateSite` 枚举响应。公共来源注册表则增加 `kind="pixiv"`。新服务状态和任务使用 `/v1/source-collections/*`。

## 一致性检查与实施验收

设计校验使用空白 SQLite 和虚构样例：建表、外键、版本区间、重复文件多来源、跨作品错误绑定、旧控制库增量升级、检查点重放、JSON 正反例及现有图片配方校验。检查不访问 Pixiv，不初始化真实湖，也不证明生产写入器的中断恢复已经实现。

实现验收还需实际验证 Python 写入、Rust 读取、源版本与缓存失效、真实登录和网页响应、完整归档重建、共享资源上限及三站回归。前端不是这轮验收的依赖。

实施顺序固定为：版本分派与小型湖读写 → 采集控制与 Pixiv 核心并行接入 → 后端接口贯通 → 真实小样本及恢复验证。所有关系与恢复规则以这三份契约为依据，避免在各模块内另立语义。
