# 契约二 写入与恢复

版本：1。定稿日期：2026-10-03。适用统一归档 2、在线 3 和采集控制 8。目标是在重试、暂停和中断时保留取得结果，并区分已下载、已归档与已发布。

## 权威与所有权

控制库保存任务意图、调度和当前执行所有权；不可变归档保存已采集事实及已确认检查点；在线库是归档的服务投影。控制库保留在现有共享状态根目录，不能混进图片湖。凭据只在受保护控制存储中。

每湖一个写入所有者和一个有序发布器。网络请求及编码不持有归档写入锁；封存和 journal 接受沿用同湖 writer/device 锁。搬盘准备、恢复和其他写入入口使用同一位置准入。

新控制表见 [control-v8-additions.sql](control-v8-additions.sql)，新库提交日志见 [journal-v2.sql](journal-v2.sql)。迁移控制库先取得既有初始化、运行器和执行锁，检查 application ID 与版本，事务完成后才启动新执行；旧控制表和暂停状态不变。

## 取得结果的收据

每次请求或文件取得先分配收据 UUID，并固定任务 ID、执行代次、claim token、输入指纹和解析/配方版本。收据及文件写在状态根下按湖、任务、claim 分隔的有界暂存中；路径不进入公共 API。

收据至少包含：

| 字段                                     | 规则                                                         |
| ---------------------------------------- | ------------------------------------------------------------ |
| `receipt_id`、`job_id`、`task_id`        | 稳定身份；同一结果重放不重新分配                             |
| `execution_epoch`、`claim_token`         | 首次提交时检查执行所有权，防止旧请求覆盖新执行               |
| `definition_sha256`、`input_fingerprint` | 核对固定任务定义、媒体清单及配方                             |
| 文件清单                                 | 暂存相对路径、长度、实际 SHA、原件或输出角色                 |
| 捕获与结果记录                           | 观察时间、非敏感上下文、原文、规范化事实和类型化结果         |
| 后续任务线索                             | 归档记录引用和固定 planner 版本，不保存任意 SQL 或可执行代码 |

文件先完成校验和持久写入，再原子写入收据。只有收据可靠保存，编码或其他依赖方才可使用该文件。断点文件沿用有效 Range/身份检查；远端内容变化时不得接在旧字节后面。

一次取得过程中的原件、编码结果、TAR 复制及未发布批次都计入相应预算。保留原件与否是任务保存策略，不能在空间紧张时静默改变。无法继续准入时进入资源等待，已取得数据保留。

## 批次与任务意图

批次 manifest 的正式形状见 [JSON Schema](contract-schema.json) 中 `BatchManifest`；[examples.json](examples.json) 只提供虚构形状样例，其哈希不是实际文件摘要。

`format_version=2`、`schema_set="canonical-media-v2"`。必需功能为 `captures-v1`、`work-media-v1`、`collection-replay-v1`。文件声明角色、schema、行数、字节和 SHA；读取端拒绝未知必需功能、越界路径和身份不符的批次。

每个任务首先写一个意图批次，包含 `collection_intent.json` 和空操作的 `collection_replay.json`。意图记录规范化定义、定义摘要及 `pixiv-plan-v1`；首个意图归档确认后才允许发出该任务的网络请求。之后 manifest 的 `source.intent_batch_id` 指向它，避免每批重复整份定义。

正常批次的去重键为 `H("collection-batch-v1", library_id, job_id, 排序后的receipt_id数组)`；意图批次使用 `H("collection-intent-v1", library_id, job_id, definition_sha256)`。批次 UUID 在封存意图第一次写入时固定；相同去重键对应不同 manifest 或文件摘要时进入 `needs_review`，不能覆盖旧结果。

JSON 任务意图和重放收据的元数据是有类型的控制证据。大目录、推荐集合和作品事实放入 Parquet，收据只引用快照或记录 ID，不能把几十万候选复制进单条控制消息。单批结果受发布条数和字节阈值限制。

## 重放收据与检查点

`collection_replay.json` 使用 `ReplayReceipt`：

- `task_outcomes`：本批确认的任务结果、执行代次、claim token、原因及记录引用。
- `checkpoint_advances`：流键、预期旧 revision、新 revision、下一个游标、是否结束及捕获引用。
- `discovery_snapshot_ids`：计划器可从归档确定性地产生候选的发现快照。
- `definition_sha256` 和 `receipt_ids`：绑定任务范围与已取得结果。

游标推进必须满足 `next_revision = expected_revision + 1`。同一批次对同一流最多推进一次；失败响应不得推进成功游标。列表页完成只证明该次返回已处理，`traversal_exhausted` 与全站或历史覆盖无关。

journal 在同一事务写入 commit、任务批次索引和检查点，检查旧 revision。去重键已经确认时先验证已有批次并返回原确认，不重新检查已经推进的游标。控制库里的检查点是这一确认的副本。

新队列只能由固定版本 planner 从已归档快照及固定定义产生。对已有作者、作品或任务合并执行，另外保存发现来源；不向已有任务增加新的依赖边。新依赖只指向后创建的子任务，避免关系图的环变成执行依赖的环。

## 提交顺序与独立发布

1. **Prepared**：暂存文件与收据可靠，outbox 保存意图路径和摘要；任务可以停在 `staged`。
2. **Archive committed**：写入器检查结果、引用、fence 与游标，封存文件，并在 journal 接受批次。取得固定 `archive_seq`。
3. **Control applied**：控制库在一个事务中登记 `collection_applied_batches`、更新结果与检查点、创建或合并候选任务。已确认的后续网络任务可开始，不等待在线发布。
4. **Published**：发布器按 journal 顺序应用批次，最后推进在线可见水位。
5. **Released**：outbox 同时满足控制已应用、发布已确认，且无在途消费者需要暂存后，回收可重建的临时数据。

第 3、4 步独立推进，所以 outbox 使用 `control_applied` 和 `published` 两个标记，不能用单个线性状态假装两者同步。在线发布积压超过预算时停止继续准入；不能无限增长归档与运行状态之间的距离。

尚未在线可见的父记录，通过收据中的批次及记录引用验证。写入器可以维护受积压预算限制的未发布后缀缓存；已有完整索引加该后缀用于对象查重。不得为新采集器重新建立一套长期整湖生产者索引。

控制应用按每湖 journal 顺序进行。相同批次重复应用先比较收据摘要，再返回已确认结果。不同批次试图以错误 revision 推进同一流时停止并核查；不把冲突转为“已经完成”。

## 在线发布与读取水位

发布开始时插入 `publications(state="preparing")`，使分块事实写入可以满足外键。逐块写事实及派生关系，与块进度同事务提交；每块依据不可变 manifest 指纹和已确认位置接续。

最后一个事务核对完整性、记录计数和变更，将 publication 标为 `published` 并推进 `online_state.served_seq`。所有读者使用固定水位，不能直接读取无过滤的事实表。

即使新批次已经把旧版本行的 `valid_until` 改为 N，水位仍为 N−1 的读者也继续看到旧行；新行的 `valid_from=N` 在完成前不可见。工作关联和媒体关联遵循同一规则，不会出现只发布一半页清单的状态。

增量发布与归档重建必须共用记录校验、当前选择和变更计算函数。重建读取固定连续 journal 前缀，写独立目录并检查 raw、对象定位、关系与当前绑定。重建成功不自动切换生产指针，换代和版本保留仍走既有位置与租约流程。

## 暂停 取消与旧执行

任务有 `desired_state` 和实际 `state`。暂停或取消首先停止新准入，已开始的执行到达可靠边界后才报告实际退出。`execution_active` 根据锁与在途执行报告，不能只根据状态名称猜测。

每次重新取得执行所有权增加 `execution_epoch`，每次任务领取有新的 claim token。首次接受未提交结果时核对二者。旧执行的暂存文件与新执行分开；迟到结果不能修改当前任务或覆盖新临时文件。

已经进入 journal 的批次在重放时按归档事实处理，不再因为当前执行代次变化而丢弃。重放可以补齐计数和确认，但不能把用户已暂停或取消的任务改回运行。取消不删除已归档事实；只有该任务独占、可安全回收的暂存参与清理。

## 失败与恢复矩阵

| 中断或冲突                  | 恢复规则                                                                         |
| --------------------------- | -------------------------------------------------------------------------------- |
| 网络完成但收据未可靠保存    | 该结果不算确认；验证可识别暂存，否则重新取得，不伪造完成                         |
| 收据已保存但尚未封存        | 校验身份及摘要，继续编码或封存                                                   |
| 批次已封存但 journal 未确认 | 同湖锁内核对并接纳相同批次；冲突保留证据                                         |
| journal 已确认但控制未应用  | 重放类型化收据，幂等创建候选和推进检查点                                         |
| 控制已应用但发布未完成      | 继续独立发布；新取数受积压额度约束                                               |
| 发布成功但确认响应丢失      | 根据 journal、publication 与已应用批次返回同一结果                               |
| 老 claim 迟到               | 不推进任务；保留受限暂存供恢复核对                                               |
| 来源媒体发生变化            | 固定媒体目标记 `source_changed` 缺口；后续新快照任务采集新版本，不静默改写原目标 |
| 认证失效                    | 暂停依赖会话的请求，保持目录与媒体进度；同账号恢复后续抓                         |
| 空间或预算耗尽              | 停止新准入，保留检查点和已取得数据，不计为远端下载失败                           |

控制库物理损坏或丢失与普通进程中断不同。意图和归档收据可用于重建已确认计划与进度，但凭据需要重新提供，未归档且无法验证的在途状态不能恢复为成功。恢复操作先检查旧运行器所有权，不以新建空控制库自动遗忘旧任务。
