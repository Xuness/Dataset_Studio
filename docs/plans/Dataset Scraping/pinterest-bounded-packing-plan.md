# Pinterest 有界物理组批方案

日期：2026-10-10。状态：方案已选定，尚未实现；本轮已经落地的故障修复见[审查修复验收](../../verification/2026-10-10-pinterest-production-review-fixes.md)。本文件不构成百万级生产验收。

## 已确认的问题

当前每个逻辑任务立即封存一个物理 Batch。Windows 隔离环境中，经正式 Runner 处理 100 个指定 Pin、100 张不同字节的静态图片，产生 201 个 segment 目录、1,403 个普通文件和 100 个 TAR。结束时暂存占用为零，深验证、独立重建和固定水位比较通过。这个结果证明文件数量放大；不证明容量盘吞吐，也没有证明在线发布存在全湖重扫。

归档接受与逻辑回执身份需要分离。后续采用“不可变逻辑回执 + 持久化组批计划 + 多回执物理批次”，保持 Pinterest 自己的事实、分页和覆盖语义。可以共享文件、TAR 和资源预留底层，不能通过 Pixiv 的作者或作品任务表达 Pinterest。

## 组批边界

第一版拟采用以下上限，并在实现时用资源准入约束收紧，不能超过现有单批 10,000 行和 32 MiB 元数据硬上限：

| 维度 | 拟采用界限 |
| --- | --- |
| 逻辑回执 | 64 个 |
| 事实行数 | 8,000 行，为对象和资产记录留出余量 |
| 规范元数据 | 24 MiB |
| 媒体字节 | 128 MiB，且不超过当前共享暂存可承诺的额度 |
| 等待时间 | 120 秒上限；无可执行前置工作、任务真正耗尽时提前提交 |

Pinterest 默认元数据请求速率为每秒 0.5 次，图片为每秒 1 次。不能直接照搬“1 秒或每次 15 秒时间片结束即封包”，否则合法的低速采集仍可能退化成一图一包。尚未组批的 prepared 回执须跨调度时间片保存；UI 分别显示已保存结果与已发布水位。时间片结束不等于结果丢弃，也不等于归档接受。

只合并同一作业、同一冻结定义、相容访问上下文中的独立结果。意图回执、旧版 prepared，以及同一分页流中有前后依赖的结果继续单独处理。合并同主键事实时，内容相同可以去重；内容不同必须报完整性错误。需要前序结果的后续任务仍只由已接受回执产生。

## 实施顺序

1. 增加 Pinterest 自有 outbox 和 batch-plan 控制表，使用新的控制版本、备份及升级锁。prepared 保存 receipt ID、task ID、claim、冻结输入指纹、结果哈希和媒体引用。冻结组员与 outbox 的 batch 映射在同一事务提交，恢复不能临时换一组成员。
2. 先实现新组批 envelope 的读取、严格校验与兼容迁移，再启用写入。通过新的格式/必需 feature 明确声明多回执语义；旧单回执归档保持原字节、路径、receipt ID 和历史 sequence。在线事实 schema 可复用时，不为组批改写 Pin、媒体或 SHA 身份；既有固定版本引用必须列入兼容验证。
3. 每个物理批次只生成一个媒体 TAR，以及每张非空事实表的一个 Parquet。回执成员清单与摘要进入不可变 manifest/replay。每个逻辑回执分别写入 journal 的 receipt 表，同一物理批次的控制回放在一个短事务中完成。
4. 将重放分页单位改为完整物理批次，或采用 `(sequence, receipt ordinal)` 游标。不能继续用 `seq > archive_seq LIMIT 128` 后逐回执推进 sequence，否则一个批次跨页时会跳过剩余回执。
5. 将已有下载预留原子合并为组批预留，覆盖所有源文件、共同 TAR、发布和回收。跨时间片的 prepared 文件仍进入实际磁盘统计。组批失败、暂停、取消、进程退出都需要可恢复的归属记录；不提前释放未来封包空间。

失败媒体的有界诊断与回收继续沿用本轮修复：失败回执接受后回收无消费者的坏文件；显式重试产生新 generation，并在新下载准入前处理旧代清理。需要调查样本时应另设有容量限制、可见的保留策略，不能默认把全部失败文件留在共享 spool 中。

## 启用前的验收条件

- 在冻结组员、写 TAR、seal、rename、journal 接受、逐回执控制回放、在线发布和清理边界注入中断；恢复后的事实和请求数符合各自边界，不丢成员、不重复发送已保存响应。
- 覆盖同批相同字节、同 URL 多绑定、旧 prepared、新旧物理批次混排，以及一个组批刚好跨重放分页边界的情况。
- 使用当前 100 Pin 基线做前后对照，再以有界合成工作集覆盖多批次、预算接续和跨时间片存活。记录目录/TAR/Parquet 数量、暂存峰值、物理写入量与重建时间，不将模拟网络时间称为源站吞吐。
- 在目标 Windows 与实际容量盘环境执行持续运行验证，覆盖共享额度竞争和暂停恢复；完成这些验证后再评估大规模无人值守下载。
