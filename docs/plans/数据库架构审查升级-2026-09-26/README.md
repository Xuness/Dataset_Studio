## P1：现有交互路径

1. 复核 `query_member_data` 的访问计划。增量关闭成员由 `affected` 的 `(source_id, asset_id)` 驱动；全量来源允许扫描其成员。新增成员沿用去重 stage 和既有区间复用。
2. 在单结果族有序发布条件下，分别累计关闭区间与插入区间：`new_count = latest_count - closed + inserted`。拒绝重复/错序发布；零变化保留旧修订；失败恢复不推进 family 水位。成员与计数仍在原子事务中提交，不在分块循环中随意增加 commit。
3. 草稿读取使用现有独立读取池，保存仍执行修订冲突检查。验证 writer 持有未提交修改时，读取及时返回旧提交。
4. 预览先在短锁内取得 pin/写入保留，再在锁外执行字节读取、哈希、暂存写入与 fsync；清理不能删除活跃读者或写者的文件。pin 释放仅更新状态，后续有界维护完成淘汰。清理/配额变更必须覆盖正在写入的情况，保持重启恢复与目录保护。
5. 分段记录等待、SQL 发布、缓存读取/哈希/写入/同步/清理耗时。默认日志避免逐图刷屏，诊断按需启用；不把一次微型实验外推为真实前端 p95。

P1 不改变正式湖格式、公共查询语义或 UI 翻页行为，不宣称已实现热更新。重型结果初次发布仍有大事务；其彻底隔离归 P3。

## P2：一湖热更新与选型

正式在线投影与新增数据湖缓存沿用用户指定的 SSD `F:\Dataset`，图片湖保留在 `E:\AI\AI_Dataset`。现有 Danbooru 索引实际位于 `D:\Dataset\Danbooru`；切换时显式列入迁移清单和空间估算，不默默移动既有索引。隔离代码测试仍按仓库约定使用 `.local/test-runs/`。

先写协议与 DDL 草案，再实现可运行原型。需明确：

- 一个服务可以管理多湖，每湖一条有序发布队列；Studio、CLI、自动任务共享所有权及提交协议。
- `archive_seq`、`served_seq`、`analysis_seq` 分别表示归档、在线可见、分析完成；媒体 pending/ready/unavailable 独立表达。下载和解码不持有数据库写事务。
- 三种读取：每请求最新已发布数据、固定浏览视图、固定成果。跨湖使用版本向量。过滤、排序、详情、帖子关联与字面 Tag 必须在同一视图解析。
- 游标引用真实保留版本；租约有期限和明确的过期反馈，永久成果引用单独管理。跨请求不保持长期 SQLite 读事务。新数据提示不会重置正在使用的视图。
- 字段变化集合区分 score、tags、关联与媒体内容，避免无关失效；按同一帖子/观察满足组合条件后再映射图片，不跨帖拼接条件。
- 精确 Tag 词典和倒排以持久整数键作基线；保持大小写、标点和非 U+0020 空白语义。CurrentPost 与 AnyObservation 分别验证。默认 FTS 分词不能替代该契约。

原型比较 SQLite WAL 在线投影与单进程 DuckDB 服务。测量对象、帖子、Tag 关系、观察历史与重复内容分布，而非只造 1,650 万整数。关注热门/稀有 Tag、负条件、多条件、不同排序、增量写放大、空间、WAL/checkpoint 和旧视图保留成本。基于结果定案；不预设把所有历史搬入 SQLite。

故障矩阵覆盖：新增、改 tags/score、同帖换图、同图多帖、metadata-only、缺图后补、重复重放、取消/重启、封存前后/投影中/发布后崩溃、磁盘满、保留视图下回收。只在隔离湖通过后推进真实迁移。

## P3：查询与迁移

日常查询返回有界页、下一页游标、`has_more`、`view_id`；总数允许未知/计算中/精确值。多湖有序流做有界合并；先定义跨湖排序和去重语义。保存工作集或导出固定用户正在看的视图，后台建立完整成果。

大成员构建与项目控制状态隔离。成果先封存、再用短事务登记引用；崩溃留下的孤儿可识别、可回收。不假设多个 WAL 文件的 ATTACH 写入具有整体原子性。

按湖取得一致基线 S，生成在线投影，重放 S+1 起的变化。对照 SHA/帖子浏览、详情、各类筛选、固定结果和排名消费者；记录切换/回退条件。catalog 在线定位、identity、browse、Rating 等旧职责逐项迁出并停止写入，在引用审计后回收。新旧路径共存必须有明确退出条件。

基础准备需求按“来源＋索引类型”合并目标版本，普通小查询不等待重分析准入。并发数由资源测量决定。

## P4：三站更新与媒体

逐站核实 API 的日期/ID/分页/鉴权/限流及删除信号。完整保留响应、未知字段、schema 和观测时间；HF/API 观察并存，演进 normalizer/capability 后才暴露新筛选字段，未知不填 0/false。

更新计划区分数据范围与执行时间：post 创建日期、远端更新时间、ID、工作集、条件范围；新增、元数据刷新、缺图补齐、失败重试与替换。冻结时区、区间边界与计划身份，记录覆盖缺口。今天补抓旧日期得到今天的观察，不伪造历史状态。

SSD 暂存有上限及背压，三站最终写同一 HDD 时共享设备预算。先采样小图编码尺寸与容量，再决定持久小图分片/封存格式；持久小图与可淘汰大预览分开管理。

## 验收与证据

公共 DTO/路由改变时运行 `pnpm contracts`；各阶段运行 `pnpm check`，存储/任务/协议改变另运行 `pnpm test:integration`。测试使用 `.local/test-runs/`，日志及完整测量保留 `.local/logs/`、`.local/reports/`。

性能目标暂定常见元数据 p95 ≤ 200 ms、已准备 SSD 小图首屏约 1 s，须按硬件、条件和并发情景验证。另记录 p99、队列等待、writer 占用、草稿保存、取消响应、WAL/历史/暂存增长。冷 HDD 原图、任意低选择性组合及全局分析独立报告。

依赖核验使用 Rust 实际链接的 `sqlite_version()` / `sqlite_source_id()`。SQLite 官方 [3.51.3 发布说明](https://sqlite.org/releaselog/3_51_3.html)记载 WAL-reset 修复；[WAL 文档](https://sqlite.org/wal.html)说明单写者、长期读取与跨文件提交边界。版本检查不等于已有数据库损坏诊断。
