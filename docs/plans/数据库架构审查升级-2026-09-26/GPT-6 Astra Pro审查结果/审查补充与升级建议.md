# Dataset Studio：源码复核补充与升级建议

审查日期：2026-09-26。依据：用户上传的 Studio 源码包和《Dataset Studio 数据库、交互读取与数据湖热更新审查》。这是一份独立的设计建议，不是已实施改造。

## 结论

原报告对主要问题的判断有源码依据：native DuckDB 直读的进程所有权限制、只接受最新版本而没有可持续读取的旧视图、基础准备与重查询的串行准入、交互筛选的全结果物化、项目写通道被发布长期占用。不能将这些都解释成“千万数据只能如此”。索引是正常数据结构；问题是过粗的失效与发布协议，以及将后台计算成本放进交互路径。

建议保留不可变图片批次、原文和观察历史，以及既有固定成员成果。优先验证统一在线投影，由每湖一个有序发布者维护。单机原型优先比较 SQLite WAL 在线库与单进程拥有 DuckDB 的服务方案，而不是直接把所有数据迁到另一种数据库。

## 范围限制

本次只有 Studio 仓库，没有 Danbooru-Store 的实现、正式数据湖、运行中的项目数据库，亦没有原报告提及的 coverage-manifest、runtime-inventory、concurrency-probe 等 JSON 证据。因此报告中的本机文件容量、三湖对象计数、Store 原地同步行为和当地并发实验只能作为报告陈述，不能声称本轮独立验证。

未执行完整 Rust 工程回归或 HTTP/UI 压测。隔离 SQL 实验使用 Python SQLite 3.46.1，不是 Studio 实际捆绑的 SQLite。数据库优化器版本变化可能改变执行计划；生产计划和延迟仍需在实际运行库验证。

## 额外发现一：增量发布仍可能按成员总量做工作

证据 E10、E11。`query_cache.rs:911` 的 UPDATE 从 family/source 的旧成员集合出发，再逐行判断 affected 与 matches 的相关 EXISTS。`:933` 又执行全 family 的有效成员 COUNT。`:874` 的项目 writer mutex 覆盖这些操作及单一事务。

隔离实验直接提取上传源码中的表、两个索引和 SQL。在 affected 始终只有一个资产且成员没有实际变化时，10,000、100,000、500,000 个成员对应原 UPDATE 约 130,000、1,300,000、6,500,000 条 VM 指令；计数约 70,000、700,000、3,500,000 条。原计划仅以 family/source 定位主表范围。

候选增量 UPDATE 以 affected 资产集合驱动主键定位，在该环境中变为 family/source/asset_id 完整前缀寻址。小型语义样例覆盖新增、删除、post_id 更换、NULL、未变化资产、另一来源和旧修订；结果与旧 SQL 相同。候选不是生产补丁，未验证全部来源变化、恢复和并发场景。

改进方向：按 affected 主键访问；保留未变化成员的区间复用；分别统计关闭区间数与新增区间数，在严格单族发布与幂等条件下维护 `新计数 = 旧计数 - 关闭数 + 新增数`。首次构建按封存的去重 stage 计数。不要把现在合并的 changed_members 当净增量。

## 额外发现二：暖预览也存在全局串行点

证据 E15、E16。`PreviewCache` 为 `Arc<Mutex<State>>`。`get()` 在同一把锁内执行查询、路径检查、文件读取、SHA 校验和 LRU UPDATE。`put()` 在同一把锁内执行写文件、sync_all、发布、登记和清理。CachePin 析构也可能持锁清理。

因此，冷缩略图的落盘与清理可能阻塞已命中 SSD 缓存的读取。这是明确的临界区边界，不是已测得的主要延迟来源。

改进方向：短临界区只保留必要状态操作；文件读取、哈希和暂存写入移到锁外；在安全 pin/open 协议下处理与删除的竞争；逐 key 合并请求；LRU 触碰适当批量化；清理转入受预算约束的后台任务。不能靠删除哈希校验、路径保护或 pin 来获得速度。

## 额外发现三：基础索引有第二个单工入口

证据 E06、E07、E18。除了 QueryBudget 单 active lease，SourceIndexes 还通过 `Semaphore::new(1)` 串行准备，查询调度器也等待当前构建完成再处理下一项。按 revision 创建准备任务，应考虑按“来源＋索引类型”合并目标版本，避免等待期间继续堆积已过时需求。

不要简单把所有并发数乘以三。先让日常小查询脱离重任务预算队列，再为后台同步设置有界批次、交互保留资源和物理设备 I/O 配额。

## 保留与收敛

保留：不可变 TAR 和原文归档、稳定的来源及图片身份、观察历史、现有独立读取池、版本化工作集成员、固定排名、独立 evaluation/registry、预览内容键，以及已有恢复与取消保护。

收敛：catalog、身份摘要、帖子浏览顺序、Rating 候选和常用查询字段所承担的在线职责。新的在线层必须接替对应旧读取路径，而不是永久多加第五套派生副本。

当前系统已经有增量更新、SHA/帖子键分页、媒体偏移读取、预取和取消。不要把它改造成每次复制全部成员、每次重打包图片或每次克隆完整 analysis.duckdb 的系统。

## 建议的在线职责

| 逻辑对象 | 职责 |
|---|---|
| assets / locations | 稳定图片身份、内容摘要、包偏移、本地字节属性和媒体就绪状态 |
| posts_current | 每来源帖子的常用当前投影，及对应观察版本引用 |
| post_versions / observations | 已发布的历史字段版本、原始响应引用、normalizer 语义 |
| post_asset_links | 同图多帖、换图关系及其有效区间 |
| tags / postings | 精确字面 Tag，按同一帖子或观察版本判断组合条件 |
| publication / changes | 完整可读水位、变化实体及字段、批次身份和幂等重放信息 |
| results / references | 固定成员及必要字段版本的成果引用、租约和回收约束 |

这是逻辑职责，不是“全部历史都复制到一张巨大 SQLite 表”的要求。当前投影走快速路径；近期浏览视图保留必要版本；任意历史分析可继续走归档与 DuckDB。

内部高扇出关联可以采用持久的整数 surrogate key，减少重复长字符串，但外部 `(source_id, asset_id)` 必须稳定。不能因跨站内容哈希相同就混淆来源语义。

## 三种读取语义

**实时模式**：每个请求读最新完整发布的版本；允许用户明确接受列表漂移，不需要无限保留历史。

**固定浏览视图**：进入筛选时获得每来源版本向量。分页、过滤、排序和详情使用同一视图；后续发布以提示方式出现，用户刷新才切换。需要真实历史字段/关联/Tag 可见性，不能只在 cursor 内放 seq。

**固定成果**：保存工作集、评审、排名或导出时，明确冻结成员，以及任务依赖的 observation_id 或字段快照。保存操作应固定当前视图，不能悄悄按最新库重新执行另一份查询。

短请求事务提供一次请求的一致性，但不能自动保留几小时后下一页的旧数据。不要用一个长期 SQLite 读事务承担浏览会话。版本租约需要上限和明确过期行为，永久成果引用与临时浏览保留分开。

## Tag 查询必须保留的语义

以同一观察记录满足所有条件后再映射图片。一个图片对应帖子 A 含 tag_x，帖子 B 含 tag_y，不等于存在一个帖子同时满足 tag_x AND tag_y。rating、score 和 tags 也不能从不同帖子拼接满足。现有 CurrentPost 与 AnyObservation 模式应分别保持。

原型至少比较词典＋关系倒排，以及必要时的压缩倒排。不得用默认全文分词悄悄改变下划线、括号、标点、大小写和字面 Tag 匹配。不能仅以“对象数 1,650 万”判断空间与查询难度；要测帖子数、Tag 关系数、观察历史数、热门/稀有词分布和单次变化集。

## 发布协议

网络请求、图片下载与解码不放在数据库写事务内。原文和媒体先以可恢复方式持久化，封存批次后再执行在线投影更新。单库发布者保证批次顺序，幂等地应用明确的 changed set，并将所有必要在线结构与 served_seq 一起提交。

archive_seq、served_seq、analysis_seq 表示不同完成阶段；图片 pending/ready/unavailable 状态另行表达。在线查询只依赖完整的 served_seq，不应被异步历史分析拖住。三个湖独立提交，以版本向量表达跨湖视图，不引入不必要的全局事务。

评分变化不得使内容缩略图失效，但评分排序或依赖评分的结果必须遵循自己的版本语义。字段变化记录用于精确判断受影响功能，不再为每个缓存创造一套互相追赶的“最新版本”。

## 交互与结果持久化

日常搜索返回 items、cursor、has_more、view_id；总数允许 unknown/后台计算，不用虚假的精确值。保存工作集、导出、评审与排名再建立固定成果。复杂低选择性查询和全局新排序可以退回后台任务，不承诺任意条件恒定耗时。

项目小型控制状态与大成员写入应隔离。可以把大结果构建放在独立结果存储，封存后短事务登记；也可以沿用现有修订结构进行不可见版本的分批构建，但必须先定义阶段状态、单族串行、读者可见条件和失败恢复。不能只把 32,768 条后面加 commit 就结束。

跨两个 SQLite WAL 文件的写入不能假定通过 ATTACH 自动成为整体原子事务。需要显式封存、登记、孤儿识别和回收协议。

## 媒体与资源

已有内容身份和 TAR 偏移读取应继续保留。统一固定缩略图规格及 renderer 版本，新入库图优先生成小图；旧湖按受控计划回填。应区分常用持久缩略图层与可淘汰的临时大预览，而不是把全湖准备寄托于有限 LRU。

全湖小图容量按实际编码采样估算，且需评估海量小文件的文件系统成本；可采用分片目录或封存预览包，不要默认把全部文件堆进单目录。先修暖缓存临界区，再评估冷盘读取、解码、预取和缓存预算。

三站抓取可并行，但向同一物理 HDD 写入时应有统一调度。下载先在 SSD 暂存并不意味着可以无限积压；必须设置空间上限和背压。

## 推进与验收

第一阶段先补分段观测，并处理预览锁、草稿读取池以及增量发布访问路径。记录排队、SQL、hash、fsync、WAL、物理盘 I/O，避免只测一次总耗时。

第二阶段用隔离的一湖实现完整发布/浏览小闭环。覆盖新增、改 tags/score、换图、同图多帖、metadata-only、缺图后补、重复重放、取消重启、发布中故障和旧视图回收。然后按真实关系规模放大测试。

第三阶段迁移在线查询及其消费者。稳定来源身份，取得一致基线 S，从 S+1 重放变化，对照旧新查询，按湖切换适配器；必要时为初始迁移安排维护窗口，不能把稳态免停机承诺偷换成迁移也绝不需窗口。旧索引待消费者迁移及成果引用检查后回收。

第四阶段接入 API 更新 UI 和调度。将目标数据范围与执行时间分开，支持 post 创建时间、远端更新时间、ID/工作集范围及操作种类；记录时区、冻结边界、重试缺口和覆盖状态。API 能力逐站核实。今天补抓某个旧日期的帖子，只能获得今天返回的观察，不能伪造当日历史。

Yandere/Gelbooru 还需要升级 normalizer/capability 契约：当前 profile 固定 HF 版本，保留 API 原始 JSON 不自动等于前端可查询新字段。缺失值不能补成 false/0；空页和未返回 ID 不能自动当删除。

候选验收目标可沿用报告中的常用元数据 p95 200ms 与已备 SSD 缩略图首屏约 1s，但这些是待测目标，不是已达性能。必须同时验证更新并发下的 p95/p99、草稿写延迟、取消响应、长期 WAL/历史/暂存增长和持续更新不反复回首页。
