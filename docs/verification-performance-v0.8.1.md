# 0.8.1 性能修复与验收

2026-09-10，北京时间。依据[性能排查报告](performance-metarecall-workset-v0.8.md)完成修复，已更新当前开发环境。项目数据库仍为 v8，现有排名成果可以直接读取。开发前端和桌面宿主保持开发模式，计算引擎实际使用 Release。

## 实测结果

| 现有排名成果，G 分级合格候选前 48 名 | HTTP 读取超过 30 秒 | **8.9 ms**；48 项分数及名次与原表一致 |
| 现有排名成果，G 分级合格候选，不限前 N | 原语句存在索引失配 | 主排名首屏 8.1 ms，补救排名首屏 8.9 ms |
| 现有成果，各分级前 48 名 | 原谓词无法按排名范围直接定位 | 主排名首屏 34 ms，匹配 192 项；补救排名首屏 15 ms |
| 同一份 122,529 项真实冻结输入，工作进程执行 | Debug 0.8.0：7.269 秒 | Release 0.8.1：1.479 秒，约 **4.92 倍** |

表中的首屏时间为返回首批对象或榜单行的 API 耗时，不是全部缩略图渲染完成时间。另取该工作集首项验证预览：66 ms 返回 42,267 字节 JPEG，成功解码为 288×360，命中已有缩略图缓存；请求的源文件读取预算为 2 MiB。

工作集首屏和榜单读取使用现有索引、操作系统缓存及应用环境，没有清空缓存；不是冷盘吞吐测试。冻结输入对照包含工作进程的输入哈希、资格检查、评分、名次、写入和索引，不包含范围固定、元数据投影、父进程完整校验及成果提交。对照逐项比较全部评分列、主排名、补救排名、入选通道和统计摘要，122,529 行全部一致。最终产物的这次对照每种构建各运行一次，不能据此推算千万级任务总耗时。

原先约 47 分 42 秒的全湖任务没有重新运行。现有工作集仍为 11,493,687 项；两份全湖排名材料及清单的大小、修改时间保持不变，原评分摘要和抽查的前 48 名保持一致。项目仍只有原有的两个查询结果，浏览没有新建全量排序材料。

## 修复范围

- 来源枚举使用来源上的成员存在性索引查询，避免每次轮询扫描整个工作集。
- 工作集与选择的帖子排序利用已有浏览索引按需求交。每次最多前进 8,192 个候选，额外每来源最多预读 129 项；小范围至多解析 4,096 项。多来源、未知帖子、相同帖子及两个方向均保留原排序语义。
- 稀疏范围通过游标继续定位，界面显示已检查数量；通用排序使用已返回的结果 ID 轮询。等待和失败期间暂停下一页缩略图预取，失败显示原始原因并提供重新读取入口。
- 真实榜单检查补充发现了两处索引失配：原始排名列不匹配表达式索引，`coalesce(rating,'z')` 排序触发临时排序。新的条件复用旧成果索引，按至多三个小页面合并并保留原有空值、同名次和分级顺序；常见总数使用已验证摘要。没有改写或重建既有评分表。
- 排名中间材料将多个 512 行读取批次合并到 8,192 行事务，保持 DELETE/FULL 设置，在读取、检查点和最终完成之前提交。
- 正常执行减少一次重复输入哈希，并复用一次完整输出校验的进程内证明。证明绑定文件身份、哈希及计划，Windows 文件句柄在校验至提交期间拒绝修改；恢复已有输出仍进行完整校验。
- 开发启动器默认使用 Release 引擎，缓存身份取自实际二进制 SHA-256。新任务记录阶段时长、分级和心跳；旧任务没有观测信息时不虚构历史耗时。
- 顶部入口为“保存当前范围”，榜单入口为“保存筛选为工作集”。保存对话框展示实际范围、条件和数量；配置页增加“查看已有排名”。

具体职责及兼容边界见[决策 0010](decisions/0010-bounded-browse-and-ranking-performance.md)。

## 查看现有排名

1. 打开项目 **Danbooru-评分筛选**，进入 **计算工具 → Danbooru 元数据排名 → 结果榜单**；配置页也可点击 **查看已有排名**。
2. 选择 **2026/9/9 21:38、11,493,687 项**的已发布成果。现有任务模式是“仅计算排名”。
3. 选择 G/S/Q/E 分级，“查看范围”选择合格候选，“入选通道”选择全部通道；可切换主排名或补救排名，点击行或“评分依据”查看明细。
4. 需要保存筛选结果时，填写 **每个分级前 N 名**，确认匹配数量，再点击 **保存筛选为工作集**。如果选择“各分级分别列出”，N 分别作用于每个分级。

现有的“Danbooru数据湖筛选”工作集来自全量输入查询，并未按排名截取。工作集保存成员，打开后的浏览排序由浏览器排序选项决定；排名顺序在结果榜单中查看。
