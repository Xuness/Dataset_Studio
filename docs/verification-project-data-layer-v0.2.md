## 真实 Danbooru 有界读取

只读索引位于 D:\Dataset\Danbooru，图片湖位于 E:\AI\AI_Dataset\Danbooru。当前 generation 为 gen-46699c39ac64482884e412524da0b599，SQLite 与 DuckDB 读取水位均为 2834。

先检查实际表结构与索引，再从 SHA 排序的 0、4、8、c 四个位置各取一个对象。通过独立 Debug 引擎的 HTTP API，对每个对象完成两轮来源记录、历史观察和原始元数据读取。没有递归扫描图片目录或修改归档索引。

| 复测项目 | 8 次请求的范围 |
| --- | --- |
| 来源记录 | 84–469 ms |
| 历史观察 | 215–649 ms |
| 原始元数据 | 80–512 ms |
| 引擎峰值 Working Set | 约 370 MiB |
| 读取完成后的 Private Bytes | 约 271 MiB |

样本中的条目 #3970458 与原始 JSON 一致：来源尺寸为 2480×3507，来源格式 PNG；实际存储对象为 WebP，195706 字节。应用保持存储尺寸未知，未把来源尺寸当作已测量的图片尺寸。日期级 observed_at 的 time_quality 也保留并显示。

第一次端到端实验出现过一次约 9.1 秒的观察请求。之后保留 DLL、释放每次请求的数据库连接，并把打开耗时计入读取预算；复测没有重现该延迟，但没有确定异常的唯一原因。8 秒为协作式原生读取预算，不能承诺所有操作系统 I/O 或 HTTP 关闭都在 8 秒内结束。

这不是 OS 冷缓存测试：未清空系统缓存。SHA 关联计划仍含列扫描，四个位置的正确性与耗时不能证明千万级全量、随机分布或长期运行性能。256 MB 配置是 DuckDB 的内存预算，不是进程 RSS 硬限制。

详细报告：.local/metadata-verification-1788788735236/report.json。最初实验保存在 .local/metadata-verification-1788788418171/report.json。静态审计与初始诊断使用归档自带 Python；产品和上述端到端接口使用应用自己的原生 DLL，不依赖该 Python 环境。
