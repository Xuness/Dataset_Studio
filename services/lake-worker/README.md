# Studio 数据湖更新服务

Linux x86_64 可使用 `pnpm setup:lake --dev --python=/path/to/python3.13` 创建项目内环境，在设置中选择 `.local/runtime/lake-worker/bin/python`。源码由同一引擎分发，凭据由 Linux 桌面密钥环保护；系统依赖和从零建湖入口见 [Linux 开发运行](../../docs/architecture/linux-development.md)。Windows 安装入口继续可用。

本模块由 Dataset Studio 仓库维护，负责 Danbooru、Yandere、Gelbooru 的 API 更新，以及 Pixiv 作者与作品采集，提供原文保留、图片处理、持久任务、调度、归档及在线发布。Rust 引擎负责应用生命周期和 HTTP 接口，React 工作台只使用公开 SDK。Pixiv 界面、独立命令与 API 使用见[来源采集接入](../../docs/architecture/source-collections.md)。

四个站点都可以在数据湖工作台选择“创建新的空湖”，填写独立的图片归档目录和在线目录后，从 ID、ID 区间或 Pixiv 作者/作品开始采集。已有湖选择“核验并登记”。创建过程不联网，失败后保持相同提交内容重试即可接续；未知非空目录不会被覆盖。Booru 公共入口为 `POST /v1/lake-updates/lakes/create` 和 `client.lakeUpdates.createLake({request_key, site, media_root, index_root})`；无需旧生产者索引或发行归档。身份与恢复规则见 [0065](../../docs/decisions/0065-empty-lake-initialization.md)。

Booru 的“按标签 / 画师 / 角色采集”接受全部包含、任一包含和排除三组精确 Tag，可附加 ID 边界。远端按单个正向标签取候选，完整组合条件在本地按同一条元数据判断；所有有效候选元数据保留，只有命中条件的图片进入下载队列。纯元数据策略不下载图片。该范围不推进全站新帖游标，预算暂停后可继续原分支。协议例：`{"kind":"tags","query":{"all":["artist_name","character_name"],"any":[],"none":["monochrome"]},"start_id":1,"end_id":10001}`。限制、恢复与计数见 [0066](../../docs/decisions/0066-booru-tag-discovery.md)。

标签采集可“优先复用近期扫描”（新建表单默认 24 小时，可调整）或“重新核验源站”。复用按实际已覆盖区间执行，补抓缺口并保留原获取时间。选择“从已入湖元数据选择”可按标签、ID 或全部已有帖子补图，无需先拥有图片；地址缺失或失效时只刷新相应帖子。接口 `lakeUpdates.catalog(libraryId, {query, version, after, limit})` 提供不依赖图片的有界帖子目录，目录版本可交给 `source=local` 的标签任务。覆盖依据、新鲜度和固定版本边界见 [0067](../../docs/decisions/0067-query-coverage-and-metadata-catalog.md)。

归档重建、旧任务交接及生产者索引退役使用 `node tooling/lake-storage.mjs`。它直接使用本仓库服务源码和已配置测试/维护解释器；重建仅写独立准备目录，退役默认预览，`--apply` 才回收清单内文件。完整边界与操作顺序见 [0050](../../docs/decisions/0050-archive-rebuild-and-producer-retirement.md)。

运行源码由引擎的 `build.rs` 编入二进制，启动时按源码摘要展开到应用数据目录的 `lake-worker/<revision>`。每次更新使用独立源码版本，不改写正在运行的版本。不需要外部 Danbooru-Store 仓库、editable install、工作目录或 PYTHONPATH。Python 解释器及第三方依赖仍是运行环境，不嵌入 Rust 可执行文件。

## 环境和启动

在仓库根目录运行：

```powershell
pwsh -File tooling/setup-lake-worker.ps1 -Dev
```

默认创建 `.local/runtime/lake-worker`，安装本目录 `pyproject.toml` 的依赖。可用 `-Python <python.exe>` 选择 Python 3.11–3.13。然后在“设置 → 数据湖 API”填写该环境的 Python 和共享更新状态目录。已有配置继续使用原 Python 与状态目录，旧 `store_root` 字段不再参与运行。

开发诊断可直接运行模块入口；常规使用由 Studio 引擎托管，无需手动另开运行器：

```powershell
& '.local/runtime/lake-worker/Scripts/python.exe' -I 'services/lake-worker/worker.py' --root '<更新状态目录>' --mode serve
```

`worker.py` 固定 UTF-8 并从自身路径导入 `studio_lake`。`--mode rpc` 继续使用协议版本 1 的标准输入/输出 JSON，凭据不进入命令行。不要同时启动多个更新控制器。

## 代码和数据边界

- `src/studio_lake/updates`：三站适配、控制数据库、下载、速率和设备调度、固定输入、归档提交与重放。
- `collectors/pixiv`：网页响应、会话、作者目录与关系解释；`collections`：新采集任务、计划、回执与控制回放；`media_lake`：多媒体归档 2 / 在线 3 的写入、发布、读模型与重建。
- `image_policy.py`：自定义配方校验、标识和实际编码；`ingest.py` 保留原先两种策略的字节处理与旧归档恢复语义。
- `library.py`、`metadata.py`、`online*.py`、`index.py`：现有规范湖和在线投影契约。`daily_state.py` 等仅为读取、接续既有归档证据保留，Studio 不接管旧每日自动化入口。
- `upstream-origin.json`：迁入前的 Store 提交与文件摘要，用于追踪初始来源；以后在 Studio 内维护。

索引、状态与准备数据继续使用配置的 SSD 目录，图片与原始元数据归档使用原 HDD 目录。旧三湖身份、在线格式 2、项目格式 13 不改变，无需重新转换或复制。新增 Pixiv 湖独立使用归档 2 / 在线 3；运行器和读取端按版本分派。

控制数据库当前为 schema 14：v4 保护自定义配方兼容性，v5–v7 记录取消回收、调度和位置迁移，v8–v11 增加 Pixiv 采集、增量计划、回执和恢复，v12 隔离不理解标签范围的旧运行器，v13 增加查询页覆盖与访问条件身份，v14 隔离不理解本地缺图条件和 Pixiv 标签条件的旧运行器。升级前检查旧运行器和在途任务锁；有活动执行时明确拒绝升级。建表与版本推进在同一事务中提交，旧任务、幂等键、游标、凭据、计划和固定输入保留。已执行的迁移需要补充结构时，必须新增版本，不能只修改旧版本的建表代码。旧独立 `daily` 流程仍有自己的状态及锁，不读取此控制库。

配置前先执行无状态依赖/协议握手，验证通过并就绪后才保存并启动调度。已配置时仍可在设置页更换解释器，保持原控制状态目录；故障状态由 Rust 提供，自动启动重试采用 10–300 秒退避。状态目录迁移不包含在解释器更换操作中。

搬盘前使用设置中的“迁移数据湖位置”冻结该湖写入并建立检查点；prepared 后搬动媒体/索引，再验证并完成读写位置切换。支持只移动一个目录和中断后继续。未经准备的离线旧位置不能验证备份的新旧，需恢复旧位置后准备。完整语义、版本保留与旧副本边界见 [0047](../../docs/decisions/0047-lake-runtime-and-location-recovery.md)。

## 保存策略

更新下载按 API 返回的可用原图地址执行，`is_deleted` / `is_banned` 仅作为来源状态保留，不单独阻止下载。原始响应与结构化元数据中的标记均保留；无可用地址或实际下载失败会分别记录原因。旧任务可用“重试未获取项”重新检查被标记跳过的记录。见 [0049](../../docs/decisions/0049-source-status-and-media-availability.md)。

`media.profile` 保留 `metadata_only`、`original`、`webp-2048-q95`，新增 `custom`。没有新增全局默认。自定义示例：

```json
{
  "profile": "custom",
  "existing": "match_profile",
  "allow_sample": false,
  "encoding": {
    "version": 1,
    "format": "webp",
    "max_edge": 3072,
    "quality": 90,
    "lossless": false,
    "method": 6,
    "animation": "preserve",
    "alpha": "preserve"
  }
}
```

共同参数：`max_edge=null` 保持原尺寸，否则为 1–32768 像素，等比例缩小且不放大。`animation=preserve` 对多帧图保留原文件，跳过缩放/转码；`first_frame` 明确仅取首帧。`alpha` 为保留、背景合成或拒绝透明图片；合成使用 `background=#RRGGBB`。JPEG 不能选择保留透明通道。

| 编码 | 专属参数                                           |
| ---- | -------------------------------------------------- |
| WebP | `lossless`；有损 `quality=1–100`；`method=0–6`     |
| JPEG | `quality=1–100`；`optimize`；`subsampling=444/420` |
| PNG  | 无损编码；`compress_level=0–9`，没有有损质量滑条   |

不兼容的参数会被拒绝。无损编码不撤销用户选择的缩放、首帧提取或背景合成。自定义编码保留/转换颜色配置，归档中记录源图片信息、编码配方、Pillow/编码器版本及实际尺寸；API 原文保留不受编码策略影响。

规范化编码配方的 SHA-256 构成 `storage_profile`。改变尺寸、质量、动画或透明处理会改变配方身份；取得图片时的备用图许可与已有图片策略不改变配方身份。`keep` 仍可复用同一媒体身份的已有图片；`match_profile` 要求匹配完整配方，再遵守原图/备用图来源约束。旧资产不删除，物理字节继续按 SHA-256 去重。

界面的命名预设使用应用偏好及修订保护，跨项目共享。在“保存策略”或“保存与管理预设”中选择预设都会立即填入图片参数；界面显示所选预设与当前设置是否一致，修改后可点“应用预设”恢复保存值。管理区展示预设参数摘要；应用不改变更新范围、预算或执行方式。创建任务/计划时固定参数；修改或删除预设不会修改已创建任务/计划。

高级预算只限制单轮执行工作量，不定义任务范围或成功下载目标。`page_budget` 是候选元数据扫描页数上限（1–100000）；Yandere/Danbooru 普通区间请求每页最多 200 条，Gelbooru 为 100 条，固定 ID 查询的实际批次可更小。`item_budget` 是本轮 API 返回并匹配范围的记录数上限（1–10000000），复用、仅元数据、无图记录也会计数。任一上限耗尽会暂停；用户继续后重置本轮预算并接续原检查点。希望一次完成固定范围时留出预算余量，因为确认范围结束可能还需要一轮扫描；ID 区间的宽度不等于实际可下载图片数。

## 新帖补全基线

“补充新帖”的起点 ID 不含该帖子。首次追新需要明确起点；HF 导入的最大 ID 可以作为继续获取后续新帖的边界，但不证明更早的帖子或图片全部齐全。单独验收几个较新的 ID 也不会建立连续覆盖。

新帖任务启动时查询远端并冻结本轮上界；元数据扫描完成后，将该上界保存为该湖共享的 `update_new_metadata_cursor`。下一次起点留空便从保存位置之后继续。它只随实际的新帖扫描推进，不会因查看数据湖、导入数据或下载指定 ID 自动移动；推进时还会检查原基线，避免旧任务覆盖已经变化的位置。

基线表示元数据扫描进度，不表示图片全部下载成功。失败、等待空间或尚未处理的图片仍属于原任务，应在原任务继续或重试；新帖任务不会替代历史缺图修复。任务运行期间网站后来新增的帖子由下一轮获取。

## 下载与调度

数据湖工作台的“下载与调度”管理跨项目、跨任务共享的执行参数，使用独立修订保护；不修改已创建任务的范围、保存配方或幂等身份。对应公开 SDK 为 `lakeUpdates.pipeline()` / `savePipeline()`，HTTP 为 `GET/PUT /v1/lake-updates/pipeline`。设置保存在控制库 `settings.pipeline_v1`，运行器约每秒读取一次，下调限额不会中断已有占用；暂停任务仍需手动继续。

流水线为：元数据扫描 → 持久候选队列 → 并发下载 → 受限编码 → 单路批量归档与热发布。元数据网络请求不持有图片发布协调锁；同湖的归档和队列检查点推进串行。可以选择边扫描边下载或先建立完整清单，后者仍受任务扫描预算限制。

媒体发布在每湖独立的执行线程中进行。写入和同步归档时，协调器仍可收集下载结果、补充下载和送入编码；同湖最多一个媒体批次在发布，发布中的图片仍计入在途和暂存额度。临时 API 连接/服务失败只让扫描等待重试，已获取的候选图片继续处理；错误摘要和重试时间显示在任务详情中。

| 设置                      | 建议初始值                               |
| ------------------------- | ---------------------------------------- |
| 每站点下载并发            | 4                                        |
| 每站点 API 请求起始频率   | 0.9 次/秒                                |
| 每站点图片请求起始频率    | 2 次/秒；可留空不额外限频                |
| 同时活动数据湖            | 3                                        |
| 运行器共享编码并发        | 2                                        |
| 解码内存估算预算          | 2048 MiB                                 |
| SSD 暂存 / 磁盘保留空间   | 8192 / 2048 MiB                          |
| 单张下载 / 像素上限       | 128 MiB / 100000000 像素                 |
| 每湖在途图片 / 元数据前看 | 64 项 / 5000 条                          |
| 发布批次                  | 32 项、64 MiB、10 秒；任一阈值满足后发布 |
| 图片下载带宽              | 默认不限，可按 MiB/s 约束所有湖合计吞吐  |

这些是本机调优起点，不是站点公布的配额。并发限制同时存在的工作，请求/秒限制开始 HTTP 请求的频率，图/秒表示成功入湖产出。API 与图片通道分别限速；429/503 的 Retry-After 会形成共享冷却，图片限频关闭也不会跳过冷却。API 限速在同一控制目录共享；编码、暂存与带宽额度由同一运行器共享，不约束其他软件的网络流量。

下载线程各持有一个可复用 Session。完整原件以 `.downloaded` 和校验收据落在 SSD，编码产物继续兼容旧 `.ready` 收据。恢复时校验产物，避免重复下载；已确认入湖的产物再清理。

暂存按原件、编码输出与打包副本的阶段峰值准入，不再为每张图片预留四倍下载上限。响应长度明确后纠正预留；未知长度从最多 8 MiB 起步、每 4 MiB 扩容，取得额度后才写入新块。编码前用真实尺寸校正，完成后收缩到实际产物和打包余量。暂时不能扩容时保留断点并让其他工作继续，这种等待不增加下载失败次数；真实空间耗尽仍等待可恢复重试。解码内存单独按像素/输入体积估算，不是进程 RSS 的硬上限。

界面显示等待下载、下载、等待编码、编码、等待发布、发布中及暂存等待的数量，并聚合并行文件的字节进度。“共享资源占用”区分实际暂存、预留额度和上限，也显示解码内存额度；数值对应遥测采样时间。字节率和入湖图率采用最长 30 秒窗口；停止后清零。阶段累计时长是工作项之和，并发时可超过墙钟时间。旧任务升级前没有记录的请求数和阶段时长不会回填。

不需要重建三个湖或迁移任务定义。旧暂停任务可直接继续；新版本还修正了本地范围最后一页遗漏以及已知 ID 末端因预算恰好用尽而多暂停一轮的边界。

设计与兼容边界见 [ADR 0041](../../docs/decisions/0041-lake-download-pipeline.md) 和 [ADR 0043](../../docs/decisions/0043-independent-lake-stages.md)。

## 断点与异常恢复

未完成图片保留 `.partial` / `.partial.json` 校验检查点。断网、暂停或服务退出后，下一次执行自动请求剩余字节；强制终止进程时回到最近一次持久检查点，通常最多回退约 4 MiB 或两秒的数据。只有原图校验和或强 ETag 足以验证内容时才使用范围请求，服务器不支持时安全重下该张图片；损坏或变化的断点不会直接拼接入湖。

前端重新打开后读取原任务；后台 worker 退出由引擎监督器重新拉起，原运行任务自动恢复归档/候选队列后接续。手动暂停、取消和已完成的任务保持原状态。任务详情的“诊断与恢复”显示后台接续记录和最近网络异常，流水线统计显示断点续传次数。网络异常只保留类型与字节/时间信息，避免泄露请求 URL 和凭据。

不需要迁移正式湖或重建已有任务；旧版尚未保留的半张下载无法找回。协议、强制终止测试与行为边界见 [ADR 0042](../../docs/decisions/0042-resumable-lake-transfers.md)。

## 验证

取消后的暂存回收独立记录进度：等待所有执行阶段退出，核对已接受归档和控制回执，再按任务目录分批清理。任务详情显示回收完成或待重试；暂停、服务退出和可重试失败仍保留断点。取消任务不能重新打开，重复恢复已排队任务不会增加执行次数。更新控制库升级到 v5 时为旧取消任务补记回收责任，需先停止仍运行的旧版控制进程。按湖选择到期队首，使单湖积压不再挡住其他空闲槽位。协议及限制见 [ADR 0046](../../docs/decisions/0046-update-command-handoff-and-cancel-cleanup.md)。

图片 HTTP 404 进入有次数上限的重试，不直接认定帖子删除。同一站点图片通道在 60 秒内累计 8 次 404 后冷却至少 60 秒，仍遵守更长的既有冷却；已经开始的下载及元数据、编码、发布继续工作。重试最多 8 次，耗尽后保留缺口供检查。此保护不代表站点公布了限流规则，也不绕过访问限制。

“继续”接续原队列；“重试未获取项”优先重用已发布元数据与原下载断点，仅缺少有效地址、来源删除/受限、元数据缺失或 404 已耗尽尝试时刷新 API。兼容带 RGB ICC 的灰度图片；无法处理的色彩配置只产生单张 `image_color_profile_error`，原件保留，其余图片照常处理。详见 [ADR 0044](../../docs/decisions/0044-lake-media-recovery.md)。

PNG 元数据兼容解码与下载后的资源准入共用同一模块：仅对已知元数据块重算解码副本的 CRC，并保留完整原始块及异常记录；较大 ICC 单独有界解压（4 MiB）并回填图片。像素、透明度、动画块、文件结构仍严格检查，原始下载字节不改动，不使用全局宽松解码开关。完整限制与验收见 [ADR 0048](../../docs/decisions/0048-bounded-png-metadata-recovery.md)。

IEND 后附加数据在 16 MiB 累积预算内完整保留为处理详情，解码只使用 PNG 主体。未结束的 ICC 压缩流只有在块 CRC 正确、完整配置大小及标签范围通过检查且 LittleCMS 可读取时才兼容处理；原块与动作保留，原图/动画输出不裁剪。详见 [ADR 0051](../../docs/decisions/0051-png-trailing-data-and-complete-icc.md)。

按修改范围选择 pytest 文件或用例，例如 `pnpm test:lake tests/test_png_compat.py -k metadata_crc`；参数相对本服务目录。只有需要完整服务回归时才执行不带过滤的 `pnpm test:lake`。涉及 HTTP/SDK 的更新行为用 `pnpm test:integration lake-updates`，工作台交互变化按需用 `pnpm test:lake-ui`，不默认连续运行三套。优先使用 `.local/runtime/lake-worker`，也可指定 `STUDIO_LAKE_TEST_PYTHON`，不再使用 `STUDIO_LAKE_TEST_STORE`。夹具和证据只写入 `.local/`；测试不访问真实站点，不创建正式计划。
